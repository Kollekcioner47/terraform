ПРАКТИКА 2. СОСТОЯНИЕ: ОТ ЛОКАЛЬНОГО ФАЙЛА ДО ОБЩЕГО ХРАНИЛИЩА

Продолжительность: 2 академических часа.
Провайдер: yandex-cloud/yandex. Практика выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ЗАНЯТИЯ

  Вы поймёте, что лежит в файле состояния и почему он важнее самих
  файлов конфигурации. Перенесёте состояние в Object Storage, включите
  блокировку, чтобы двое не поломали инфраструктуру одновременно,
  возьмёте под управление ресурс, созданный руками, переименуете ресурс
  без пересоздания и выведете ресурс из-под управления, не удаляя его.

ЧТО НУЖНО ЗАРАНЕЕ

  * Доступ в облако из практики 1: каталог, сервисный аккаунт, ключ.
  * Роль storage.editor или storage.admin у сервисного аккаунта:
    без неё он не сможет читать и писать состояние в бакете.
  * Понимание, что такое ресурс, план и apply — это практика 1.

ПОЧЕМУ ЭТО ГЛАВНАЯ ПРАКТИКА КУРСА

  В практике 1 состояние лежало в файле terraform.tfstate рядом
  с конфигурацией. Пока вы работаете один и на своей машине, это
  работает. Как только появляется второй человек, вторая машина или
  конвейер, начинаются проблемы, которые стоят инфраструктуры:
  состояние теряется, переписывается чужими руками или оказывается
  в git вместе с паролями.

  Всё, что разбирается дальше в курсе — модули, окружения, конвейер, —
  опирается на то, как хранится состояние.


========================================================================
1. ЧТО ТАКОЕ СОСТОЯНИЕ
========================================================================

Состояние (state) — это файл, в котором Terraform запоминает, какие
ресурсы он создал и какими они получились. Это не отчёт и не журнал,
а рабочий инструмент: без него Terraform не знает, чем управляет.

Посмотреть, что внутри, можно командой:

  terraform show

Более полное представление — выгрузка в JSON:

  terraform state pull

Пример того, что там на самом деле лежит (сокращённо):

  {
    "version": 4,
    "terraform_version": "1.16.4",
    "resources": [
      {
        "mode": "managed",
        "type": "yandex_vpc_network",
        "name": "course",
        "provider": "provider[\"registry.terraform.io/yandex-cloud/yandex\"]",
        "instances": [
          {
            "schema_version": 0,
            "attributes": {
              "id": "enpkjh306mefquqoocb7",
              "name": "tf-state-p2-net",
              "folder_id": "b1gr0h5em3390pf2o9iq",
              "labels": { "course": "terraform", "lesson": "2" },
              "default_security_group_id": "enp6btk68ff00h5odkh5",
              ...
            }
          }
        ]
      }
    ]
  }

Что здесь важно понять:

  * Состояние связывает ОПИСАНИЕ с РЕАЛЬНЫМ ОБЪЕКТОМ в облаке.
    Именно идентификатор id из состояния говорит Terraform, что
    «yandex_vpc_network.course» — это сеть enpkjh306mefquqoocb7,
    а не какая-то другая.
  * В состоянии лежат значения ВСЕХ атрибутов, включая те, которые
    вы не указывали: идентификатор группы безопасности по умолчанию,
    время создания, служебные поля.
  * Если состояние потерять, Terraform перестанет узнавать свои
    ресурсы. Следующий apply попытается создать их заново — а облако
    ответит ошибкой, что объект с таким именем уже есть, либо
    (что хуже) создаст дубликаты с другими именами.

ПОЧЕМУ СОСТОЯНИЕ НЕЛЬЗЯ ПРАВИТЬ РУКАМИ

  Соблазн большой: открыть файл, поменять имя или идентификатор.
  Не делайте так. В состоянии есть счётчик версий и контрольные
  суммы; испорченный файл приводит к ошибкам вида «state snapshot
  was not created with the same Terraform version» или к молчаливому
  созданию второй копии ресурса.

  Для правки состояния есть команды terraform state — они разбираются
  ниже, в разделе 10.

ПОЧЕМУ СОСТОЯНИЕ — ЭТО СЕКРЕТ

  В состоянии оказываются все значения, которые вы передали в ресурсы:
  пароли баз данных, ключи, токены. Даже если вы задали пароль
  переменной со флагом sensitive, в состоянии он лежит открытым
  текстом: флаг sensitive влияет только на вывод в терминал.

  Отсюда три правила:

  1. Файлы состояния (*.tfstate, *.tfstate.backup) — в .gitignore.
  2. Каталог .terraform — тоже не в git: там скачанные провайдеры.
  3. Доступ к состоянию ограничивают: хранят в бакете с ограниченным
     доступом или в хранилище секретов (практика 6).

  ИСПРАВЛЕНО. В прежней версии курса файл terraform.tfstate и каталог
  .terraform лежали прямо в материалах курса рядом с конфигурацией.

  Проверьте свой проект:

    cat .gitignore

  В нашем .gitignore уже перечислены tfstate, tfvars, ключи и .env.

------------------------------------------------------------------
2. ГДЕ ХРАНИТЬ СОСТОЯНИЕ
------------------------------------------------------------------

Вариантов три, и выбирать надо осознанно.

  ЛОКАЛЬНЫЙ ФАЙЛ. Умолчание. Работает, пока вы один. Минусы: файл
  теряется вместе с машиной, лежит без шифрования, блокировки нет —
  два одновременных apply испортят состояние.

  ХРАНИЛИЩЕ В ОБЛАКЕ (Object Storage, S3, бакет в VK Cloud). Общее
  хранилище с блокировкой и версионированием. Это то, что мы делаем
  в этой практике.

  УПРАВЛЯЕМЫЙ СЕРВИС (Terraform Cloud, Yandex Cloud Managed
  Terraform). Берёт на себя хранение, блокировку, права и историю
  запусков. Удобно, но это отдельный продукт со своей оплатой, и его
  в курсе нет: принципы те же, а зависимость от внешнего сервиса
  на занятиях только мешает.

Почему Object Storage в Яндекс Облаке:

  * бакет — глобальный ресурс, доступен откуда угодно;
  * поддерживается версионирование: испорченное состояние можно
    откатить;
  * поддерживаются условные записи, значит работает нативная
    блокировка Terraform;
  * есть S3-совместимый API, поэтому используется штатный бэкенд s3.

------------------------------------------------------------------
3. СОЗДАЁМ БАКЕТ ДЛЯ СОСТОЯНИЯ
------------------------------------------------------------------

Хитрость, о которой надо знать сразу: бакет нельзя создать тем же
состоянием, которое в нём будет лежать. Получится замкнутый круг:
Terraform не может записать состояние, пока бакета нет, а описать
бакет он может только применив план.

Поэтому такой бакет создают отдельно: руками, скриптом или отдельной
конфигурацией (вариант «bootstrap» — в части 2).

Готовый скрипт лежит в files/02_state/create-state-bucket.sh. Ниже —
то же самое по шагам.

  # 1. Бакет. Имя должно быть уникальным во всём Object Storage
  yc storage bucket create --name tf-course-state-ivan

  # 2. Версионирование
  yc storage bucket update --name tf-course-state-ivan \
    --versioning versioning-enabled

  # 3. Права сервисного аккаунта на каталог
  yc resource-manager folder add-access-binding <folder_id> \
    --role storage.editor \
    --service-account-id <sa_id>

  # 4. Статический ключ доступа к Object Storage
  yc iam access-key create \
    --service-account-id <sa_id> \
    --description "доступ к бакету состояния" \
    --format json > s3-access-key.json

ТРИ ЛОВУШКИ ЭТОГО ШАГА

  Ловушка 1: значение параметра версионирования. Командная строка
  принимает только значения из перечисления:

    versioning-disabled | versioning-enabled | versioning-suspended

  То есть --versioning versioning-enabled, а не --versioning enabled.
  При неверном значении команда отвечает списком допустимых.

  Ловушка 2: структура ответа при создании ключа. В ответе два
  значения, и идентификатор ключа лежит во вложенном объекте:

    {
      "access_key": {
        "id": "ajetie9irg2oqtm5o0vo",
        "key_id": "YCAJEXXXXXXXXXXXXXXXXX",   <- это access_key
        "created_at": "...",
        "description": "..."
      },
      "secret": "..."                             <- это secret_key
    }

  В access_key нужно значение key_id (начинается с YCAJE), а не id.
  Если подставить весь объект целиком, Object Storage ответит
  «400 Bad Request» — и это худший вид ошибки: непонятно ни что
  случилось, ни где искать причину. Разбор в приложении 3.

  Ловушка 3: имя бакета. Только строчные латинские буквы, цифры,
  точка и дефис. Русские буквы, заглавные и подчёркивания недопустимы:
  облако ответит InvalidBucketName: The specified bucket is not valid.
  Это сообщение легко получить, если имя бакета подставлялось в файл
  автоматически и «поехало» из-за кодировки.

------------------------------------------------------------------
4. ПОДКЛЮЧАЕМ ХРАНИЛИЩЕ: БЛОК BACKEND
------------------------------------------------------------------

В каталоге проекта появляется файл backend.tf (в материалах курса он
лежит как backend.tf.example — переименуйте):

  terraform {
    backend "s3" {
      endpoints = {
        s3 = "https://storage.yandexcloud.net"
      }

      bucket = "tf-course-state-ivan"
      region = "ru-central1"
      key    = "course/terraform.tfstate"

      use_lockfile = true

      skip_region_validation      = true
      skip_credentials_validation = true
      skip_requesting_account_id  = true
      skip_s3_checksum            = true
    }
  }

Разберём строки, которые вызывают вопросы.

  endpoints.s3 — адрес S3-совместимого API Object Storage.

  region = "ru-central1" — регион. Значение условное: настоящий регион
  берётся из адреса сервиса, а поле нужно, чтобы бэкенд s3 был
  удовлетворён.

  key — путь к файлу состояния ВНУТРИ бакета. Можно складывать
  состояния разных проектов и окружений в один бакет, разводя их
  ключами: course/prod/terraform.tfstate, course/dev/terraform.tfstate.

  use_lockfile = true — нативная блокировка состояния (подробно
  в разделе 5).

  skip_* — отключение проверок, которые бэкенд выполняет для AWS.
  Object Storage совместим с S3 не во всём, поэтому эти проверки
  проходят вхолостую и мешают.

ВАЖНОЕ ОГРАНИЧЕНИЕ: В БЛОКЕ BACKEND НЕЛЬЗЯ ИСПОЛЬЗОВАТЬ ПЕРЕМЕННЫЕ

  Ни var.cloud_id, ни local.bucket_name здесь не работают:

    Error: Variables not allowed
    Variables may not be used here.

  Причина: блок backend читается до того, как Terraform вычисляет
  значения переменных. Поэтому имя бакета пишут текстом, а секретные
  значения передают отдельно — переменными окружения или файлом
  с ключом -backend-config (раздел 5).

  Привычка: имя бакета и ключ состояния — не секрет, их можно
  хранить в файле. Ключи доступа — секрет, им место вне репозитория.

------------------------------------------------------------------
5. КЛЮЧИ ДОСТУПА И ПЕРВАЯ ИНИЦИАЛИЗАЦИЯ
------------------------------------------------------------------

Ключи доступа к бакету передаются в момент инициализации. Два способа.

  Способ 1: файл с ключами (удобно, когда проектов много).

  Создайте backend.tfvars (в git не попадает):

    access_key = "YCAJEXXXXXXXXXXXXXXXXXX"
    secret_key = "..."

  И инициализируйте проект с ним:

    terraform init -backend-config=backend.tfvars

  Способ 2: переменные окружения (удобно в конвейере и когда ключи
  выдаёт система управления секретами).

    export AWS_ACCESS_KEY_ID="YCAJEXXXXXXXXXXXXXXXXXX"
    export AWS_SECRET_ACCESS_KEY="..."

  Имена переменных именно AWS_*: бэкенд называется s3 и читает
  стандартные переменные AWS.

Инициализация:

  terraform init -backend-config=backend.tfvars

  Initializing the backend...
  Successfully configured the backend "s3"! Terraform will automatically
  use this backend unless the backend configuration changes.

Если состояние уже было локальным, добавьте ключ миграции:

  terraform init -migrate-state -backend-config=backend.tfvars

  Terraform has detected that the configuration specified for the
  backend has changed. Would you like to copy your existing state
  to the new backend?
    Enter a value: yes

  Successfully configured the backend "s3"! ...
  Terraform has successfully migrated your existing state.

После миграции локальный terraform.tfstate можно удалить: он больше
не используется. Файл terraform.tfstate.backup — это автоматическая
резервная копия предыдущего состояния, Terraform держит её сам.

Проверьте, что состояние действительно уехало:

  yc storage s3api list-objects --bucket tf-course-state-ivan

  - key: course/terraform.tfstate
    size: "8910"

Полезно помнить два ключа инициализации:

  -migrate-state   перенести существующее состояние в новое хранилище
  -reconfigure     просто перечитать настройки бэкенда, состояние
                   не переносить (например, сменили ключи доступа)

------------------------------------------------------------------
6. БЛОКИРОВКА СОСТОЯНИЯ
------------------------------------------------------------------

Зачем. Представьте, что двое одновременно запустили apply. Оба
прочитали состояние, оба посчитали план, оба начали писать. Второй
запишет своё состояние поверх первого, и часть ресурсов «потеряется»
из управления: в облаке они есть, а Terraform про них не знает.
Следующий apply попытается создать их заново.

Как это работает у нас. Параметр use_lockfile = true включает нативную
блокировку (Terraform 1.10 и новее). Перед изменением Terraform
создаёт в бакете рядом с состоянием объект-замок:

  course/terraform.tfstate        состояние
  course/terraform.tfstate.tflock замок

Создание замка — условная запись: «создай объект, только если такого
ещё нет» (заголовок If-None-Match). Object Storage это поддерживает,
поэтому механизм работает.

Как проверить, что блокировка работает. Запустите apply и, пока он
идёт, во втором терминале — план:

  # терминал 1
  terraform apply

  # терминал 2, сразу же
  terraform plan -lock-timeout=0s

Второй запуск получит ошибку (полный вид — в разделе 12):

  Error: Error acquiring the state lock
  Error message: operation error S3: PutObject, https response error
  StatusCode: 412, RequestID: ..., api error PreconditionFailed:
  At least one of the pre-conditions you specified did not hold
  Lock Info:
    ID:        f0de5be3-df51-6dbb-10c1-f2eb323d3c1f
    Path:      tf-course-state-ivan/course/terraform.tfstate
    Operation: OperationTypeApply
    Who:       user@host

Код 412 — это и есть сработавшая защита. Если бы состояние лежало
локально, второй запуск спокойно начал бы работу.

Залипший замок. Если Terraform был прерван (Ctrl+C, пропала связь,
упала машина), замок может остаться. Тогда применяют:

  terraform force-unlock f0de5be3-df51-6dbb-10c1-f2eb323d3c1f

Идентификатор берётся из текста ошибки. ПРЕЖДЕ ЧЕМ снимать замок,
убедитесь, что процесс действительно не работает: если второй
человек на самом деле применяет изменения, снятие замка вернёт нас
к той самой ситуации, от которой замок и защищает.

ПОЧЕМУ МЫ НЕ ИСПОЛЬЗУЕМ СХЕМУ ИЗ ДОКУМЕНТАЦИИ С YDB

  Документация Яндекс Облака описывает блокировку состояния через
  базу данных YDB: создаётся serverless-база, в ней документная
  таблица LockID, а в блоке backend указывается параметр
  dynamodb_table. В той же статье есть предупреждение: начиная
  с Terraform 1.11 блокировка через Document API объявлена устаревшей
  и будет удалена в одной из ближайших версий.

  Мы используем use_lockfile — он опирается на возможности самого
  Object Storage, не требует отдельной базы и не устарел. Схема с YDB
  упомянута здесь только для того, чтобы вы не удивились, встретив
  её в документации или в чужой конфигурации.

------------------------------------------------------------------
7. КОМАНДЫ TERRAFORM STATE
------------------------------------------------------------------

Это инструменты для работы с состоянием. Пользоваться ими нужно
аккуратно: они меняют то, чем Terraform управляет, и не трогают
ресурсы в облаке.

  terraform state list
      Список адресов ресурсов под управлением.

      data.yandex_compute_image.os
      yandex_compute_instance.app
      yandex_vpc_network.course
      yandex_vpc_subnet.app_subnet

  terraform state show <адрес>
      Подробности одного ресурса, как он записан в состоянии:

      # yandex_vpc_network.course:
      resource "yandex_vpc_network" "course" {
          id     = "enpkjh306mefquqoocb7"
          name   = "tf-state-p2-net"
          labels = { "course" = "terraform", "lesson" = "2" }
          ...
      }

  terraform state pull
      Выгрузить состояние целиком в stdout (удобно для копии).

  terraform state mv <откуда> <куда>
      Перенести ресурс на другой адрес. Эквивалент блока moved,
      но делается руками и не остаётся в истории изменений.

        terraform state mv yandex_vpc_subnet.app \
                            yandex_vpc_subnet.app_subnet

  terraform state rm <адрес>
      Убрать ресурс из состояния, НЕ удаляя его из облака. После этого
      Terraform про него не знает.

        terraform state rm yandex_vpc_network.imported

      ВАЖНО: сразу после state rm нужно убрать описание ресурса
      из конфигурации, иначе следующий apply создаст его заново —
      второй экземпляр рядом с существующим.

  Чего делать НЕ надо: править файл состояния руками и «подчищать»
  его редактором. Для всего есть команды.

  Ответ на частый вопрос: почему после state rm ресурс остался
  в облаке, а платить за него всё равно надо? Потому что состояние —
  это записи Terraform о том, чем он управляет. Удаление из состояния
  ничего не удаляет в облаке.

------------------------------------------------------------------
8. ИМПОРТ: ВЗЯТЬ ПОД УПРАВЛЕНИЕ ТО, ЧТО СОЗДАНО РУКАМИ
------------------------------------------------------------------

Ситуация типовая: инфраструктура частично существует. Сеть создали
в консоли, машину подняли скриптом, бакет завели вручную. Удалять
и создавать заново нельзя — в сети работает чужой сервис.

Два способа импорта.

СПОСОБ 1: БЛОК IMPORT (рекомендуемый, Terraform 1.5 и новее)

  В конфигурации появляется блок:

    import {
      to = yandex_vpc_network.imported
      id = "enp9tnph2kvspjhnmkn7"
    }

  Описания ресурса писать не нужно: Terraform сгенерирует его сам.

    terraform plan -generate-config-out=generated.tf

    # yandex_vpc_network.imported will be imported
    # (config will be generated)
      resource "yandex_vpc_network" "imported" {
          description = "сеть, созданная вручную для проверки импорта"
          folder_id   = "b1gr0h5em3390pf2o9iq"
          id          = "enp9tnph2kvspjhnmkn7"
          labels      = {}
          name        = "hand-made-net"
          subnet_ids  = []
      }

    Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.

  Появится файл generated.tf с описанием существующего ресурса.
  Его надо прочитать, убрать лишнее (поля, которые вы не хотите
  фиксировать) и перенести в свой файл конфигурации — а сам
  generated.tf удалить, чтобы не было двух описаний одного ресурса.

  Затем:

    terraform apply
    yandex_vpc_network.imported: Import complete [id=enp9tnph2kvspjhnmkn7]
    Apply complete! Resources: 1 imported, 0 added, 0 changed, 0 destroyed.

  И ПОСЛЕ ЭТОГО УДАЛИТЕ БЛОК IMPORT из конфигурации: он нужен один раз.
  Оставленный блок при следующем применении снова попытается
  импортировать тот же ресурс.

СПОСОБ 2: КОМАНДА IMPORT (когда нужно разово, вручную)

  terraform import yandex_vpc_network.imported enp9tnph2kvspjhnmkn7

  Перед этим описание ресурса надо написать самому. Команда только
  вносит соответствие в состояние.

ЧТО НАДО ПОНИМАТЬ ПРО ИМПОРТ

  * Импорт НЕ меняет ресурс в облаке. Он лишь вносит ресурс
    в состояние.
  * Если описание в конфигурации не совпадает с реальностью,
    следующий план покажет изменения — и это самая опасная минута
    всей практики: случайная правка чужой сети или диска стоит дорого.
    Читайте план внимательно.
  * Далеко не все ресурсы провайдера поддерживают импорт. Если
    ресурс не импортируется, остаётся либо пересоздать его, либо
    жить с ним вне Terraform.

------------------------------------------------------------------
9. ПЕРЕИМЕНОВАНИЕ РЕСУРСА БЕЗ ПЕРЕСОЗДАНИЯ (MOVED)
------------------------------------------------------------------

Имя ресурса внутри конфигурации — это адрес в состоянии. Захотелось
переименовать yandex_vpc_subnet "app" в "app_subnet" — и если просто
поменять имя, Terraform увидит удаление старого адреса и создание
нового. Для машины это означает удаление вместе с диском.

Решение — блок moved:

  moved {
    from = yandex_vpc_subnet.app
    to   = yandex_vpc_subnet.app_subnet
  }

Порядок работы:

  1. Переименовать ресурс в конфигурации и во всех ссылках на него
     (в нашем примере — в описании машины и в выводах).
  2. Добавить блок moved.
  3. Посмотреть план:

       # yandex_vpc_subnet.app has moved to yandex_vpc_subnet.app_subnet
         resource "yandex_vpc_subnet" "app_subnet" {
             id   = "fl8597657tum6usjpubu"
             name = "tf-state-p2-subnet-ru-central1-d"
         }
       Plan: 0 to add, 0 to change, 0 to destroy.

     Обратите внимание: идентификатор не изменился, ресурс не пересоздан,
     изменений ноль.

  4. Применить: terraform apply.
  5. Блок moved можно оставить — он безвреден и служит документацией
     для коллег.

Блок moved умеет и более сложные переезды: перенос ресурса в модуль
и обратно, объединение count в for_each, разбиение одного ресурса
на несколько. Синтаксис тот же.

  Правило: переименовывать адреса ресурсов можно и нужно, но только
  вместе с блоком moved. Иначе — пересоздание.

------------------------------------------------------------------
10. ВЫВЕСТИ РЕСУРС ИЗ УПРАВЛЕНИЯ, НЕ УДАЛЯЯ ЕГО (REMOVED)
------------------------------------------------------------------

Обратная задача: ресурс нужен, но управлять им отсюда больше
не нужно — он переезжает в другую конфигурацию или в модуль.

Если просто удалить его из файлов, следующий apply УДАЛИТ его
в облаке. Чтобы этого не произошло, нужен блок removed:

  removed {
    from = yandex_vpc_network.imported

    lifecycle {
      destroy = false     # ресурс в облаке остаётся
    }
  }

План в этом случае говорит человеческим языком:

  Terraform will forget the following objects, but it will not
  delete them:
   - yandex_vpc_network.imported

  After applying this plan, Terraform will no longer manage these
  objects. You will need to import them into Terraform to manage
  them again.

Проверка: после apply сеть осталась в облаке, но исчезла из списка
terraform state list — и следующий terraform destroy её не тронул.
Это ровно то, чего мы добивались.

  Если указать destroy = true (или не указывать блок lifecycle вовсе),
  Terraform удалит ресурс из облака. Значение по умолчанию — удаление.

  Чем это лучше команды terraform state rm: изменение остаётся
  в системе контроля версий. Коллега, читающий ревью, видит, что
  ресурс вывели из-под управления осознанно, а не потеряли.

------------------------------------------------------------------
11. ДРЕЙФ: КОГДА РЕАЛЬНОСТЬ РАСХОДИТСЯ С ОПИСАНИЕМ
------------------------------------------------------------------

Дрейф (drift) — это расхождение между тем, что записано в состоянии,
и тем, что на самом деле в облаке. Причины: кто-то поправил ресурс
в консоли, сработала автоматика, ресурс изменился сам.

Посмотреть расхождения, НИЧЕГО не меняя:

  terraform plan -refresh-only

  Note: Objects have changed outside of Terraform

  Terraform detected the following changes made outside of Terraform
  since the last "terraform apply" which may have affected this plan:

    # yandex_compute_instance.app has changed
    ~ resource "yandex_compute_instance" "app" {
        ~ labels = {
            + "drift" = "manual"
          }
      }

  This is a refresh-only plan, so Terraform will not take any actions
  to undo these. If you were expecting these changes then you can
  apply this plan to record the updated values in the Terraform state
  without changing any remote objects.

Ключевая фраза — «without changing any remote objects»: план только
обновит состояние, облако не тронет. Применить такое обновление:

  terraform apply -refresh-only

А теперь второй вариант, который нужен чаще. Обычный plan тоже
показывает дрейф, но предлагает его ИСПРАВИТЬ — вернуть ресурс
к описанному виду:

  terraform plan

  # yandex_compute_instance.app will be updated in-place
  ~ resource "yandex_compute_instance" "app" {
      ~ labels = {
          - "drift" = "manual" -> null
        }
    }

Здесь метка, добавленная руками, будет удалена. Это правильное
поведение: инфраструктурой управляет Terraform, а не человек
с консолью. Но важно понимать разницу:

  вы хотите ПРИНЯТЬ ручное изменение → plan -refresh-only
  вы хотите ОТМЕНИТЬ ручное изменение → обычный apply

И то и другое — осознанное решение. Чего делать не надо: оставлять
расхождение незамеченным. Дрейф имеет свойство накапливаться,
а потом выясняется, что конфигурация описывает не то, что работает.

Как дрейф ловят в работе: регулярный план по расписанию (в конвейере,
практика 8) — если план не пустой, а изменений никто не вносил,
значит кто-то правит инфраструктуру руками.

------------------------------------------------------------------
12. ЗАЩИТА ОТ СЛУЧАЙНОГО УДАЛЕНИЯ
------------------------------------------------------------------

Удаление — самая разрушительная операция Terraform. На неё есть
две независимые защиты, и они не заменяют друг друга.

ЗАЩИТА В КОНФИГУРАЦИИ: lifecycle prevent_destroy

  resource "yandex_compute_instance" "app" {
    # ...
    lifecycle {
      prevent_destroy = true
    }
  }

  Попытка удалить такой ресурс (или заменить его, что тоже означает
  удаление) закончится ошибкой:

    Error: Instance cannot be destroyed
    Resource yandex_compute_instance.app has lifecycle.prevent_destroy
    set, but the plan calls for this resource to be destroyed.

  Полезно для баз данных, бакетов с данными, дисков. Минус: чтобы
  действительно удалить ресурс, придётся сначала убрать эту строку
  и применить изменение — то есть два лишних шага в момент, когда
  всё горит.

ЗАЩИТА НА СТОРОНЕ ОБЛАКА: deletion_protection

  resource "yandex_mdb_postgresql_cluster" "db" {
    # ...
    deletion_protection = true
  }

  Защита работает в самом облаке: удалить ресурс не сможет ни
  Terraform, ни человек через консоль, пока флаг не снят. Это
  надёжнее конфигурации, потому что не зависит от того, что написано
  в файлах.

  Практическое правило: deletion_protection = true — для всего, что
  хранит данные; prevent_destroy — для того, что дорого пересоздавать.

И третий уровень защиты, не технический: в конвейере apply запускают
только после того, как план прочитал человек. Об этом в практике 8.

------------------------------------------------------------------
13. КАК ЭТО ЖЕ ДЕЛАЕТСЯ В AWS И VK CLOUD
------------------------------------------------------------------

Хранение состояния — та область, где облака почти не различаются:
везде это бакет, совместимый с S3, и бэкенд backend "s3".

  Яндекс Облако
      адрес:   https://storage.yandexcloud.net
      регион:  ru-central1
      ключи:   статический ключ доступа сервисного аккаунта
      флаги:   skip_region_validation, skip_credentials_validation,
               skip_requesting_account_id, skip_s3_checksum
      замок:   use_lockfile

  AWS
      адрес:   подразумевается (S3), endpoint не указывают
      регион:  свой регион, например eu-west-1
      ключи:   IAM-пользователь или, лучше, роль
      флаги:   не нужны: S3 полностью совместим сам с собой
      замок:   use_lockfile (ранее dynamodb_table — тоже устарел)

  VK Cloud
      адрес:   S3-совместимый Object Storage, endpoint указывают
      регион:  свой регион
      ключи:   доступ пользователя проекта
      флаги:   skip_* нужны, как и в Яндекс Облаке
      замок:   use_lockfile, если поддерживаются условные записи

  Что важно понять: смена облака здесь означает смену адреса,
  региона и ключей. Сам блок backend и подход к блокировке остаются.
  Поэтому состояние принято хранить в бакете того облака, где живёт
  инфраструктура, — это ближе по сети и не смешивает права доступа.

14. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

  СИМПТОМ: Error acquiring the state lock
  ПРИЧИНА: работает другой процесс Terraform (или остался замок
  от прерванного запуска).
  ЧТО ДЕЛАТЬ: убедиться, что никто не применяет изменения; если
  процесс не работает — terraform force-unlock <ID из ошибки>.

  СИМПТОМ: 400 Bad Request или AuthorizationHeaderMalformed при
  обращении к бакету
  ПРИЧИНА: неверный ключ доступа. Самая частая ошибка — в переменную
  попал весь объект ключа из вывода yc вместо значения key_id.
  ЧТО ДЕЛАТЬ: проверить, что access_key начинается с YCAJE и не
  содержит фигурных скобок.

  СИМПТОМ: InvalidBucketName: The specified bucket is not valid
  ПРИЧИНА: в имени бакета недопустимые символы — русские буквы,
  заглавные, подчёркивания. Часто появляется, когда имя подставлялось
  скриптом и «поехало» из-за кодировки файла.
  ЧТО ДЕЛАТЬ: проверить имя: только строчные латинские буквы, цифры,
  точка и дефис.

  СИМПТОМ: Backend configuration changed / Initialization required
  ПРИЧИНА: изменились настройки блока backend (например, имя бакета
  или ключ состояния).
  ЧТО ДЕЛАТЬ: terraform init -reconfigure. Если меняли хранилище
  целиком и хотите перенести состояние — terraform init
  -migrate-state.

  СИМПТОМ: «Error: Variables not allowed» в блоке backend
  ПРИЧИНА: в backend использована переменная Terraform.
  ЧТО ДЕЛАТЬ: подставить значение текстом, а секреты передавать
  через -backend-config или переменные окружения.

  СИМПТОМ: план предлагает создать ресурс, который уже есть в облаке
  ПРИЧИНА: ресурс потерян из состояния (правка состояния руками,
  работа из другого каталога, потерянный локальный файл).
  ЧТО ДЕЛАТЬ: НЕ применять план. Сначала вернуть ресурс под
  управление импортом (раздел 8), затем проверить план.

  СИМПТОМ: terraform destroy удалил лишнее
  ПРИЧИНА: в состоянии оказалось больше, чем вы думали, — например,
  вы удалили описание из конфигурации и не использовали removed.
  ЧТО ДЕЛАТЬ: удалённое восстанавливается только из резервной копии
  состояния и повторным применением; именно поэтому включайте
  версионирование бакета и смотрите план перед применением.

  СИМПТОМ: бакет не удаляется — «bucket is not empty», хотя объектов
  в списке нет
  ПРИЧИНА: включено версионирование: у объектов остались предыдущие
  версии и маркеры удаления. Наш учебный бакет накопил их два
  десятка.
  ЧТО ДЕЛАТЬ: удалить все версии, а не только текущие объекты.
  Пока они есть, бакет не удалится — и деньги за хранение будут
  списываться.

------------------------------------------------------------------
15. ЗАДАНИЯ
------------------------------------------------------------------

  1. Базовое. Перенесите состояние практики 1 в бакет: создайте бакет
     с версионированием, настройте backend, выполните
     init -migrate-state. Убедитесь, что локальный файл состояния
     больше не нужен: удалите его и выполните terraform plan.

  2. Блокировка. Запустите apply и одновременно с ним план во втором
     терминале. Добейтесь ошибки про замок, прочитайте её целиком.
     Найдите объект-замок в бакете.

  3. Импорт. Создайте сеть командой yc (не через Terraform), затем
     возьмите её под управление через блок import с ключом
     -generate-config-out. Убедитесь, что план после импорта пуст,
     и удалите блок import из конфигурации.

  4. Переименование. Переименуйте любой ресурс в конфигурации
     (и во всех ссылках на него) с блоком moved. Проверьте, что
     идентификатор ресурса в облаке не изменился.

  5. Вывод из управления. Создайте сеть через Terraform, затем
     выведите её из управления блоком removed с destroy = false.
     Убедитесь, что сеть осталась в облаке и что terraform destroy
     её не удаляет. После проверки удалите сеть командой yc.

  6. Дрейф. Измените метку виртуальной машины в консоли. Посмотрите
     план в двух видах: обычный и -refresh-only. Объясните, чем
     отличаются предлагаемые действия.

  7. Хранилище в своём проекте. Опишите бакет для состояния отдельной
     конфигурацией (подход «bootstrap»): папка с двумя-тремя ресурсами,
     локальное состояние, отдельный ключ. Это позволит не создавать
     бакет руками в следующий раз.

16. ЧТО ДАЛЬШЕ
------------------------------------------------------------------

Состояние живёт в бакете, блокировка работает, ресурсы можно
импортировать и переименовывать без потерь. Дальше займёмся языком
Terraform: переменные с проверками, циклы, динамические блоки
и модули — то, что превращает конфигурацию из одного файла
в переиспользуемый набор.
