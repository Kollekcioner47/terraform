ПРАКТИКА 3. ЯЗЫК TERRAFORM: ПЕРЕМЕННЫЕ, ЦИКЛЫ И МОДУЛИ

Продолжительность: 2 академических часа.
Провайдер: yandex-cloud/yandex. Практика выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ПРАКТИКИ

  Вы научитесь описывать не один стенд, а класс стендов: значения
  вынести в переменные с проверками, однотипные ресурсы создавать
  циклами, правила — динамическими блоками, а повторяющуюся часть
  конфигурации — своим модулем. Плюс разберёте готовый модуль
  из библиотеки Яндекса и поймёте, чего от чужих модулей ожидать.

ЧТО НУЖНО ЗАРАНЕЕ

  * Работающий доступ в облако (практика 1).
  * Понимание состояния (практика 2) — модули и циклы меняют адреса
    ресурсов в состоянии, и без этого понимания легко случайно
    пересоздать инфраструктуру.

ЗАЧЕМ ЭТО НУЖНО

  До этой практики конфигурация описывала конкретный стенд: три
  подсети, две машины, порты 22 и 80. Как только понадобится второй
  стенд — для коллеги, для тестового окружения, для другой зоны, —
  придётся копировать файлы и править значения руками. Через месяц
  копий станет пять, и они разойдутся.

  Переменные, циклы и модули превращают конфигурацию в инструмент:
  один и тот же код создаёт разное окружение по разным значениям.

------------------------------------------------------------------
0. КАТАЛОГ ПРОЕКТА И ФАЙЛЫ
------------------------------------------------------------------

Правило, которое нарушают чаще всего: ОДИН ПРОЕКТ — ОДИН
КАТАЛОГ. Terraform работает с состоянием в пределах каталога,
поэтому файлы разных проектов в одной папке перемешают ресурсы
и состояние.

Создаём каталог практики:

  mkdir -p ~/terraform-course/work/03-language
  cd ~/terraform-course/work/03-language

Здесь ~/terraform-course — клон репозитория с материалами курса.
Каталог work/ внутрь репозитория не попадает: он перечислен
в .gitignore, чтобы ваши эксперименты не смешивались
с материалами курса.

СТРУКТУРА ПРОЕКТА

  03-language/
  ├── instances.tf
  ├── locals.tf
  ├── network.tf
  ├── outputs.tf
  ├── provider.tf
  ├── public_module/
  │   └── main.tf
  ├── terraform.tfvars.example
  ├── variables.tf
  └── versions.tf

  ../modules/vpc/          общий модуль сети (практика 3)
    ├── main.tf
    ├── outputs.tf
    ├── variables.tf
    └── versions.tf

  Плюс файлы, которые создаются при работе и в репозиторий
  не попадают: terraform.tfvars (значения переменных),
  terraform.tfstate (состояние), .terraform/ (провайдеры).
  Файл .terraform.lock.hcl, наоборот, нужно сохранить в git:
  он фиксирует версии провайдеров.

КАК СОЗДАЁМ ФАЙЛЫ

  Файлы можно набрать по тексту практики. Конструкция
  cat > имя-файла <<'EOF' записывает в файл всё, что введено до
  строки EOF, поэтому такой блок можно скопировать в терминал
  целиком. Строки cat и EOF стоят в первом столбце: отступ сломал
  бы завершение ввода.

  Готовые файлы практики лежат в материалах курса — их можно
  взять вместо набора по тексту:

  cp -r ~/terraform-course/files/03_language/. .
  mkdir -p ../modules
  cp -r ~/terraform-course/files/modules/vpc ../modules/

  Вторая команда нужна потому, что практики 3–6 и 8–9 используют
  общий модуль сети: в конфигурациях он подключается как
  source = "../modules/vpc", то есть лежит рядом
  с каталогом практики.


cat > versions.tf <<'EOF'
terraform {
  required_version = ">= 1.6.3"

  required_providers {
    yandex = {
      source  = "yandex-cloud/yandex"
      version = "~> 0.229.0"
    }
  }
}
EOF

cat > provider.tf <<'EOF'
provider "yandex" {
  cloud_id                 = var.cloud_id
  folder_id                = var.folder_id
  zone                     = var.zone
  service_account_key_file = var.sa_key_file
}
EOF

cat > network.tf <<'EOF'
# Вызов своего модуля сети.
#
# Модуль лежит в каталоге files/modules/vpc. Источник указывается
# относительным путём — так работают локальные модули.
#
# Правила работы с модулями:
#   * модуль не знает про облако и каталог — всё приходит переменными;
#   * версия модуля фиксируется: у локального модуля это делает система
#     контроля версий, у внешнего — параметр ref;
#   * всё, что нужно снаружи, модуль отдаёт через outputs.

module "vpc" {
  source = "../modules/vpc"

  network_name = "${var.project_name}-${var.environment}-net"

  # Словарь подсетей передаётся как есть: модуль сам применит for_each.
  subnets = var.subnets

  allowed_ports = var.allowed_ports
  labels        = local.common_labels
}
EOF

cat > terraform.tfvars.example <<'EOF'
# Пример значений переменных практики 3.

# по умолчанию, поэтому файл короткий.

cloud_id       = "b1gXXXXXXXXXXXXXXX"
folder_id      = "b1gYYYYYYYYYYYYYYY"

# Дополнительные метки добавляются к общим (locals.common_labels).

  owner = "ivan"
}

# Машины ролей. Ключ словаря попадает в имя ресурса и в его метку роли.
instances = {
  app = {
    subnet = "app"
  }
  queue = {
    subnet = "data"
    cores  = 2
    memory = 4
  }

# Число машин-исполнителей, создаваемых через count.

Код каждого файла проекта приведён в том разделе, где этот файл
разбирается.

МОДУЛЬ СЕТИ ЦЕЛИКОМ

Модуль сети используется начиная с этой практики во всех
остальных, поэтому создайте его сразу. Каталог модуля лежит
рядом с каталогом практики:

  mkdir -p ../modules/vpc

cat > ../modules/vpc/versions.tf <<'EOF'
# Модуль сети: версия Terraform и провайдеры.
#
# Модуль объявляет ограничения сам, а не надеется на корневую
# конфигурацию: так его можно подключать в любой проект.

terraform {
  required_version = ">= 1.6.3"

  required_providers {
    yandex = {
      source  = "yandex-cloud/yandex"
      version = "~> 0.229.0"
    }
  }
}
EOF

cat > ../modules/vpc/variables.tf <<'EOF'
# Входные переменные модуля.
#
# Правило хорошего модуля: он знает только то, что ему передали.
# Никаких идентификаторов каталога и облака внутри модуля — иначе
# модуль нельзя переиспользовать в другом проекте.

variable "network_name" {
  type        = string
  description = "Имя облачной сети"

  validation {
    condition     = can(regex("^[a-z][a-z0-9-]{1,61}$", var.network_name))
    error_message = "Имя сети: строчные латинские буквы, цифры и дефис."
  }
}

variable "subnets" {
  type = map(object({
    zone = string
    cidr = string
  }))
  description = "Подсети: ключ — имя подсети, значения — зона и диапазон адресов"

  validation {
    # Проверяем, что передали хотя бы одну подсеть: сеть без подсетей
    # бесполезна, а ошибку лучше получить сразу.
    condition     = length(var.subnets) > 0
    error_message = "Нужна хотя бы одна подсеть."
  }
}

variable "allowed_ports" {
  type        = list(number)
  description = "Порты, открытые для входящих подключений из интернета"
  default     = [22]

  validation {
    condition     = alltrue([for p in var.allowed_ports : p > 0 && p <= 65535])
    error_message = "Порт должен быть в диапазоне от 1 до 65535."
  }
}

variable "labels" {
  type        = map(string)
  description = "Метки, которые вешаются на все ресурсы модуля"
  default     = {}
}

# Выход в интернет для машин без публичных адресов.
#
# В Яндекс Облаке машина без публичного адреса не имеет выхода
# в интернет: маршрута по умолчанию у неё просто нет. Такую машину
# нельзя ни обновить, ни доустановить на неё пакет — а именно это
# делает cloud-init при первом запуске.
#
# Для этого в сети создают NAT-шлюз и таблицу маршрутизации, а подсети
# получают ссылку на эту таблицу. Шлюз платный, поэтому по умолчанию
# он выключен: включайте, когда в подсети есть машины без публичных
# адресов.
variable "create_nat_gateway" {
  type        = bool
  description = "Создавать ли NAT-шлюз и таблицу маршрутизации для выхода в интернет"
  default     = false
}
EOF

cat > ../modules/vpc/main.tf <<'EOF'
# Сеть, подсети и группа безопасности.
#
# Здесь собраны приёмы языка Terraform, которые чаще всего нужны
# на практике: for_each по словарю, динамический блок и условное
# создание ресурсов.

resource "yandex_vpc_network" "this" {
  name   = var.network_name
  labels = var.labels
}

# NAT-шлюз: выход в интернет для машин без публичных адресов.
#
# Выключен по умолчанию: шлюз платный, и в конфигурациях без приватных
# машин он не нужен. Включается переменной create_nat_gateway.
resource "yandex_vpc_gateway" "nat" {
  count = var.create_nat_gateway ? 1 : 0

  name = "${var.network_name}-nat"
  shared_egress_gateway {}
}

# Таблица маршрутизации: весь трафик «не в свою сеть» идёт через шлюз.
resource "yandex_vpc_route_table" "nat" {
  count = var.create_nat_gateway ? 1 : 0

  name       = "${var.network_name}-rt"
  network_id = yandex_vpc_network.this.id

  static_route {
    destination_prefix = "0.0.0.0/0"
    gateway_id         = yandex_vpc_gateway.nat[0].id
  }
}

# for_each по словарю подсетей.
#
# Почему for_each, а не count: ключом словаря служит ИМЯ подсети.
# Добавление подсети в середину словаря не сдвинет адреса остальных
# элементов состояния (в отличие от count, где всё зависит от позиции).
resource "yandex_vpc_subnet" "this" {
  for_each = var.subnets

  # Имя подсети включает имя сети, а имя сети — окружение.
  #
  # ПОЧЕМУ ТАК, А НЕ ПРОСТО each.key. Имя подсети должно быть
  # уникальным в пределах КАТАЛОГА. Когда в одном каталоге живут
  # два окружения (dev и prod), подсети с именем «app» из разных
  # сетей сталкиваются:
  #
  #   Error: Error while requesting API to create subnet:
  #   code = AlreadyExists desc = Subnet with name app already exists
  #
  # Мы получили эту ошибку, запуская итоговый стенд в двух
  # окружениях. Лечится это на уровне модуля — префиксом, а не
  # правкой каждого вызова.
  name = "${var.network_name}-${each.key}"
  zone = each.value.zone

  network_id     = yandex_vpc_network.this.id
  v4_cidr_blocks = [each.value.cidr]

  # Ссылка на таблицу маршрутизации появляется только вместе со шлюзом.
  route_table_id = var.create_nat_gateway ? yandex_vpc_route_table.nat[0].id : null

  labels = var.labels
}

# Динамический блок.
#
# Правила для каждого порта из списка однотипны, и писать их руками
# значит копировать один и тот же блок. dynamic "ingress" генерирует
# блоки по коллекции.
#
# Обратите внимание на имя переменной в content: это имя самого
# динамического блока (ingress), а не какое-то зарезервированное слово.
resource "yandex_vpc_security_group" "this" {
  name        = "${var.network_name}-sg"
  description = "Группа безопасности, созданная модулем vpc"
  network_id  = yandex_vpc_network.this.id

  labels = var.labels

  dynamic "ingress" {
    for_each = var.allowed_ports

    content {
      description    = "Порт ${ingress.value} из интернета"
      protocol       = "TCP"
      port           = ingress.value
      v4_cidr_blocks = ["0.0.0.0/0"]
    }
  }

  # Исходящий трафик разрешён полностью.
  #
  # Это не «на всякий случай», а необходимость: установка пакетов идёт
  # на порты 80 и 443 к зеркалам репозиториев, разрешение имён — на 53-й,
  # обращения к API — тоже наружу. Ограничив исходящий трафик, вы
  # получите машину, которая грузится, но не может доустановить ни одного
  # пакета, а cloud-init завершится ошибкой вида:
  #
  #   Cannot initiate the connection to mirror.yandex.ru:80
  #   connection timed out
  #
  # В рабочей среде исходящий трафик принято сужать явно: разрешить
  # конкретные адреса обновлений, DNS и API облака, остальное закрыть.
  egress {
    description    = "Исходящий трафик"
    protocol       = "ANY"
    from_port      = 0
    to_port        = 65535
    v4_cidr_blocks = ["0.0.0.0/0"]
  }
}
EOF

cat > ../modules/vpc/outputs.tf <<'EOF'
# Выходные значения модуля.
#
# Модуль обязан отдать наружу всё, что может понадобиться снаружи:
# идентификаторы созданных ресурсов. Если этого не сделать, вызывающей
# конфигурации придётся угадывать идентификаторы или обращаться
# к источникам данных.

output "network_id" {
  description = "Идентификатор созданной сети"
  value       = yandex_vpc_network.this.id
}

output "subnet_ids" {
  description = "Идентификаторы подсетей: ключ — имя подсети"
  value       = { for name, subnet in yandex_vpc_subnet.this : name => subnet.id }
}

output "subnet_zones" {
  description = "Зоны подсетей: ключ — имя подсети"
  value       = { for name, subnet in yandex_vpc_subnet.this : name => subnet.zone }
}

output "security_group_id" {
  description = "Идентификатор группы безопасности"
  value       = yandex_vpc_security_group.this.id
}

output "subnet_count" {
  description = "Сколько подсетей создано"
  value       = length(yandex_vpc_subnet.this)
}

output "nat_gateway_id" {
  description = "Идентификатор NAT-шлюза (null, если шлюз не создавался)"
  value       = var.create_nat_gateway ? yandex_vpc_gateway.nat[0].id : null
}

output "route_table_id" {
  description = "Идентификатор таблицы маршрутизации (null, если не создавалась)"
  value       = var.create_nat_gateway ? yandex_vpc_route_table.nat[0].id : null
}
EOF

------------------------------------------------------------------
1. ПЕРЕМЕННЫЕ: ЧТО ВЫНОСИТЬ И КАК ОПИСЫВАТЬ
------------------------------------------------------------------

Правило простое: если значение может отличаться от запуска к запуску —
это переменная. Если значение вычисляется из других — это locals.
Если значение всегда одинаковое — его место прямо в ресурсе.

Переменная — это точка настройки конфигурации: имя, тип, описание
и правила проверки. Один и тот же код с разными значениями создаёт
разные стенды, и править для этого сами файлы не нужно. Обратная
сторона: у переменной появляется интерфейс — её кто-то задаёт
снаружи, и этот интерфейс нельзя менять молча.

Описание переменной с типом, значением по умолчанию и проверкой:

  variable "environment" {
    type        = string
    description = "Окружение: dev, stage или prod"
    default     = "dev"

    validation {
      condition     = contains(["dev", "stage", "prod"], var.environment)
      error_message = "Окружение должно быть одним из: dev, stage, prod."
    }
  }

Проверка работает до обращения к облаку. Попробуем подсунуть
недопустимое значение:

  terraform plan -var='environment=testing'

  Planning failed. Terraform encountered an error while generating
  this plan.

  Error: Invalid value for variable
  Окружение должно быть одним из: dev, stage, prod.

Именно этого и добиваются проверкой: ошибка видна сразу, понятна
и не стоит ни одной секунды облачного времени. Хорошая проверка
экономит куда больше времени, чем стоит её написание.

Без проверки то же самое значение ушло бы в облако, и ошибка
вернулась бы от API — другим текстом, после плана, а иногда уже
после частичного применения. Поэтому проверку пишут не «на всякий
случай», а там, где ошибка дороже всего: имена, диапазоны, списки
допустимых значений.

В validation ровно два поля. condition — выражение, которое даёт
true или false; error_message — текст, который увидит человек.
Отсюда следствие, о котором узнают на первой же сложной проверке:
condition может ссылаться только на саму проверяемую переменную
и на константы. Сравнить две переменные между собой в validation
нельзя — для этого есть locals и precondition в ресурсах (раздел 11).

ТИПЫ ПЕРЕМЕННЫХ

  Тип решает две задачи: не даёт положить в переменную бессмыслицу
  и говорит читателю, что за значение здесь ожидается. Тип — это
  не украшение: при несовпадении Terraform пытается привести значение
  к объявленному типу, и приведение иногда проходит незаметно.

  string, number, bool — простые значения. Приведение здесь работает
  в обе стороны: "1" станет числом 1 там, где объявлен number,
  а число 1 станет строкой "1". Если привести не получается, план
  падает до обращения к облаку:

    Error: Invalid value for variable

    The given value is not suitable for var.worker_count declared
    at variables.tf line 107, in variable "worker_count":
    a number is required.

  Отдельно про строку: string примет "два" так же охотно, как "dev".
  Тип такую ошибку не поймает — её ловит validation по списку
  допустимых значений.

  list(number), list(string), set(string) — списки и множества.
    Разница: в списке порядок важен и допускаются повторы, во множестве
    порядок не определён и повторов нет. Порядок — не мелочь: на нём
    держится count (раздел 4), а множество специально сделано без
    порядка, чтобы положиться на него было нельзя.

  map(string), map(number) — словари, где все значения одного типа.
    Ключи у словаря всегда строки, и именно на них опирается for_each.

  object({...}) — структура с фиксированными полями и типами:

    variable "instances" {
      type = map(object({
        subnet = string
        cores  = optional(number, 2)
        memory = optional(number, 2)
      }))
      description = "Виртуальные машины: ключ — роль машины"
    }

  Функция optional() задаёт значение поля по умолчанию. Без неё
  пришлось бы указывать cores и memory у каждой машины, хотя обычно
  они одинаковые. optional() появилась в Terraform 1.3 — на старых
  версиях такое описание не сработает.

  Обратите внимание на двойственность слова «по умолчанию»: optional()
  задаёт умолчание ПОЛЯ внутри объекта, а default в самой переменной —
  умолчание ЗНАЧЕНИЯ переменной целиком. Это разные уровни, и они
  спокойно уживаются в одном описании.

ЧТО ЗАДАВАТЬ В DEFAULT, А ЧТО НЕТ

  default стоит задавать там, где есть разумное общее значение: зона
  по умолчанию, список портов, префикс имён. Тогда terraform.tfvars
  остаётся коротким, а конфигурация запускается сразу после init.

  Без default оставляют то, что человек обязан выбрать осознанно.
  В нашем variables.tf это cloud_id, folder_id, sa_key_file
  и ssh_public_key: умолчания у них нет и быть не может. Если такую
  переменную не задать, Terraform не пойдёт в облако, а остановится
  с сообщением:

    Error: No value for required variable

    The root module input variable "folder_id" is not set, and has
    no default value.

  Правило простое: default — это ответ на вопрос «что будет, если
  про переменную забыли». Если забыть про неё нельзя, умолчания
  быть не должно.

ПРИОРИТЕТ ИСТОЧНИКОВ ЗНАЧЕНИЙ

  Одно и то же значение можно задать несколькими способами. Terraform
  собирает их по очереди, и каждый следующий источник перекрывает
  предыдущий:

    1. default в описании переменной;
    2. файл terraform.tfvars;
    3. файл, переданный ключом -var-file;
    4. переменная окружения TF_VAR_имя;
    5. ключ -var в командной строке.

  Запомнить порядок помогает смысл: сначала то, что записано в коде,
  потом то, что лежит рядом с кодом, потом то, что задано в текущем
  сеансе работы. Чем ближе значение к запуску, тем оно важнее.

  Имена у переменных окружения свои: переменная environment задаётся
  как TF_VAR_environment, то есть с префиксом TF_VAR_ и в том же
  регистре.

    export TF_VAR_environment=stage
    terraform plan -var='worker_count=2'

  Здесь worker_count придёт из ключа -var, а не из окружения: ключи
  и файлы командной строки разбираются позже переменных окружения.
  Есть и ещё один источник, о котором забывают: любой файл
  *.auto.tfvars в каталоге подхватывается автоматически, без
  -var-file. Поэтому такое значение появляется «из ниоткуда».

  Ключ -var хорош для разовой проверки и плох для секретов: значение
  остаётся в истории команд и видно в списке процессов. Как хранить
  секреты — разговор практики 6.

  Проверить, что получилось на самом деле, можно так:

    terraform console
    > var.environment

  Файл terraform.tfvars в репозиторий не попадает: в нём идентификаторы
  вашего каталога, пути и иногда секреты. Рядом держат
  terraform.tfvars.example — файл без секретов, по которому коллега
  поймёт, что нужно заполнить.

ЧУВСТВИТЕЛЬНЫЕ ЗНАЧЕНИЯ

  Переменную можно пометить как чувствительную:

    variable "db_password" {
      type      = string
      sensitive = true
    }

  Что это даёт: значение не печатается в плане и в выводах команд.

    db_password = <sensitive>

  ЧЕГО ЭТО НЕ ДАЁТ: значение всё равно попадает в файл состояния
  и в состояние на сервере. Флаг sensitive защищает от случайного
  вывода на экран и в журнал конвейера, но не превращает переменную
  в секрет. Настоящие секреты хранят в хранилище секретов — этим
  займёмся в практике 6.

  Ещё одно свойство: чувствительность передаётся дальше по цепочке.
  Атрибут ресурса, собранный из sensitive-переменной (пароль
  в metadata, ключ в labels), помечается чувствительным сам, и в плане
  он тоже показывается как <sensitive>. У выводов флаг sensitive
  приходится ставить отдельно: модуль не вправе отдать наружу
  значение, которое считает чувствительным, без такой пометки —
  Terraform остановит план с ошибкой.

ИМЯ ПЕРЕМЕННОЙ — ЭТО КОНТРАКТ

  Переменная — часть интерфейса конфигурации: её задают в файле
  terraform.tfvars, в конвейере, в командной строке. Пока смысл
  и имя совпадают, всё в порядке. Но если смысл поменялся (было
  «зона подсети», стало «зона машины»), а имя осталось, беда
  приходит молча: старое значение окажется в новом месте, план
  пройдёт, а инфраструктура получится не та.

  Поэтому смена смысла — это смена имени: либо новая переменная
  с новым именем, а старая удаляется, либо то же имя, но изменённое
  значение по умолчанию и явная пометка в description. Terraform
  на такое не жалуется: для него имя переменной — просто строка.

  Переменные этого проекта — в файле variables.tf. Смотрите,
  какие переменные объявлены без значения по умолчанию (их
  обязательно задать в terraform.tfvars), а какие имеют default.

cat > variables.tf <<'EOF'
# Переменные: типы, значения по умолчанию, проверки, чувствительность.
#
# В этой практике важен не набор переменных, а приёмы:
#   * сложные типы (map(object({...})));
#   * проверки, которые ловят ошибку до обращения к облаку;
#   * чувствительные значения, которые не печатаются в выводе.

variable "cloud_id" {
  type        = string
  description = "Идентификатор облака"
}

variable "folder_id" {
  type        = string
  description = "Идентификатор каталога"
}

variable "zone" {
  type        = string
  description = "Зона доступности по умолчанию"
  default     = "ru-central1-d"
}

variable "sa_key_file" {
  type        = string
  description = "Путь к авторизованному ключу сервисного аккаунта"
}

variable "ssh_public_key" {
  type        = string
  description = "Путь к публичному SSH-ключу"
}

variable "project_name" {
  type        = string
  description = "Префикс в именах ресурсов"
  default     = "tf-lang"
}

# Проверка значения по списку допустимых.
variable "environment" {
  type        = string
  description = "Окружение: dev, stage или prod"
  default     = "dev"

  validation {
    condition     = contains(["dev", "stage", "prod"], var.environment)
    error_message = "Окружение должно быть одним из: dev, stage, prod."
  }
}

# Сложный тип: словарь объектов. Так описывают однотипные сущности,
# которых заранее неизвестное количество.
variable "subnets" {
  type = map(object({
    zone = string
    cidr = string
  }))
  description = "Подсети: ключ — имя, значения — зона и диапазон адресов"

  default = {
    app = {
      zone = "ru-central1-a"
      cidr = "10.30.10.0/24"
    }
    data = {
      zone = "ru-central1-b"
      cidr = "10.30.20.0/24"
    }
    edge = {
      zone = "ru-central1-d"
      cidr = "10.30.30.0/24"
    }
  }
}

variable "allowed_ports" {
  type        = list(number)
  description = "Порты, открытые на вход из интернета"
  default     = [22, 80, 443]
}

# Словарь машин. Ключ словаря становится частью имени ресурса,
# поэтому он должен быть осмысленным: app, queue, cache.
variable "instances" {
  type = map(object({
    subnet = string
    cores  = optional(number, 2)
    memory = optional(number, 2)
  }))
  description = "Виртуальные машины: ключ — роль машины"

  default = {
    app = {
      subnet = "app"
    }
    queue = {
      subnet = "data"
      cores  = 2
      memory = 4
    }
  }
}

# Число машин, создаваемых через count. Про разницу между count
# и for_each — в тексте практики.
variable "worker_count" {
  type        = number
  description = "Сколько машин-исполнителей создать"
  default     = 1

  validation {
    condition     = var.worker_count >= 0 && var.worker_count <= 3
    error_message = "Допустимое число машин-исполнителей: от 0 до 3."
  }
}

variable "enable_debug_vm" {
  type        = bool
  description = "Создавать ли отладочную машину (условное создание ресурса)"
  default     = false
}

  type        = map(string)
  description = "Дополнительные метки, которые добавляются к общим"
  default     = {}

# Чувствительное значение: пароль базы данных. Флаг sensitive

# команд и в плане.
variable "db_password" {
  type        = string
  description = "Пароль базы данных (учебный пример чувствительного значения)"
  default     = "ChangeMe_12345"

------------------------------------------------------------------
2. LOCALS: ВЫЧИСЛЕНИЯ ВНУТРИ КОНФИГУРАЦИИ
------------------------------------------------------------------

locals — это именованные выражения. Их не задают снаружи: значения
вычисляются из переменных, ресурсов и других locals. Разница
с переменной короткая: variable описывает то, что приходит от
человека, locals — то, что конфигурация считает сама. Отсюда
и правило: если значение можно вычислить из других, оно не должно
быть переменной — иначе человек сможет задать его неверно, и никто
этого не поймает.

  Наружу locals не видны. Ни соседний каталог, ни подключённый модуль
  не могут обратиться к вашему local напрямую: граница модуля — это
  только входы (переменные) и выходы (outputs). Поэтому вычисления
  держат в locals, а на границе модуля переводят в outputs.

Ниже — файл locals.tf целиком. Он небольшой, и в нём собраны все
вычисления этой конфигурации: именно их дальше используют ресурсы
и выводы.

cat > locals.tf <<'EOF'
# Локальные значения: вычисления, которые не являются входными данными.
#
# Разница между variable и locals:
#   variable — то, что приходит снаружи (значения задаёт человек);
#   locals   — то, что вычисляется внутри (промежуточные результаты).
#
# Если значение можно вычислить из других — это locals, а не переменная.

locals {
  # merge объединяет словари. Позже указанный словарь перекрывает
  # более ранний — это удобный способ дать пользователю переопределить
  # часть общих меток.
  common_labels = merge(
    {
      course      = "terraform"
      lesson      = "3"
      environment = var.environment
    },
    var.extra_labels
  )

  # Условное выражение. Типовая задача: в рабочем окружении берём
  # проверенный образ, в учебном — свежий.
  image_family = var.environment == "prod" ? "ubuntu-2404-lts" : "ubuntu-2604-lts"

  # Цикл for по словарю: собираем новый словарь имён ресурсов.
  # format подставляет значения в шаблон.
  instance_names = {
    for role, cfg in var.instances :
    role => format("%s-%s-%s", var.project_name, var.environment, role)
  }

  # Обратный словарь: зона -> имя подсети. Нужен, чтобы находить
  # подсеть по зоне, а не по имени.
  subnet_by_zone = {
    for name, subnet in var.subnets : subnet.zone => name
  }

  # Функции работы с адресами: cidrsubnet разбивает большой диапазон
  # на подсети. Второй аргумент — сколько бит добавить к маске,
  # третий — номер подсети.
  #
  # Например, cidrsubnet("10.40.0.0/16", 8, 1) даст 10.40.1.0/24.
  monitoring_cidr = cidrsubnet("10.40.0.0/16", 8, 1)

  # try возвращает первое значение, которое удалось вычислить,
  # не вызывая ошибки. Часто нужен при работе с необязательными
  # элементами структур.
  first_subnet_name = try(keys(var.subnets)[0], "нет-подсетей")

  # Подсеть в зоне по умолчанию. Нужна машинам, которые не привязаны
  # к конкретной подсети: в Яндекс Облаке зона машины обязана совпадать
  # с зоной подсети, иначе облако откажет в создании.
  subnet_in_default_zone = lookup(local.subnet_by_zone, var.zone,
  local.first_subnet_name)

  # Функция length считает элементы коллекции, upper переводит
  # строку в верхний регистр.
  summary = format(
    "Окружение %s: подсетей %d, машин %d, исполнителей %d",
    upper(var.environment),
    length(var.subnets),
    length(var.instances),
    var.worker_count,
  )
}
EOF

Разберём его по частям.

  ОБЪЕДИНИТЬ СЛОВАРИ (с возможностью переопределить часть):

    locals {
      common_labels = merge(
        {
          course      = "terraform"
          lesson      = "3"
          environment = var.environment
        },
        var.extra_labels
      )
    }

    Значения из var.extra_labels перекрывают одноимённые ключи. Так
    удобно давать пользователю добавить свои метки, не меняя общих.

    Почему это locals, а не переменная: набор общих меток должен быть
    одинаковым для всех ресурсов, и вычислять его — задача самой
    конфигурации. Пользователь же получает ровно одну точку
    расширения, var.extra_labels, и не может случайно убрать метку
    course. Порядок аргументов merge и есть правило приоритета:
    побеждает тот словарь, который указан последним.

  ВЫБРАТЬ ЗНАЧЕНИЕ УСЛОВИЕМ:

    image_family = var.environment == "prod" ? "ubuntu-2404-lts" : "ubuntu-2604-lts"

    Читается так: если окружение prod — взять проверенный образ,
    иначе свежий.

    Такое выражение лучше держать в locals, если выбор встречается
    в конфигурации больше одного раза: одно место правки вместо пяти.
    И заметьте: здесь сравнивается значение переменной, поэтому
    выражение пересчитывается при каждом плане. Смена environment
    меняет и образ, и имена, и метки — но не сами файлы.

  ПОСТРОИТЬ СЛОВАРЬ ЦИКЛОМ:

    instance_names = {
      for role, cfg in var.instances :
      role => format("%s-%s-%s", var.project_name, var.environment, role)
    }

    Цикл for превращает один словарь в другой, не создавая ресурсов.
    Обратите внимание: cfg в теле цикла не используется, но его
    обязательно указывать — так устроен синтаксис for по словарю.
    Если поле нужно, его берут как cfg.subnet. Такой словарь — ещё
    и способ держать имена в одном месте: и ресурс, и вывод берут
    имя из local.instance_names[role] и разойтись уже не могут.

  ПОЛУЧИТЬ ОБРАТНЫЙ СЛОВАРЬ (зона -> имя подсети):

    subnet_by_zone = {
      for name, subnet in var.subnets : subnet.zone => name
    }

    Зачем обратный словарь: машине нужна подсеть по зоне, а входные
    данные описывают подсети по имени. Один раз перевернув словарь,
    конфигурация дальше ищет подсеть одной строкой —
    local.subnet_by_zone[var.zone]. Это и короче, и надёжнее, чем
    перебирать подсети в каждом ресурсе: правило поиска описано
    в одном месте.

  ВЫЧИСЛИТЬ ДИАПАЗОН АДРЕСОВ:

    monitoring_cidr = cidrsubnet("10.40.0.0/16", 8, 1)

    Функция cidrsubnet(диапазон, сколько бит добавить, номер подсети)
    разбивает большой диапазон на подсети. В нашем случае получится
    10.40.1.0/24, и это видно в выводе:

      monitoring_cidr = "10.40.1.0/24"

    Это вычисление держат в locals, а не в ресурсе, потому что
    диапазон нужен сразу нескольким местам: подсети, правилам
    и выводу. Считать его в трёх местах — верный способ однажды
    получить три разных ответа. Второй аргумент (8) означает, что
    к маске /16 добавляется восемь бит: 16 + 8 = 24.

  ЗАСТРАХОВАТЬСЯ ОТ ОТСУТСТВУЮЩИХ ЗНАЧЕНИЙ:

    first_subnet_name = try(keys(var.subnets)[0], "нет-подсетей")

    Функция try возвращает первое выражение, которое удалось вычислить
    без ошибки. Если словарь пуст, keys() вернёт пустой список,
    обращение к [0] вызовет ошибку — и тогда вернётся строка
    «нет-подсетей».

    try() уместен на границе с данными, которых может не быть: пустой
    словарь, необязательное поле. Но у него есть цена — он скрывает
    и настоящие опечатки в выражении, подменяя их запасным значением.
    Если известно, чего именно может не хватать, лучше подходит
    проверка условия или one() (раздел 10).

  ВАЖНО ПРО ПОРЯДОК КЛЮЧЕЙ. В словаре Terraform порядок не хранится,
  но функция keys() возвращает ключи отсортированными. То есть
  keys({app = 1, data = 2, edge = 3}) даст ["app", "data", "edge"].
  На это можно опираться, но лучше не строить логику на «первом
  ключе»: однажды словарь пополнится, и первым окажется другой ключ.
  В этой практике мы на этом споткнёмся — см. разбор поломок.

  ЕЩЁ ДВЕ ДЕТАЛИ ПРО LOCALS. Внутри одного блока locals можно
  ссылаться на другие locals: в locals.tf так устроен
  subnet_in_default_zone — он использует и subnet_by_zone, и
  first_subnet_name. Порядок строк при этом не важен: Terraform
  строит граф зависимостей и вычисляет значения в нужном порядке.

  Второе — ограничение, о котором лучше знать заранее: значения
  в count и for_each должны быть известны ДО применения. Если local
  собран из атрибута ещё не созданного ресурса, Terraform остановит
  план и скажет, что ключи for_each нельзя определить до apply.

------------------------------------------------------------------
3. ФУНКЦИИ И TERRAFORM CONSOLE
------------------------------------------------------------------

Функций в Terraform больше сотни, и запоминать их не нужно: есть
интерактивная консоль, где выражение можно проверить, ничего не
создавая и не трогая состояние.

  terraform console

Дальше вводите выражения и видите результат (ниже — настоящие выводы):

  > cidrsubnet("10.40.0.0/16", 8, 1)
  "10.40.1.0/24"

  > format("%s-%02d", "worker", 3)
  "worker-03"

  > upper("dev")
  "DEV"

  > merge({a=1}, {b=2}, {a=3})
  {
    "a" = 3
    "b" = 2
  }

  > lookup({app="10.30.10.0/24"}, "app", "нет")
  "10.30.10.0/24"

  > try([][0], "значения нет")
  "значения нет"

  > [for z in ["a","b","d"] : "ru-central1-${z}"]
  [
    "ru-central1-a",
    "ru-central1-b",
    "ru-central1-d",
  ]

  > { for k, v in {app="a", data="b"} : v => k }
  {
    "a" = "app"
    "b" = "data"
  }

  > contains([22, 80], 443)
  false

Консоль умеет работать и со значениями вашей конфигурации: в ней
доступны переменные, locals и ресурсы. Это лучший способ проверить
сложное выражение, не запуская план:

  > local.instance_names
  {
    "app" = "tf-lang-dev-app"
    "queue" = "tf-lang-dev-queue"
  }

  > length(local.common_labels)
  4

Порядок отладки выражения обычно такой: сначала соберите его
в консоли по частям (keys(var.subnets), затем [0], затем try вокруг
всего), а готовое выражение переносите в locals. Так вы видите
значение, а не сообщение об ошибке в середине плана.

У консоли есть и практическая мелочь: она читает terraform.tfvars
и спрашивает значения тех переменных, у которых нет умолчания.
Чтобы не отвечать каждый раз, переменные передают ключами:

  terraform console -var='environment=stage'

Если в ответ на выражение консоль пишет «Reference to undeclared
local value», значит выражение ссылается на то, чего в каталоге нет:
обычно это опечатка в имени local или ресурса.

Выход — Ctrl+D или команда exit.

ФУНКЦИИ, КОТОРЫЕ ОПАСНЫ В КОНФИГУРАЦИИ

Не все функции одинаково безобидны. Часть из них зависит не от
данных, а от момента запуска:

  * timestamp() возвращает текущее время;
  * uuid() — новый случайный идентификатор;
  * bcrypt() — новую соль при каждом вызове.

Про такую функцию легко сказать «удобно» и записать её в метку или
в имя ресурса. План после этого перестаёт быть пустым: при каждом
запуске выражение даёт новое значение, Terraform видит изменение
и предлагает что-то поменять — снова и снова. Для метки это шум
в плане, для имени — постоянное пересоздание ресурса, а если от него
зависят другие, они уедут следом.

То, что план не пуст, само по себе не ошибка: он и должен показывать
расхождения. Ошибка — когда расхождение создаёт функция, а не
изменение инфраструктуры: за шумом перестают видеть настоящие
изменения.

Правильные способы получить «случайное» значение:

  * если значение должно появиться один раз, а потом жить
    в состоянии, — это ресурс random_id или random_password
    из провайдера random: он вычисляется при создании и дальше
    не меняется;
  * если нужно время создания — берите его из атрибута ресурса
    (created_at), а не из timestamp();
  * если timestamp() всё же нужен, закрывайте поле от изменений:

      lifecycle {
        ignore_changes = [labels["created"]]
      }

Функция plantimestamp() (Terraform 1.8+) возвращает одно и то же
время в пределах одного запуска, поэтому шума от неё меньше. Но между
запусками значение всё равно меняется, так что проблему она
не снимает, а только смягчает.

------------------------------------------------------------------
4. ЦИКЛЫ: COUNT И FOR_EACH
------------------------------------------------------------------

Создать несколько однотипных ресурсов можно двумя способами, и выбор
между ними — не вкусовщина, а влияние на то, что произойдёт при
изменениях.

В проекте оба способа живут рядом, в одном файле instances.tf: машины
ролей создаются циклом for_each по словарю var.instances,
машины-исполнители — циклом count по числу var.worker_count,
а отладочная машина — условным count = 0 или 1.

cat > instances.tf <<'EOF'
# Виртуальные машины: два способа создать несколько однотипных ресурсов.

data "yandex_compute_image" "os" {
  family = local.image_family
}

# СПОСОБ 1: for_each по словарю.
#
# Ключ словаря становится ключом элемента: each.key, а значения —
# each.value. В состояние ресурс попадает по адресу
# yandex_compute_instance.app["app"] — с ключом, а не с индексом.
#
# Это значит, что если из словаря убрать одну запись или добавить
# новую, остальные машины не будут пересозданы.
resource "yandex_compute_instance" "app" {
  for_each = var.instances

  name        = local.instance_names[each.key]
  description = "Машина роли ${each.key}, созданная циклом for_each"
  zone        = var.subnets[each.value.subnet].zone

  platform_id               = "standard-v3"
  allow_stopping_for_update = true

  resources {
    cores         = each.value.cores
    memory        = each.value.memory
    core_fraction = 20
  }

  scheduling_policy {
    preemptible = true
  }

  boot_disk {
    initialize_params {
      image_id = data.yandex_compute_image.os.id
      type     = "network-hdd"
      size     = 10
    }
  }

  network_interface {
    subnet_id = module.vpc.subnet_ids[each.value.subnet]

    # Внешний адрес нужен только машинам окружения dev:
    # условное выражение внутри ресурса.
    nat = var.environment != "prod"
  }

  metadata = {
    ssh-keys = "ubuntu:${file(var.ssh_public_key)}"
  }

  labels = merge(local.common_labels, { role = each.key })
}

# СПОСОБ 2: count по числу.
#
# count создаёт ресурсы с индексами: yandex_compute_instance.worker[0],
# [1], [2]. Внутри ресурса номер доступен как count.index.
#
# Когда что применять:
#   count    — ресурсы полностью взаимозаменяемы (три одинаковых
#              исполнителя очереди);
#   for_each — у ресурсов есть осмысленный ключ (роли, зоны, имена).
#
# Опасность count: если удалить элемент из середины списка, все
# последующие сдвинут индексы, и Terraform пересоздаст их.
resource "yandex_compute_instance" "worker" {
  count = var.worker_count

  name        = "${var.project_name}-${var.environment}-worker-${count.index + 1}"
  description = "Машина-исполнитель номер ${count.index + 1}, созданная циклом count"

  # Зона берётся из подсети, а не из переменной zone: иначе при
  # несовпадении зон облако откажет в создании машины.
  zone = var.subnets[local.subnet_in_default_zone].zone

  platform_id               = "standard-v3"
  allow_stopping_for_update = true

  resources {
    cores         = 2
    memory        = 2
    core_fraction = 20
  }

  scheduling_policy {
    preemptible = true
  }

  boot_disk {
    initialize_params {
      image_id = data.yandex_compute_image.os.id
      type     = "network-hdd"
      size     = 10
    }
  }

  network_interface {
    # Обращаемся к подсети по имени: если такой подсети нет,
    # Terraform сообщит об этом на этапе плана.
    subnet_id = module.vpc.subnet_ids[local.subnet_in_default_zone]
    nat       = var.environment != "prod"
  }

  metadata = {
    ssh-keys = "ubuntu:${file(var.ssh_public_key)}"
  }

  labels = merge(local.common_labels, { role = "worker" })
}

# Условное создание ресурса.
#
# Если enable_debug_vm = false, count равен нулю и ресурса нет вовсе.
# Так удобно включать отладочные машины на время разбора инцидента.
resource "yandex_compute_instance" "debug" {
  count = var.enable_debug_vm ? 1 : 0

  name        = "${var.project_name}-${var.environment}-debug"
  description = "Отладочная машина, создаётся по требованию"
  zone        = var.subnets[local.subnet_in_default_zone].zone

  platform_id = "standard-v3"

  resources {
    cores         = 2
    memory        = 2
    core_fraction = 20
  }

  scheduling_policy {
    preemptible = true
  }

  boot_disk {
    initialize_params {
      image_id = data.yandex_compute_image.os.id
      type     = "network-hdd"
      size     = 10
    }
  }

  network_interface {
    subnet_id = module.vpc.subnet_ids[local.subnet_in_default_zone]
    nat       = true
  }

  metadata = {
    ssh-keys = "ubuntu:${file(var.ssh_public_key)}"
  }

  labels = merge(local.common_labels, { role = "debug" })
}
EOF

Обратите внимание на две детали в этом файле: зона машины берётся
из подсети (var.subnets[...].zone), а не из отдельной переменной,
и имя ресурса собирается из local.instance_names — то есть из
вычислений раздела 2. Дальше разберём оба способа по очереди
и посмотрим, что происходит в плане, когда конфигурация меняется.

СПОСОБ 1: COUNT

  resource "yandex_compute_instance" "worker" {
    count = var.worker_count
    name  = "${var.project_name}-worker-${count.index + 1}"
    # ...
  }

  Номера машин станут индексами: yandex_compute_instance.worker[0],
  worker[1]. Внутри ресурса номер доступен как count.index.

  Увеличим число исполнителей с одного до двух:

    # yandex_compute_instance.worker[1] will be created

    Plan: 1 to add, 0 to change, 0 to destroy.

  Первая машина не тронута — добавилась только вторая. Пока всё
  хорошо, потому что добавление в конец индексов не сдвигает.

  Проблема начинается, когда элемент убирают из середины списка.
  Пусть исполнителей было три и второй (worker[1]) решили удалить.
  Сами позиции в конфигурации не меняются, но меняется их смысл:
  на место [1] встаёт машина, которая раньше была [2]. Terraform
  сравнивает состояние с конфигурацией по адресам и видит, что
  адрес [1] изменился, а адрес [2] исчез:

    # yandex_compute_instance.worker[1] must be replaced
    # yandex_compute_instance.worker[2] will be destroyed

  Машину пересоздают, хотя её никто не трогал. В учебном стенде это
  ещё полбеды, а в рабочем — потеря данных на диске и минуты простоя.
  Причина именно в позиционных адресах: у count нет другого способа
  отличить один ресурс от другого.

  ЕЩЁ ОДИН ПРИЁМ: условное создание ресурса. count = 0 означает
  «не создавать»:

    resource "yandex_compute_instance" "debug" {
      count = var.enable_debug_vm ? 1 : 0
      # ...
    }

  Так включают отладочные машины на время разбора инцидента, не
  трогая основной код. Ресурс с count = 0 существует в конфигурации,
  но не в состоянии; когда переменная станет true, машина появится,
  а при false — удалится. В нашем instances.tf так сделан ресурс
  debug, а тот же приём в модуле сети включает NAT-шлюз
  (create_nat_gateway).

  Условное создание через count — единственный случай, когда count
  уместен для одиночного ресурса: позиций здесь ноль или одна,
  и сдвигаться нечему.

СПОСОБ 2: FOR_EACH

  resource "yandex_compute_instance" "app" {
    for_each = var.instances

    name = local.instance_names[each.key]
    # ...
    labels = merge(local.common_labels, { role = each.key })
  }

  Ресурсы получают ключи словаря, а не номера:

    yandex_compute_instance.app["app"]
    yandex_compute_instance.app["queue"]

  Тот же план создания выглядит так:

    # yandex_compute_instance.app["app"] will be created
    # yandex_compute_instance.app["queue"] will be created
    # yandex_compute_instance.worker[0] will be created
    # module.vpc.yandex_vpc_network.this will be created
    # module.vpc.yandex_vpc_subnet.this["app"] will be created
    # module.vpc.yandex_vpc_subnet.this["data"] will be created
    # module.vpc.yandex_vpc_subnet.this["edge"] will be created

    Plan: 8 to add, 0 to change, 0 to destroy.

  Обратите внимание: подсети внутри модуля тоже создаются циклом
  for_each по словарю subnets, и их адреса содержат ключи.

  Проверим устойчивость адресов: уберём роль queue из словаря.

    # yandex_compute_instance.app["queue"] will be destroyed

    Plan: 0 to add, 0 to change, 1 to destroy.

  Удалилась ровно одна машина. Машина app["app"] и исполнитель
  worker[0] не тронуты. Если бы то же самое делалось через count,
  удаление второго элемента из списка задело бы и третий.

  Причина в разнице адресов. У count адрес — это позиция, и она
  меняется вместе с коллекцией. У for_each адрес — это ключ, и ключ
  элемента от его соседей не зависит: убрали queue — исчез ровно
  ["queue"], добавили новую роль — появился новый ключ, а остальные
  машины остались на месте. Именно поэтому в instances.tf машины
  ролей создаются через for_each по словарю var.instances, где ключ —
  осмысленная роль, а не через count по их числу.

КОГДА ЧТО ПРИМЕНЯТЬ

  count    — ресурсы полностью взаимозаменяемы и их порядок
             не важен: три одинаковых исполнителя очереди;
  for_each — у каждого ресурса есть осмысленный ключ: роли машин,
             зоны, имена подсетей.

  Практическое правило: если можете назвать ресурс словами —
  используйте for_each.

  Ещё одно наблюдение из плана: ключ становится частью адреса ресурса
  в состоянии. Поэтому ключи выбирают один раз и надолго:
  переименование ключа Terraform воспринимает как удаление одного
  ресурса и создание другого. Если переименовать всё же нужно,
  спасает блок moved — о нём в разделе 6.

  for_each принимает словарь или множество (map, set). СПИСОК
  не принимает, и это не придирка: список — про порядок, а порядок
  в адресах ресурсов как раз то, от чего мы уходим. Если у вас
  список, превратите его в множество:

    for_each = toset(var.availability_zones)

  Разберём два случая отдельно.

  СЛОВАРЬ. Ключ словаря становится ключом адреса, значение доступно
  как each.value. В нашем instances.tf это var.instances: ключ — роль
  машины (app, queue), значение — объект с полями subnet, cores
  и memory. Отсюда строки вида each.value.subnet и
  local.instance_names[each.key].

  МНОЖЕСТВО set(string). Здесь ключ и значение совпадают: each.key
  и each.value — одна и та же строка. Адрес тоже содержит строку:
  yandex_vpc_subnet.this["app"]. Удобно, когда нужен просто набор
  уникальных имён.

  ЧЕГО У МНОЖЕСТВА НЕТ — ИНДЕКСОВ. У set нет порядка, поэтому
  обратиться к «первому элементу» нельзя: выражение var.zones[0]
  на множестве даст ошибку

    Error: Invalid index

    The given key does not identify an element in this collection
    value.

  Это защита, а не неудобство: если бы у элемента был номер «первый»,
  набор перестал бы быть набором, и адреса ресурсов снова зависели бы
  от порядка. Если первое значение всё же нужно, набор сначала
  превращают в список (tolist или sort), но тогда вы возвращаетесь
  к позициям — и к count.

  Последняя деталь: ключи for_each должны быть известны до применения.
  Ключом не может быть атрибут ещё не созданного ресурса — Terraform
  остановит план с сообщением, что ключи for_each нельзя определить
  до apply. Поэтому ключами делают имена, зоны и роли, а не
  идентификаторы из облака.

  for_each работает и с модулями: module "app" { for_each = ... } даёт
  адреса вида module.app["app"]..., и правило то же самое.

------------------------------------------------------------------
5. ДИНАМИЧЕСКИЕ БЛОКИ
------------------------------------------------------------------

Правила группы безопасности для разных портов отличаются одним
значением. Писать их копированием — значит забыть добавить порт
в одном месте и не заметить этого.

  resource "yandex_vpc_security_group" "this" {
    name       = "${var.network_name}-sg"
    network_id = yandex_vpc_network.this.id

    dynamic "ingress" {
      for_each = var.allowed_ports

      content {
        description    = "Порт ${ingress.value} из интернета"
        protocol       = "TCP"
        port           = ingress.value
        v4_cidr_blocks = ["0.0.0.0/0"]
      }
    }
  }

Что здесь важно понять:

  * dynamic "имя_блока" создаёт столько вложенных блоков, сколько
    элементов в коллекции;
  * внутри content доступны ingress.key и ingress.value — имя
    переменной совпадает с именем динамического блока, это не
    зарезервированное слово;
  * если имя неудобно, его переопределяют:

      dynamic "ingress" {
        for_each = var.allowed_ports
        iterator = port

        content {
          port = port.value
        }
      }

  * динамический блок можно сделать условным, передав пустую
    коллекцию: for_each = var.enable_public_access ? [80, 443] : [].

КОГДА DYNAMIC УМЕСТЕН, А КОГДА НЕТ

  dynamic уместен, когда блоков заведомо много, они однотипны
  и их число задаётся данными: порты из списка, правила из словаря,
  диски у машины, записи DNS. В нашем модуле так сделаны правила
  ingress: список портов приходит переменной allowed_ports, и число
  блоков заранее неизвестно.

  Явный блок лучше, когда правил два-три и они различаются не одним
  значением. Сравните: правило для 80-го порта с описанием «HTTP
  из интернета» и правило для 22-го с ограничением по адресам — это
  два разных правила, и dynamic заставит выражать разницу условными
  выражениями внутри content. Читаться это будет хуже, чем два
  обычных блока.

  Практическое правило простое: если план нужно открывать, чтобы
  понять, что создаётся, — это перебор. План читают во время
  инцидента, а не при написании кода.

ЕЩЁ ДВЕ ОСОБЕННОСТИ

  * dynamic — это про БЛОКИ, а не про аргументы. Аргумент вроде
    labels или name так не собрать: для аргументов есть обычное
    for-выражение или merge(local.common_labels, {...}).

  * На множество здесь действует то же ограничение, что и в for_each:
    если for_each — set(string), обратиться к элементу по индексу
    нельзя, да и незачем: content выполняется отдельно для каждого
    элемента, и внутри него доступны только ключ и значение. Если
    коллекция пуста (например, портов нет вовсе), не создастся
    ни одного блока — это и есть способ сделать правило условным.

------------------------------------------------------------------
6. СВОЙ МОДУЛЬ
------------------------------------------------------------------

Модуль — это каталог с конфигурацией, которую можно подключать
из других конфигураций. Признак того, что пора делать модуль:
вы копируете один и тот же блок ресурсов во второй проект.

КОНТРАКТ МОДУЛЯ: ВХОДЫ И ВЫХОДЫ

  У модуля ровно две границы, и обе описаны файлами:

  * переменные (variables.tf) — то, что модуль принимает;
  * выводы (outputs.tf) — то, что он отдаёт наружу.

  Всё, что лежит между ними, — внутреннее дело модуля. Это и есть
  контракт: снаружи видны только имена переменных и выводов, и, пока
  они не менялись, внутренности можно переписывать как угодно.

  Из этого следует свойство, на котором спотыкаются чаще всего:
  МОДУЛЬ НЕ ВИДИТ ПЕРЕМЕННЫЕ РОДИТЕЛЯ. Внутри модуля var.subnets —
  это переменная самого модуля, а не корневой конфигурации, даже
  если имена совпадают. Связь появляется только там, где её написали
  руками:

    module "vpc" {
      source  = "../modules/vpc"
      subnets = var.subnets      # передали — модуль увидит
      # network_id = ... передать нельзя: такого входа нет
    }

  Вызов module "vpc" { source = ... } без аргументов ничего не
  «подхватит» извне: он либо упадёт на обязательных переменных
  модуля, либо создаст ресурсы с умолчаниями. Ошибка вида
  «Unsupported argument» означает обратное — вы передали модулю то,
  чего в его контракте нет. Так же и с результатами: ресурс внутри
  модуля снаружи не виден, доступен только module.vpc.<имя_вывода>.

Структура нашего модуля сети (files/modules/vpc):

  versions.tf    версии Terraform и провайдера
  variables.tf   входные параметры: имя сети, подсети, порты, метки
  main.tf        ресурсы: сеть, подсети циклом, группа безопасности
  outputs.tf     что модуль отдаёт наружу

ПРАВИЛА ХОРОШЕГО МОДУЛЯ

  1. Модуль не знает про ваше окружение. Никаких cloud_id, folder_id
     и зон внутри: всё приходит переменными. Иначе модуль нельзя
     переиспользовать.
  2. Всё, что нужно снаружи, модуль отдаёт через outputs.
     Если этого не сделать, вызывающей конфигурации придётся
     угадывать идентификаторы.
  3. У модуля своя версия. У локального модуля роль версии играет
     система контроля версий, у внешнего — параметр ref.
  4. У модуля есть README: что он создаёт, какие переменные
     обязательны, что не поддерживается.

ПОДКЛЮЧЕНИЕ ЛОКАЛЬНОГО МОДУЛЯ

  module "vpc" {
    source = "../modules/vpc"

    network_name  = "${var.project_name}-${var.environment}-net"
    subnets       = var.subnets
    allowed_ports = var.allowed_ports
    labels        = local.common_labels
  }

  Путь в source — относительный, от каталога, где лежит файл
  с вызовом модуля. Файлы модуля при этом НЕ копируются: они
  остаются на месте.

  Частая ошибка новичка: указать путь на уровень выше или ниже
  и получить

    Error: Unreadable module directory
    Error: Module not installed

  Второе сообщение означает, что модуль ещё не установлен: после
  добавления модуля нужно выполнить terraform init.

  ОТКУДА МОЖНО БРАТЬ МОДУЛЬ

  В source допустимы несколько видов адресов, и у каждого свои
  последствия для обновлений:

    source = "../modules/vpc"        # свой модуль рядом с практикой
    source = "./modules/vpc"         # свой модуль внутри проекта
    source = "terraform-aws-modules/vpc/aws"   # публичный реестр
    source = "git::https://github.com/org/repo.git//modules/vpc?ref=v1.4.0"

  Локальный путь — самый простой и самый связанный: модуль меняется
  вместе с проектом, и версия у него одна на всех. Адрес в реестре
  состоит из трёх частей (владелец/имя/провайдер) и требует
  отдельного аргумента version. Ссылка на git — это, по сути, тот же
  чужой код, только с другой площадки: через ?ref= указывают тег,
  ветку или коммит, и надёжен здесь только тег.

  ЧЕГО СТОИТ ОТСУТСТВИЕ ВЕРСИИ. Без зафиксированной версии init
  каждый раз забирает то, что сейчас лежит в источнике, — обычно
  ветку по умолчанию. Дальше события развиваются так: чужой модуль
  обновили, у вас на машине план один, в конвейере другой, а у коллеги
  третий. Ошибка воспроизводится «через раз», а причина — в строке,
  которая выглядит безобидно. Поэтому у внешнего модуля версию
  указывают всегда, а её обновление делают отдельным изменением,
  чтобы его было видно в ревью.

  КАК ЧИТАТЬ ПЛАН, КОГДА ПОЯВИЛСЯ МОДУЛЬ. После добавления или
  обновления модуля сначала выполняют terraform init: он скачивает
  модуль, и только после этого план вообще можно построить. В плане
  и в state list адреса получают префикс module.<имя>, и по нему
  видно, что создаёт модуль: module.vpc.yandex_vpc_subnet.this.
  Если при добавлении модуля план показывает не только создание,
  но и destroy для ресурсов, которые уже существовали, — значит
  адреса изменились и Terraform считает их разными объектами.
  Лечится это блоком moved.

  ПЕРЕНОС РЕСУРСА В МОДУЛЬ: MOVED

  Пусть сеть уже создана корневой конфигурацией и её решили вынести
  в модуль. Для Terraform это два разных ресурса: адрес
  yandex_vpc_network.this и module.vpc.yandex_vpc_network.this. Без
  подсказки план покажет удаление старой сети и создание новой, а для
  сети это означает пересоздание всего, что на неё ссылается.

  Блок moved сообщает, что это один и тот же объект:

    moved {
      from = yandex_vpc_network.this
      to   = module.vpc.yandex_vpc_network.this
    }

  Что важно знать про moved:

  * from — старый адрес, to — новый; оба указываются без кавычек;
  * адреса должны описывать один и тот же объект: moved переносит
    запись в состоянии, а не создаёт ресурс;
  * в плане появляется строка «has moved to», и ни удаления,
    ни создания при этом не происходит;
  * после применения блок можно удалить — перенос уже записан
    в состояние.

  Так же переносят ресурс из модуля в корень (адреса меняются
  местами) и из одного модуля в другой. Если ресурсов несколько,
  блоков moved тоже несколько. Подробнее про состояние и moved —
  в практике 2.

ОБРАЩЕНИЕ К РЕЗУЛЬТАТАМ МОДУЛЯ

  Идентификаторы, созданные внутри модуля, доступны по адресу
  module.<имя_модуля>.<имя_вывода>:

    network_interface {
      subnet_id = module.vpc.subnet_ids[each.value.subnet]
    }

  Здесь subnet_ids — это словарь из outputs модуля:

    output "subnet_ids" {
      value = { for name, subnet in yandex_vpc_subnet.this : name => subnet.id }
    }

  Внутри модуля адрес ресурса — yandex_vpc_subnet.this["app"],
  снаружи — module.vpc.subnet_ids["app"]. Разница видна и в выводе
  terraform state list:

    module.vpc.yandex_vpc_network.this
    module.vpc.yandex_vpc_security_group.this
    module.vpc.yandex_vpc_subnet.this["app"]
    module.vpc.yandex_vpc_subnet.this["data"]
    module.vpc.yandex_vpc_subnet.this["edge"]

  Модуль не создаёт «ещё один уровень» в облаке: в облаке по-прежнему
  одна сеть и три подсети. Модуль — это уровень описания,
  а не уровень инфраструктуры.

7. ГОТОВЫЙ МОДУЛЬ ИЗ БИБЛИОТЕКИ
------------------------------------------------------------------

Яндекс публикует набор модулей terraform-yc-modules на GitHub:
сеть, кластер Kubernetes, группа машин и другие. Пользоваться ими
можно и нужно — так экономят время и получают конфигурацию,
написанную людьми, которые знают сервис.

В документации источник модуля показан так:

  source = "git@github.com:terraform-yc-modules/terraform-yc-vpc.git"

Это адрес для SSH: чтобы он заработал, нужен SSH-ключ, добавленный
в GitHub. На учебной машине его обычно нет, и init падает с ошибкой
Permission denied (publickey). Рабочий вариант — HTTPS:

  module "vpc" {
    source = "git::https://github.com/terraform-yc-modules/terraform-yc-vpc.git?ref=1.0.9"

    network_name = "tf-lang-library-net"

    private_subnets = [
      {
        name           = "subnet-a"
        zone           = "ru-central1-a"
        v4_cidr_blocks = ["10.50.0.0/24"]
      },
      {
        name           = "subnet-b"
        zone           = "ru-central1-b"
        v4_cidr_blocks = ["10.50.1.0/24"]
      },
    ]
  }

Приставка git:: означает «скачать средствами git», а ref=1.0.9 —
версию (тег). Версию указывать обязательно: без неё будет скачана
ветка по умолчанию, и однажды она изменится — без предупреждения
и в самый неподходящий момент.

  Три вида источника различаются в первую очередь способом указать
  версию, и это единственное, что стоит держать в голове:

    source = "../modules/vpc"                  # версия = версия проекта
    source = "ns/name/provider"                # version = "~> 1.0"
    source = "git::https://...git?ref=v1.0.9"  # версия = git-тег

  В реестре версия — отдельный аргумент version, и он понимает
  ограничения вида "~> 1.0" («любая 1.x начиная с 1.0»). В git это
  параметр ref, и ограничений там нет: либо конкретный тег, либо
  ветка, которая однажды уедет. У локального модуля версии нет вовсе —
  её роль играет история самого проекта.

Проверим, что делается при инициализации:

  terraform init

  Downloading git::https://github.com/terraform-yc-modules/
              terraform-yc-vpc.git?ref=1.0.9 for vpc...
  Terraform has been successfully initialized!

  (Длинная строка перенесена — в терминале она выводится одной строкой.)

А теперь посмотрим план внимательно:

  # module.vpc.yandex_vpc_default_security_group.default_sg[0] will be created
  # module.vpc.yandex_vpc_gateway.egress_gateway[0] will be created
  # module.vpc.yandex_vpc_network.this[0] will be created
  # module.vpc.yandex_vpc_route_table.private[0] will be created
  # module.vpc.yandex_vpc_route_table.public[0] will be created
  # module.vpc.yandex_vpc_subnet.private["10.50.0.0/24"] will be created
  # module.vpc.yandex_vpc_subnet.private["10.50.1.0/24"] will be created

  Plan: 7 to add, 0 to change, 0 to destroy.

ЧЕМУ ЭТО УЧИТ

  * Чужой модуль создаёт БОЛЬШЕ, чем вы просили. Мы попросили сеть
    и две подсети, а получили ещё NAT-шлюз, таблицы маршрутизации
    и группу безопасности по умолчанию. Шлюз — платный ресурс:
    за время практики это копейки, но в рабочей среде такие
    «подарки» надо видеть заранее.
  * Ключи в результатах модуля могут быть не такими, как вы ждёте.
    Подсети в выводе оказались с ключом по диапазону адресов
    ("10.50.0.0/24"), а не по имени subnet-a:

      output "subnets" {
        value = module.vpc.private_subnets
      }

      # "10.50.1.0/24" = {
      #     "name"           = "subnet-b"
      #     "subnet_id"      = "e2l547l6i77hogd8qij5"
      #     "zone"           = "ru-central1-b"
      # }

  * Поэтому входные переменные и результаты чужого модуля читают
    в его README, а не угадывают. Удобный способ посмотреть, что
    модуль принимает:

      terraform providers schema -json   # для провайдеров
      terraform-docs                     # для модулей, если установлен

Ещё одна практическая оговорка: правило «не доверяй чужому модулю
слепо» особенно верно для инфраструктуры. Перед применением
читайте план и держите версию зафиксированной — тогда обновление
модуля станет осознанным действием.

  Пример подключения готового модуля — в отдельном файле,
  чтобы его можно было положить в свой каталог и попробовать.

  mkdir -p public_module

cat > public_module/main.tf <<'EOF'
# Пример подключения готового модуля из библиотеки terraform-yc-modules.
#
# Это отдельный пример, а не часть основной конфигурации практики:
# положите его в отдельный каталог, если хотите попробовать.
#
# ЧТО МЕНЯЕТСЯ ПО СРАВНЕНИЮ СО СВОИМ МОДУЛЕМ
#
#   * источник (source) — адрес git-репозитория, а не путь на диске;
#   * обязателен параметр ref — версия (тег) модуля;
#   * модуль создаёт ресурсы по своим правилам, и его входные
#     переменные надо смотреть в документации модуля (README в
#     репозитории), а не угадывать.
#
# ПОЧЕМУ git::https, А НЕ git@github.com
#
#   Документация Яндекс Облака показывает источник в виде
#   git@github.com:terraform-yc-modules/terraform-yc-vpc.git.
#   Такой адрес требует настроенного SSH-ключа, добавленного в GitHub.
#   На учебной машине его обычно нет, и init падает с ошибкой
#   «Permission denied (publickey)».
#
#   Надёжнее использовать HTTPS — он работает без ключей:
#
#     source = "git::https://github.com/terraform-yc-modules/terraform-yc-vpc.git?ref=1.0.9"
#
#   Приставка git:: говорит Terraform, что источник надо скачать
#   средствами git.
#
# ЧТО ВАЖНО ПРО ВЕРСИИ
#
#   Параметр ref обязателен в рабочей среде: без него модуль будет
#   скачиваться из ветки по умолчанию, и однажды он изменится —
#   без предупреждения и в самый неподходящий момент. Допустимые
#   значения ref: тег (1.0.9), ветка (main), коммит.

terraform {

  monitoring_cidr = "10.40.1.0/24"

  instances = {

      "internal_ip" = "10.30.10.13"

      "external_ip" = "84.201.178.170"
      "internal_ip" = "10.30.20.29"
      "name" = "tf-lang-p3-dev-queue"
      "zone" = "ru-central1-b"
    }
  }

  workers = [
    {
      "external_ip" = "158.160.205.32"
      "name" = "tf-lang-p3-dev-worker-1"
    },
  ]

  db_password = <sensitive>

  inventory_json = "{\"environment\":\"dev\",
     \"instances\":{\"app\":\"10.30.10.13\",\"queue\":\"10.30.20.29\"},
     \"workers\":[\"10.30.30.3\"]}"

Обратите внимание:

  * вывод-коллекция собирается циклом for прямо в блоке output;
  * чувствительное значение показано как <sensitive> — именно так
    работает флаг sensitive;
  * вывод с jsonencode даёт одну строку, которую удобно забирать
    скриптом:

      terraform output -json inventory_json

    Такие выводы используют для передачи данных в другие системы:
    инвентарь для системы управления конфигурациями, список адресов
    для балансировщика, значения для конвейера.

    Такой вывод — это интерфейс для других систем, поэтому его форму
    выбирают осознанно. Словарь удобен, когда по ключу ищут значение
    (инвентарь для системы управления конфигурациями), список — когда
    важен порядок обхода, а одна строка JSON — когда результат
    забирает скрипт или конвейер. Поэтому к выводам применимо то же
    правило, что и к переменным: пока имя и смысл совпадают, всё
    в порядке, а смена формы — это изменение контракта, о котором
    нужно предупредить.


  Выходные значения практики собраны в файле outputs.tf:
  здесь и коллекции, и чувствительный вывод, и JSON.

cat > outputs.tf <<'EOF'
# Выходные значения.

#   * вывод коллекции целиком (словарь адресов всех машин);
#   * вывод с sensitive = true — значение скрывается в терминале;
#   * вывод в JSON — удобно забирать скриптами и конвейером.

output "instances" {
  description = "Машины ролей: ключ — роль, значение — адреса"
  value = {
    for role, vm in yandex_compute_instance.app :
    role => {
      name        = vm.name
      zone        = vm.zone
      external_ip = vm.network_interface[0].nat_ip_address
      internal_ip = vm.network_interface[0].ip_address
    }
  }
}

output "workers" {
  description = "Машины-исполнители, созданные через count"
  value = [
    for vm in yandex_compute_instance.worker : {
      name        = vm.name
      external_ip = vm.network_interface[0].nat_ip_address
    }
  ]
}

output "subnet_ids" {
  description = "Идентификаторы подсетей из модуля vpc"
  value       = module.vpc.subnet_ids
}

output "subnet_count" {
  description = "Сколько подсетей создал модуль"
  value       = module.vpc.subnet_count
}

output "summary" {
  description = "Сводка по стенду из locals"

9. КАК ПИСАТЬ ПОНЯТНЫЕ КОНФИГУРАЦИИ
------------------------------------------------------------------

Несколько привычек, которые отличают конфигурацию, которую через
полгода можно читать, от той, которую проще переписать.

  СТРУКТУРА ФАЙЛОВ ПО СМЫСЛУ. Не «main.tf со всем содержимым»,
  а network.tf, instances.tf, variables.tf, outputs.tf. Terraform
  читает все файлы каталога как один, поэтому имена файлов —
  удобство для людей.

  ИМЕНА РЕСУРСОВ СЛОВАМИ. yandex_compute_instance.app читается,
  yandex_compute_instance.vm1 — нет. Имя ресурса живёт в состоянии,
  и его потом не переименовать без блока moved.

  КОММЕНТАРИИ ПРО «ПОЧЕМУ», А НЕ «ЧТО». Строка «создаём сеть» бесполезна:
  это и так видно из кода. Полезно другое: «отдельная сеть, потому что
  в общей запрещены широкие диапазоны адресов».

  ОДИН СТЕНД — ОДИН КАТАЛОГ. Смешивать окружения в одном каталоге
  через переменные можно, но состояние общее, а значит ошибка в одном
  окружении задевает второе. Про разделение окружений — в практике 9.

  ПРОВЕРКИ ДЛЯ ВСЕГО, ЧТО МОЖНО ПРОВЕРИТЬ. Зона из списка, размер
  диска в диапазоне, число машин не больше трёх. Проверка стоит
  две строки и экономит полчаса.

  ФОРМАТИРОВАНИЕ ТОЖЕ ЧАСТЬ СТИЛЯ. У языка Terraform есть канон
  оформления, и его применяет команда terraform fmt: она выравнивает
  знаки равенства, приводит отступы к двум пробелам, разбивает
  слишком длинные строки. Запускают её перед коммитом:

    terraform fmt -recursive

  А в конвейере проверяют, ничего не меняя:

    terraform fmt -check -recursive

  ЗАЧЕМ ЭТО НУЖНО, КРОМЕ КРАСОТЫ. Ревью читают диффом, и в диффе
  важно видеть смысл, а не оформление. Пока каждый выравнивает знаки
  равенства как хочет, правка одной строки тащит за собой
  переформатированный блок, и в нём тонут настоящие изменения. Когда
  файл причёсан одной командой, дифф показывает только то, что
  действительно поменяли.

    resources {
      cores         = each.value.cores
      memory        = each.value.memory
      core_fraction = 20
    }

  Здесь сразу видно, что значения разные, а аргументы — одного
  уровня, и выровнены они по самому длинному имени. То же требование
  действует и к отступам вложенных блоков: они показывают структуру
  ресурса.

10. ПОЛЕЗНЫЕ ФУНКЦИИ И ПРИЁМЫ
------------------------------------------------------------------

  ФИЛЬТРАЦИЯ В ЦИКЛЕ (if):

    locals {
      # только рабочие подсети
      prod_subnets = {
        for name, s in var.subnets : name => s if s.zone != "ru-central1-a"
      }
    }

    Условие if отсеивает элементы: в новый словарь попадут только те
    подсети, у которых зона не ru-central1-a. Синтаксис читается как
    фраза: «для каждой подсети — имя и объект, если условие
    выполнено». Тот же приём работает и для списков:

      open_ports = [for p in var.allowed_ports : p if p != 22]

    Если условие окажется ложным для всех элементов, получится пустая
    коллекция. Это законный результат, но помните: пустая коллекция
    в for_each или в dynamic означает «не создавать ничего» — иногда
    это именно то, что нужно, а иногда признак ошибки в условии.

  ПРОВЕРКА УСЛОВИЯ ДЛЯ ВСЕЙ КОЛЛЕКЦИИ:

    validation {
      condition     = alltrue([for p in var.allowed_ports : p > 0 && p <= 65535])
      error_message = "Порт должен быть в диапазоне от 1 до 65535."
    }

    anytrue() — «хотя бы один элемент», alltrue() — «все элементы».

  ПОИСК С ЗАПАСНЫМ ЗНАЧЕНИЕМ:

    lookup(local.subnet_by_zone, var.zone, local.first_subnet_name)

  ПЕРВЫЙ ЭЛЕМЕНТ ИЛИ ЗНАЧЕНИЕ ПО УМОЛЧАНИЮ: one(), try().
  one([1]) вернёт 1, one([]) вернёт null — удобно, когда ресурс
  создаётся условно через count.

    Разница между ними по смыслу. one() отвечает на вопрос «сколько
    элементов» и работает только с коллекцией из нуля или одного
    элемента: one([1]) вернёт 1, one([]) вернёт null, а one([1, 2])
    остановит план — это защита от неоднозначности. try() шире:
    он перехватывает любую ошибку выражения, поэтому им проверяют
    обращения к необязательным полям структур:

      subnet_zone = try(var.subnets[var.zone].zone, null)

    Правило выбора: если речь о длине коллекции — one(), если
    о возможной ошибке в выражении — try(). И не заворачивайте
    в try() половину конфигурации: вместе с ошибкой он спрячет
    и опечатку в имени переменной.

  СПЛАТ-ВЫРАЖЕНИЕ: [*]

    Все адреса машин, созданных через count, одной строкой:

      worker_ips = yandex_compute_instance.worker[*].network_interface[0].nat_ip_address

    Знак [*] означает «взять это поле у каждого элемента коллекции»
    и собрать результат в список. Без сплата то же самое пришлось бы
    писать циклом:

      worker_ips = [
        for w in yandex_compute_instance.worker :
        w.network_interface[0].nat_ip_address
      ]

    Сплат работает с count, потому что элементы различаются позициями.
    Для for_each он не подходит: у элементов есть ключи, а не номера,
    и результат собирают циклом for по словарю:

      instance_ips = {
        for role, vm in yandex_compute_instance.app :
        role => vm.network_interface[0].nat_ip_address
      }

    Обратите внимание: такой вывод не только короче, но и понятнее
    снаружи — ключи в нём осмысленные, и по ним видно, где чей адрес.

  ОБЪЕДИНЕНИЕ КОЛЛЕКЦИЙ: concat(), flatten(), setunion().
  ПРЕОБРАЗОВАНИЕ: toset(), tolist(), tomap(), tostring(), tonumber().

  ГРУППИРОВКА: { for x in list : x.key => x } — самый частый способ
  превратить список объектов в словарь по ключу.

  Отдельно стоит знать про функции работы с файлами: file(),
  filebase64(), templatefile(). Последняя подставляет значения
  в шаблон — удобно для cloud-init (практика 4).

11. ПРОВЕРКИ ПРЯМО В РЕСУРСАХ
------------------------------------------------------------------

Кроме проверок переменных, бывают проверки в ресурсах: они срабатывают
во время плана или применения и, в отличие от validation, могут
сравнивать ресурсы между собой.

  precondition — проверить условие ПЕРЕД созданием ресурса:

    lifecycle {
      precondition {
        condition     = data.yandex_compute_image.os.family != ""
        error_message = "Не удалось определить семейство образов."
      }
    }

  postcondition — проверить результат ПОСЛЕ создания:

    lifecycle {
      postcondition {
        condition     = self.network_interface[0].nat_ip_address != ""
        error_message = "Машина создана без публичного адреса."
      }
    }

  check — отдельный блок для проверок, которые не должны мешать
  применению (Terraform 1.5+):

    check "vm_has_ip" {
      assert {
        condition = (
          yandex_compute_instance.app["app"].network_interface[0].nat_ip_address != ""
        )
        error_message = "Машина app осталась без публичного адреса."
      }
    }

    Отличие от precondition: провал check не останавливает apply,
    а печатает предупреждение. Это способ сказать «инфраструктура
    собралась, но выглядит подозрительно».

  ЧТО ВЫБРАТЬ

    Правило простое и повторяет всё, что уже сказано про проверки:

    * validation — для входных значений: срабатывает раньше всех,
      дёшево, ничего не знает о ресурсах;
    * precondition — для условий, которые нужно проверить перед
      изменением конкретного ресурса, в том числе с участием других
      ресурсов и источников данных;
    * postcondition — для проверки того, что реально получилось
      (адрес появился, диск не пустой); внутри доступен self;
    * check — для подозрительных ситуаций, из-за которых не нужно
      останавливать работу: результат попадёт в вывод плана
      как предупреждение.

    И то, ради чего всё это: ошибка, найденная на плане, стоит одного
    запуска, а та же ошибка, найденная через неделю на работающем
    стенде, — нескольких часов разбирательства. Проверка переносит
    обнаружение проблемы в самый дешёвый момент.

12. КАК ЭТО ЖЕ ДЕЛАЕТСЯ В AWS И VK CLOUD
------------------------------------------------------------------

Язык Terraform един для всех провайдеров, поэтому переменные, циклы,
динамические блоки и модули выглядят одинаково. Различия —
в источниках модулей и в их зрелости.

  Яндекс Облако
      Модули: библиотека terraform-yc-modules на GitHub.
      В публичном реестре Terraform модулей Яндекса нет, поэтому
      источник указывают как git::https с тегом.
      Кластер Kubernetes, сеть, группа машин — модули есть.

  AWS
      Модули: terraform-aws-modules, опубликованы в реестре Terraform.
      Подключение выглядит так:

        module "vpc" {
          source  = "terraform-aws-modules/vpc/aws"
          version = "6.7.3"
        }

      Обратите внимание: version — отдельный аргумент, а не ?ref=.
      Это следствие того, что модуль взят из реестра, а не из git.
      У модулей AWS есть документация с примерами, и она генерируется
      автоматически из переменных.

  VK Cloud
      Модули: у провайдера vk-cs/vkcs есть собственные модули и примеры
      в репозиториях VK; в реестре Terraform публикуются сторонние.
      Подход тот же: source + версия.

  Что важно понять: приём «сначала посмотри в реестре модулей, потом
  пиши свой» работает в любом облаке. Свой модуль пишут тогда, когда
  готовый не подходит по составу ресурсов или по внутренним правилам
  компании.

13. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

  СИМПТОМ: Error: Illegal argument subnet_id. Zone in subnet does not
  match expected zone
  ПРИЧИНА: машина создаётся в зоне X, а подсеть — в зоне Y. В Яндекс
  Облаке зона виртуальной машины обязана совпадать с зоной подсети.
  Типовая причина: подсеть выбрана «первым ключом словаря», а зона —
  отдельной переменной. Так и получается эта ошибка: keys() вернул
  ключи по алфавиту, первым оказался app (зона ru-central1-a), а зона
  машины была ru-central1-d.
  ЧТО ДЕЛАТЬ: брать зону из той же подсети, в которой создаётся машина:

    zone      = var.subnets[local.subnet_in_default_zone].zone
    subnet_id = module.vpc.subnet_ids[local.subnet_in_default_zone]

  СИМПТОМ: Error: Invalid value for variable
  ПРИЧИНА: не прошла проверка validation.
  ЧТО ДЕЛАТЬ: прочитать error_message — она написана для человека.
  Это самая полезная ошибка из всех: она появляется до обращения
  к облаку.

  СИМПТОМ: The given "for_each" argument value is unsuitable: the
  given value is a list
  ПРИЧИНА: for_each требует словарь или множество, а передан список.
  ЧТО ДЕЛАТЬ: for_each = toset(var.list).

  СИМПТОМ: Error: Unreadable module directory / Module not installed
  ПРИЧИНА: неверный путь в source, либо модуль не установлен.
  ЧТО ДЕЛАТЬ: проверить путь относительно файла с вызовом модуля
  и выполнить terraform init после добавления модуля.

  СИМПТОМ: Permission denied (publickey) при init модуля из git
  ПРИЧИНА: источник указан как git@github.com (SSH), а ключа нет.
  ЧТО ДЕЛАТЬ: использовать git::https://... с параметром ref.

  СИМПТОМ: после удаления элемента из списка пересоздались машины,
  которых мы не трогали
  ПРИЧИНА: использован count. Индексы сдвинулись, и Terraform счёл
  позиции новыми ресурсами.
  ЧТО ДЕЛАТЬ: перейти на for_each по словарю; для уже созданных
  ресурсов — блок moved, чтобы сохранить их.

  СИМПТОМ: значение sensitive всё равно видно в файле состояния
  ПРИЧИНА: так и должно быть: sensitive защищает вывод команд,
  а не состояние.
  ЧТО ДЕЛАТЬ: хранить секреты в хранилище секретов, состояние —
  в бакете с ограниченным доступом (практики 2 и 6).

  СИМПТОМ: план хочет пересоздать ресурс из-за изменения адреса
  ПРИЧИНА: изменился ключ в for_each или индекс в count.
  ЧТО ДЕЛАТЬ: посмотреть строки с forces replacement, при
  необходимости — блок moved (практика 2).

В практике 4 займёмся вычислениями: платформы и пресеты, диски
