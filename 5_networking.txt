ПРАКТИКА 5. СЕТИ: ПОДСЕТИ, ГРУППЫ БЕЗОПАСНОСТИ, DNS, БАЛАНСИРОВЩИК

Продолжительность: 2 академических часа.
Провайдер: yandex-cloud/yandex. Практика выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ЗАНЯТИЯ

  Вы соберёте сеть из трёх подсетей в трёх зонах доступности,
  замените «разрешить всё» на свои группы безопасности с правилами
  по ссылкам, закрепите за веб-сервером постоянный публичный адрес,
  заведёте публичную и приватную зоны DNS и поставите перед сервером
  прикладной балансировщик, который понимает HTTP.

ЧТО НУЖНО ЗАРАНЕЕ

  * Доступ в облако (практика 1) и понимание состояния (практика 2).
  * Опыт практики 4: NAT-шлюз, cloud-init и проверки здоровья —
    здесь они используются теми же приёмами.

ПРО ДОМЕН

  Для части про сертификаты и HTTPS нужен домен, которым вы владеете:
  сертификат Let's Encrypt в Certificate Manager выпускается только
  после подтверждения владения доменом. В этой практике мы разбираем
  ALB по HTTP, а выпуск сертификата и HTTPS описаны в конце как
  упражнение: без делегированного домена их не проверить.

1. ЗОНАЛЬНЫЕ И ГЛОБАЛЬНЫЕ РЕСУРСЫ
------------------------------------------------------------------

Первое, что нужно усвоить про сети в облаке: ресурсы делятся на два
вида.

  ГЛОБАЛЬНЫЕ — не привязаны к зоне доступности. Облачная сеть,
  бакет Object Storage, DNS-зона, реестр образов.

  ЗОНАЛЬНЫЕ — существуют внутри одной зоны. Подсеть, машина, диск,
  статический адрес, кластер managed-базы.

Из этого следуют практические выводы:

  * ОДНА СЕТЬ — МНОГО ПОДСЕТЕЙ. Сеть создаётся один раз, подсети —
    по одной на каждую зону, в которой планируются ресурсы.
  * ЗОНАЛЬНЫЙ РЕСУРС НЕЛЬЗЯ ПЕРЕНЕСТИ В ДРУГУЮ ЗОНУ. Подсеть из зоны
    ru-central1-a в зону ru-central1-b не переезжает: её можно только
    создать заново, а машины — пересоздать.
  * ЗОНЫ ДОСТУПНОСТИ В ОБЛАКЕ И ВАШИ ПОДСЕТИ — РАЗНЫЕ СПИСКИ.
    Посмотреть зоны облака:

      yc compute zone list

    В Яндекс Облаке сейчас доступны ru-central1-a, -b, -d (рекомендуемая
    для новых проектов), -e, а также -m для baremetal. При этом подсети
    у нас будут только в трёх зонах из пяти: в остальных машину создать
    нельзя, потому что нет подсети.

  ИСПРАВЛЕНО. В прежней версии курса встречалась зона ru-central1-c.
  Такой зоны больше не существует.

  Наша сеть описывается так:

    resource "yandex_vpc_network" "this" {
      name = "${var.project_name}-net"
    }

    resource "yandex_vpc_subnet" "this" {
      for_each = var.subnets

      name           = "${var.project_name}-${each.key}"
      zone           = each.value.zone
      network_id     = yandex_vpc_network.this.id
      v4_cidr_blocks = [each.value.cidr]

      route_table_id = var.enable_nat_gateway ? yandex_vpc_route_table.nat[0].id : null
    }

  Диапазоны подсетей выбираются так, чтобы в будущем их можно было
  объединить в одну маршрутизируемую сеть. Мы используем 10.70.10.0/24,
  10.70.20.0/24 и 10.70.30.0/24 — это три подсети внутри одного
  диапазона 10.70.0.0/16.

2. NAT-ШЛЮЗ И ТАБЛИЦА МАРШРУТИЗАЦИИ
------------------------------------------------------------------

Разобрано в практике 4, здесь только напоминание: машина без
публичного адреса не имеет выхода в интернет, пока в сети нет
NAT-шлюза и таблицы маршрутизации, а подсети не ссылаются на эту
таблицу.

  resource "yandex_vpc_gateway" "nat" {
    count = var.enable_nat_gateway ? 1 : 0
    name  = "${var.project_name}-nat"
    shared_egress_gateway {}
  }

  resource "yandex_vpc_route_table" "nat" {
    count      = var.enable_nat_gateway ? 1 : 0
    name       = "${var.project_name}-rt"
    network_id = yandex_vpc_network.this.id

    static_route {
      destination_prefix = "0.0.0.0/0"
      gateway_id         = yandex_vpc_gateway.nat[0].id
    }
  }

Почему таблица отдельный ресурс: одна таблица может обслуживать
несколько подсетей, а в одной сети их может быть несколько — например,
одна для доступа в интернет, вторая для доступа к корпоративной сети
через VPN.

------------------------------------------------------------------
3. СВОИ ГРУППЫ БЕЗОПАСНОСТИ
------------------------------------------------------------------

До этой практики мы пользовались группой безопасности, которую создал
модуль. Теперь разберём, как их описывают всерьёз.

ДВА СПОСОБА ОПИСАНИЯ ПРАВИЛ

  Вложенные блоки внутри группы:

    resource "yandex_vpc_security_group" "web" {
      name       = "web-sg"
      network_id = yandex_vpc_network.this.id

      ingress {
        protocol       = "TCP"
        port           = 80
        v4_cidr_blocks = ["0.0.0.0/0"]
      }
    }

  Отдельные ресурсы правил:

    resource "yandex_vpc_security_group" "web" {
      name       = "${var.project_name}-web-sg"
      network_id = yandex_vpc_network.this.id
    }

    resource "yandex_vpc_security_group_rule" "web_public" {
      security_group_binding = yandex_vpc_security_group.web.id
      direction              = "ingress"
      protocol               = "TCP"
      port                   = 80
      v4_cidr_blocks         = ["0.0.0.0/0"]
    }

  В курсе мы используем второй способ, и вот почему: правила видны
  поштучно. В плане и в истории изменений понятно, какое именно
  правило добавлено или изменено, а порядок правил не влияет на
  результат. При первом способе Terraform управляет блоком целиком.

  Обратите внимание на имя аргумента: security_group_binding. Именно
  так в текущей версии провайдера указывается группа, к которой
  привязывается правило.

ПРАВИЛО ПО ССЫЛКЕ НА ДРУГУЮ ГРУППУ

  Самое полезное свойство групп безопасности — возможность указать
  источником не адреса, а другую группу:

    resource "yandex_vpc_security_group_rule" "internal_from_web" {
      security_group_binding = yandex_vpc_security_group.internal.id
      direction              = "ingress"
      protocol               = "TCP"
      port                   = 8080

      # Источник — идентификатор другой группы безопасности.
      security_group_id = yandex_vpc_security_group.web.id
    }

  Читается так: «на 8080-й порт внутренних сервисов пускать машины
  из группы web». Адреса машин при этом не перечисляются, и это
  принципиально: машины пересоздаются, адреса меняются, а группа
  остаётся. Именно так описывают доступ «приложение → база данных».

ПРО ПОРТ 22

  В учебной конфигурации SSH открыт всему интернету — иначе студенты
  не смогут подключиться с произвольного адреса. В рабочей среде так
  делать нельзя: попытки подбора ключей начинаются в первые часы после
  появления машины с открытым 22-м портом. Правильно — ограничить
  адресами офиса или пускать через бастион:

    v4_cidr_blocks = ["203.0.113.10/32"]

ПРО ИСХОДЯЩИЙ ТРАФИК

  Разобрано в практике 4: ограничение egress — самая частая причина
  «машина есть, а пакеты не ставятся». В учебной конфигурации исходящий
  трафик разрешён полностью.

------------------------------------------------------------------
4. СТАТИЧЕСКИЙ АДРЕС: ПРОВЕРКА НА ЖИВОМ СТЕНДЕ
------------------------------------------------------------------

Помните, как в практике 1 после изменения размеров машина
перезапустилась, и внешний адрес сменился? Вот что это значит на
практике: запись в DNS, правило файрвола у клиента и белый список
в чужой системе — всё это перестаёт работать. Для сервисов,
к которым обращаются извне, адрес закрепляют.

  resource "yandex_vpc_address" "web" {
    name = "${var.project_name}-web-ip"

    external_ipv4_address {
      zone_id = var.zone
    }
  }

Подключение к машине:

  network_interface {
    subnet_id      = yandex_vpc_subnet.this["web-d"].id
    nat            = true
    nat_ip_address = yandex_vpc_address.web.external_ipv4_address[0].address
    security_group_ids = [yandex_vpc_security_group.web.id]
  }

ПРОВЕРИМ, ЧТО АДРЕС ДЕЙСТВИТЕЛЬНО ПОСТОЯННЫЙ

  До пересоздания:

    terraform output -raw web_static_ip
    84.252.135.180

  Пересоздаём машину (заодно вспомним ключ -replace):

    terraform apply -replace=yandex_compute_instance.web

    yandex_compute_instance.web: Destroying... [id=fv4r9nibjf6mhnbv50ho]
    yandex_compute_instance.web: Creation complete after 38s [id=fv4tqcqeqfi4a1udqt3i]
    Apply complete! Resources: 1 added, 1 changed, 1 destroyed.

    web_private_ip = "10.70.30.15"
    web_static_ip  = "84.252.135.180"

  Внешний адрес не изменился, а внутренний сменился (был 10.70.30.18).
  Это и есть разница: публичный адрес закреплён за вами и живёт
  отдельно от машины, внутренний выдаётся в подсети при создании.

  За закреплённый адрес берут плату, и она выше, когда адрес
  не используется. Поэтому неиспользуемые адреса освобождают:
  terraform destroy удалит и адрес тоже.

5. DNS: ПУБЛИЧНАЯ И ПРИВАТНАЯ ЗОНЫ
------------------------------------------------------------------

В Яндекс Облаке есть два вида зон, и это разделение нужно понимать.

  ПУБЛИЧНАЯ ЗОНА (public = true) отвечает на запросы из интернета —
  но только после того, как домен делегирован облаку: у регистратора
  прописаны NS-серверы зоны. Создать зону можно для любого имени,
  облако не проверяет права на домен; работать она начнёт после
  делегации.

  ПРИВАТНАЯ ЗОНА (public = false) видна только машинам указанных
  сетей. Так решают внутренние имена сервисов.

    resource "yandex_dns_zone" "public" {
      name   = "${var.project_name}-public-zone"
      zone   = var.dns_zone
      public = true
    }

    resource "yandex_dns_zone" "internal" {
      name             = "${var.project_name}-internal-zone"
      zone             = "${var.project_name}.internal."
      public           = false
      private_networks = [yandex_vpc_network.this.id]
    }

ЗАПИСИ СОЗДАЮТСЯ ДВУМЯ СПОСОБАМИ

  Отдельным ресурсом — для любых имён и типов:

    resource "yandex_dns_recordset" "service" {
      zone_id = yandex_dns_zone.public.id
      name    = "service.${var.dns_zone}"
      type    = "A"
      ttl     = 300
      data    = [yandex_vpc_address.web.external_ipv4_address[0].address]
    }

  Прямо в описании машины — но ТОЛЬКО в приватной зоне:

    network_interface {
      # ...
      dns_record {
        fqdn        = "${var.project_name}-web.${yandex_dns_zone.internal.zone}"
        dns_zone_id = yandex_dns_zone.internal.id
        ttl         = 300
        ptr         = false
      }
    }

  Две ошибки, которые здесь гарантированно случаются:

    Попытка указать публичную зону в dns_record:

      Error: ... dns_record_specs[0].dns_zone_id:
      DNS Zone (dns88v0ns14lofbd4inv) has no private_visibility

    Попытка включить обратную запись в приватной зоне:

      Error: ... Auto PTR records are currently not supported
      for private DNS Zones, but got a private-only DNS Zone

  Логика понятна: запись в описании машины создаётся для её ВНУТРЕННЕГО
  адреса, а внутренние адреса в публичном DNS не публикуют и обратных
  записей для них не бывает.

ЧТО ПОЛУЧИЛОСЬ В НАШЕМ ЗАПУСКЕ

  yc dns zone list-records --id dns0q36d560b5ijdkprt

  | NAME                           | TTL  | TYPE | DATA                          |
  | health.tf-course.example.com.  | 60   | TXT  | ok:created-by-terraform       |
  | service.tf-course.example.com. | 300  | A    | 84.252.135.180                |
  | tf-course.example.com.         | 3600 | NS   | ns1.yandexcloud.net.          |
  | tf-course.example.com.         | 3600 | SOA  | ns1.yandexcloud.net. ...      |

  Записи NS и SOA создались сами вместе с зоной. NS-серверы — те самые,
  которые нужно прописать у регистратора, чтобы зона начала работать
  в интернете.

  Полезно знать: команда dig сработает только после делегации домена.
  Пока делегации нет, записи проверяют через yc или изнутри машин —
  приватную зону видят только машины её сети:

    # на машине
    dig +short tf-net-p5-web.tf-net-p5.internal.

6. CLOUD-INIT И СЛУЖБА МЕТАДАННЫХ: ЕЩЁ ОДНА НАХОДКА
------------------------------------------------------------------

В практике 4 мы выяснили, что адрес машины берётся из службы метаданных
по пути computeMetadata/v1 и с заголовком Metadata-Flavor: Google.
Здесь добавим ещё две вещи.

ПЕРВОЕ: посмотреть, какие ключи вообще есть. Не надо угадывать —
служба сама отдаёт список:

  curl -s -H "Metadata-Flavor: Google" \
    http://169.254.169.254/computeMetadata/v1/instance/

  attributes/
  description
  disks/
  hostname
  id
  maintenance-event
  name
  network-interfaces/
  service-accounts/
  tags
  vendor/
  virtual-clock/
  zone

ВТОРОЕ: идентификатор подсети лежит в ключе с именем network. Ключа
subnet-id не существует, и запрос по нему возвращает «Not Found» —
мы получили это на живом стенде:

  curl -s -H "Metadata-Flavor: Google" \
    http://169.254.169.254/computeMetadata/v1/instance/network-interfaces/0/

  access-configs/
  forwarded-ips/
  ip
  mac
  network              <- идентификатор подсети
  target-instance-ips

  curl -s -H "Metadata-Flavor: Google" \
    http://169.254.169.254/computeMetadata/v1/instance/network-interfaces/0/network
  fl8scj6sgtvq4ftpj82d

Значение ключа zone приходит в виде полного пути
(projects/<cloud>/zones/ru-central1-d), поэтому в скрипте мы обрезаем
его до имени зоны: ${ZONE##*/}.

Мораль: не угадывайте пути службы метаданных, а спрашивайте список.
Ошибка в пути не ломает машину — просто в странице появится «Not Found»,
и искать причину придётся долго.

ЧАСТЬ 2. ПРОДОЛЖЕНИЕ: ПРИКЛАДНОЙ БАЛАНСИРОВЩИК

------------------------------------------------------------------
7. ЧЕМ ALB ОТЛИЧАЕТСЯ ОТ NLB
------------------------------------------------------------------

  СЕТЕВОЙ БАЛАНСИРОВЩИК (NLB, практика 4) работает на четвёртом
  уровне: распределяет TCP-соединения по машинам. Он не понимает
  HTTP: не умеет маршрутизировать по путям и заголовкам, не умеет
  терминировать TLS, не умеет менять заголовки.

  ПРИКЛАДНОЙ БАЛАНСИРОВЩИК (ALB) работает на седьмом уровне: понимает
  HTTP. Умеет отправлять /api на одну группу бэкендов, а /images
  на другую, проверять сертификаты, перенаправлять HTTP на HTTPS,
  ограничивать частоту запросов, добавлять заголовки.

ЧТО ВЫБРАТЬ: если приложение — обычный HTTP-сервис, нужен ALB.
NLB берут для не-HTTP трафика (базы данных, MQTT, gRPC без
HTTP-обвязки) или когда нужна минимальная задержка.

------------------------------------------------------------------
8. ИЗ ЧЕГО СОСТОИТ ALB В TERRAFORM
------------------------------------------------------------------

Пять ресурсов, и их постоянно путают. Разберём по порядку.

  ЦЕЛЕВАЯ ГРУППА — кто принимает трафик:

    resource "yandex_alb_target_group" "web" {
      name = "${var.project_name}-alb-tg"

      target {
        ip_address = yandex_compute_instance.web.network_interface[0].ip_address
        subnet_id  = yandex_compute_instance.web.network_interface[0].subnet_id
      }
    }

  ГРУППА БЭКЕНДОВ — как обращаться к целям и как их проверять:

    resource "yandex_alb_backend_group" "web" {
      name = "${var.project_name}-alb-bg"

      http_backend {
        name = "web-backend"
        port = 80

        target_group_ids = [yandex_alb_target_group.web[0].id]

        healthcheck {
          timeout  = "1s"
          interval = "2s"

          healthy_threshold   = 2
          unhealthy_threshold = 2

          http_healthcheck {
            path = "/"
          }
        }
      }
    }

  Обратите внимание: интервалы здесь СТРОКИ с единицами измерения
  ("2s", "500ms"), а не числа, как у группы машин. Это разные ресурсы
  и разные схемы, и путаница между ними — обычное дело.

  HTTP-РОУТЕР — правила маршрутизации:

    resource "yandex_alb_http_router" "web" {
      name = "${var.project_name}-alb-router"
    }

  ВИРТУАЛЬНЫЙ ХОСТ — привязка имён, правил и бэкендов:

    resource "yandex_alb_virtual_host" "web" {
      name           = "${var.project_name}-alb-vh"
      http_router_id = yandex_alb_http_router.web[0].id

      authority = ["*"]

      route {
        name = "main"

        http_route {
          http_route_action {
            backend_group_id = yandex_alb_backend_group.web[0].id
          }
        }
      }
    }

  Здесь же описывают маршрутизацию по путям: несколько блоков route
  с http_match { path { prefix = "/api" } } и своими бэкендами.

  САМ БАЛАНСИРОВЩИК — слушатели, зоны, группы безопасности:

    resource "yandex_alb_load_balancer" "web" {
      name               = "${var.project_name}-alb"
      network_id         = yandex_vpc_network.this.id
      security_group_ids = [yandex_vpc_security_group.alb[0].id]

      allocation_policy {
        location {
          zone_id   = var.zone
          subnet_id = yandex_vpc_subnet.this["web-d"].id
        }
      }

      listener {
        name = "http"

        endpoint {
          address {
            external_ipv4_address {}
          }
          ports = [80]
        }

        http {
          handler {
            http_router_id = yandex_alb_http_router.web[0].id
          }
        }
      }
    }

  ДВА ВАЖНЫХ МОМЕНТА ПРО СЛУШАТЕЛЬ

    Тип адреса указывается явно. Пустой блок address {} облако
    не принимает:

      Error: Either external ipv4 address or internal ipv4 address
      or external ipv6 address should be specified for the HTTP route

    публичный адрес сам». Если адрес нужно закрепить:

      external_ipv4_address {
        address = yandex_vpc_address.alb.external_ipv4_address[0].address
      }

      yandex_alb_load_balancer.web[0]: Still creating... [06m30s elapsed]
      yandex_alb_load_balancer.web[0]: Creation complete after 6m45s

10. HTTPS И СЕРТИФИКАТ: ЧТО НУЖНО ДОБАВИТЬ
------------------------------------------------------------------

Для HTTPS в ALB нужно три вещи: домен, сертификат и слушатель
с сертификатом. Сертификат Let's Encrypt выпускается в Certificate
Manager и подтверждается через DNS-запись в вашей зоне:

  resource "yandex_cm_certificate" "this" {
    name    = "${var.project_name}-cert"
    domains = ["www.${trimsuffix(var.dns_zone, ".")}"]

    managed {
      challenge_type = "DNS_CNAME"
    }
  }

  # Запись для подтверждения владения доменом создаётся облаком,
  # её нужно перенести в свою DNS-зону:
  resource "yandex_dns_recordset" "cert_challenge" {
    for_each = {
      for ch in yandex_cm_certificate.this.challenges :
      ch.domain => ch
    }

    zone_id = yandex_dns_zone.public.id
    name    = each.value.dns_name
    type    = each.value.dns_type
    ttl     = 600
    data    = [each.value.dns_value]
  }

Затем сертификат подключается к слушателю:

  listener {
    name = "https"

    endpoint {
      address {
        external_ipv4_address {}
      }
      ports = [443]
    }

    tls {
      default_handler {
        certificate_ids = [yandex_cm_certificate.this.id]

        http_handler {
          http_router_id = yandex_alb_http_router.web[0].id
        }
      }
    }
  }

# И перенаправление с HTTP на HTTPS — одной строкой в слушателе порта 80:
#
#   http {
#     handler {
#       http_router_id        = yandex_alb_http_router.web[0].id
#       redirect_http_to_https = true
#     }
#   }

Без делегированного домена этот код не проверить: сертификат останется
в состоянии валидации, а HTTPS не заработает. Поэтому в курсе он дан
как упражнение — и обязательно с проверкой, что домен вам действительно
принадлежит.

11. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

  СИМПТОМ: Error: Invalid index — «The given key does not identify an
  element in this collection value: the collection has no elements»
  ПРИЧИНА: обращение по индексу [0] к пустому списку. У нас так было
  с адресом балансировщика: пока он не создан, адреса нет.
  ЧТО ДЕЛАТЬ: обернуть выражение в try() и вернуть null либо собрать
  значение через one().

  СИМПТОМ: Error: Invalid template interpolation value — «The expression
  result is null. Cannot include a null value in a string template»
  ПРИЧИНА: подстановка null в строку. Возникает в выводах, которые
  собирают команды.
  ЧТО ДЕЛАТЬ: проверять на null явно:

    local.alb_address == null ? "ещё не создан" : "curl -s http://${local.alb_address}/"

  СИМПТОМ: Either external ipv4 address or internal ipv4 address or
  external ipv6 address should be specified for the HTTP route
  ПРИЧИНА: в слушателе ALB указан пустой блок address {}.
  ЧТО ДЕЛАТЬ: явно указать тип адреса — external_ipv4_address {}

  СИМПТОМ: DNS Zone has no private_visibility
  ПРИЧИНА: блок dns_record у машины ссылается на публичную зону.
  ЧТО ДЕЛАТЬ: для записей машин создавать приватную зону
  (public = false + private_networks), а публичные имена заводить
  ресурсом yandex_dns_recordset.

  СИМПТОМ: Auto PTR records are currently not supported for private
  DNS Zones
  ПРИЧИНА: ptr = true в приватной зоне.
  ЧТО ДЕЛАТЬ: ptr = false.

  СИМПТОМ: Public Zone "example.com." is occupied
  ПРИЧИНА: зона для этого домена уже создана — своя же, оставшаяся
  от предыдущего запуска, или чужая, если домен общий на команду.
  Зона уникальна в пределах облака.
  ЧТО ДЕЛАТЬ: найти существующую зону (yc dns zone list) и переиспользовать
  её через источник данных, либо удалить лишнюю.

  СИМПТОМ: страница отдаёт «Not Found» вместо значений метаданных
  ПРИЧИНА: неверный путь в службе метаданных (например, subnet-id
  вместо network).
  ЧТО ДЕЛАТЬ: запросить список ключей (см. раздел 6).

  СИМПТОМ: балансировщик создан, но отвечает ошибкой 503
  ПРИЧИНА: цели не проходят проверку здоровья. Чаще всего: сервис
  не слушает порт, или группа безопасности машины не пускает
  балансировщик.
  ЧТО ДЕЛАТЬ: посмотреть состояние цели:
  yc alb target-group list, проверить healthcheck бэкенда и правила
  группы безопасности (порт должен быть открыт для подсети, из которой
  приходит балансировщик).

  СИМПТОМ: terraform destroy «висит» на балансировщике
  ПРИЧИНА: ALB удаляется несколько минут; это не ошибка.
  ЧТО ДЕЛАТЬ: подождать. В конвейере для таких операций ставят
  увеличенный таймаут.

------------------------------------------------------------------

  1. Подсети. Добавьте подсеть в зону ru-central1-e и убедитесь, что
     список зон в выводе zones_covered изменился. Машину в новой
     подсети создавать не нужно — объясните, почему её там нельзя
     создать, пока адрес не выдан в этой зоне.

  2. Правила. Закройте SSH отовсюду и оставьте доступ только с вашего
     адреса. Проверьте: подключение должно работать, а после смены
     адреса в правиле на заведомо чужой — перестать.

  3. Правило по группе. Добавьте вторую машину в группу web и убедитесь,
     что она автоматически получила доступ к внутреннему сервису —
     без правки правил.

  4. Статический адрес. Создайте второй статический адрес и привяжите
     его к машине. Затем удалите машину из конфигурации и убедитесь,
     что адрес остался. Объясните, что теперь надо сделать руками.

  5. Приватная зона. Добейтесь, чтобы машина разрешала своё внутреннее
     имя через приватную зону. Проверьте командой dig на самой машине.

  6. Маршрутизация в ALB. Добавьте второе правило: запросы по пути
     /health должны отдавать простой ответ 200. Подсказка: понадобится
     отдельный виртуальный хост или отдельный маршрут с http_match,
     а проще всего — отдельный бэкенд со своей страницей.

  7. HTTPS. Если у вас есть домен: делегируйте его облаку, выпустите
     сертификат, включите слушатель на 443 и редирект с 80 на 443.
     Если домена нет — объясните словами, какие NS-серверы нужно
     прописать у регистратора и почему без этого HTTPS не заработает.
