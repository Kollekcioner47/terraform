ПРАКТИКА 5. СЕТИ: ПОДСЕТИ, ГРУППЫ БЕЗОПАСНОСТИ, DNS, БАЛАНСИРОВЩИК

Продолжительность: 2 академических часа.
Провайдер: yandex-cloud/yandex. Практика выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ПРАКТИКИ

  Вы соберёте сеть из трёх подсетей в трёх зонах доступности,
  замените «разрешить всё» на свои группы безопасности с правилами
  по ссылкам, закрепите за веб-сервером постоянный публичный адрес,
  заведёте публичную и приватную зоны DNS и поставите перед сервером
  прикладной балансировщик, который понимает HTTP.

ЧТО НУЖНО ЗАРАНЕЕ

  * Доступ в облако (практика 1) и понимание состояния (практика 2).
  * Опыт практики 4: NAT-шлюз, cloud-init и проверки здоровья —
    здесь они используются теми же приёмами.

ПРО ДОМЕН

  Для части про сертификаты и HTTPS нужен домен, которым вы владеете:
  сертификат Let's Encrypt в Certificate Manager выпускается только
  после подтверждения владения доменом. В этой практике мы разбираем
  ALB по HTTP, а выпуск сертификата и HTTPS описаны в конце как
  упражнение: без делегированного домена их не проверить.

------------------------------------------------------------------
0. КАТАЛОГ ПРОЕКТА И ФАЙЛЫ
------------------------------------------------------------------

Правило, которое нарушают чаще всего: ОДИН ПРОЕКТ — ОДИН
КАТАЛОГ. Terraform работает с состоянием в пределах каталога,
поэтому файлы разных проектов в одной папке перемешают ресурсы
и состояние.

Создаём каталог практики:

  mkdir -p ~/terraform-course/work/05-networking
  cd ~/terraform-course/work/05-networking

Здесь ~/terraform-course — клон репозитория с материалами курса.
Каталог work/ внутрь репозитория не попадает: он перечислен
в .gitignore, чтобы ваши эксперименты не смешивались
с материалами курса.

СТРУКТУРА ПРОЕКТА

  05-networking/
  ├── address.tf
  ├── alb.tf
  ├── cloud-init/
  │   └── web.yaml
  ├── dns.tf
  ├── locals.tf

КАК СОЗДАЁМ ФАЙЛЫ

  Файлы можно набрать по тексту практики. Конструкция
  cat > имя-файла <<'EOF' записывает в файл всё, что введено до
  строки EOF, поэтому такой блок можно скопировать в терминал
  целиком. Строки cat и EOF стоят в первом столбце: отступ сломал
  бы завершение ввода.

  Готовые файлы практики лежат в материалах курса — их можно
  взять вместо набора по тексту:

  cp -r ~/terraform-course/files/05_networking/. .

cat > locals.tf <<'EOF'
# Локальные значения практики 5.

locals {
  # Адрес прикладного балансировщика.
  #
  # Достать его непросто: listener — список, внутри endpoint — список,
  # внутри address — список, и только внутри него external_ipv4_address
  # с самим адресом. Вложенность объясняется тем, что слушателей,
  # точек входа и адресов может быть несколько.
  #
  # Вторая сложность: пока балансировщик ещё не создан, адреса нет
  # вовсе, и обращение по индексу [0] к пустому списку даёт ошибку:
  #
  #   Error: Invalid index
  #   The given key does not identify an element in this collection value:
  #   the collection has no elements.
  #
  # Поэтому выражение обёрнуто в try(): если вычислить не удалось,
  # вывод равен null, а не ошибке. Так план проходит и до создания
  # балансировщика, и после него.
  alb_address = var.create_alb ? try(
    one([
      for endpoint in yandex_alb_load_balancer.web[0].listener[0].endpoint :
      one(endpoint.address).external_ipv4_address[0].address
    ]),
    null
  ) : null

  # Что открыто наружу на веб-серверах — для вывода и для проверок.
  public_ports = sort(var.web_ports)

  # Карта «зона -> имя подсети»: помогает понять, какие зоны покрыты.
  zone_to_subnet = { for name, s in var.subnets : s.zone => name }
}
EOF

cat > address.tf <<'EOF'
# Статический публичный адрес.
#
# Проблема, которую он решает: динамический адрес живёт, пока машина
# работает. В практике 1 мы это увидели своими глазами — после
# изменения размеров машина перезапустилась, и внешний адрес сменился
# со 158.160.197.131 на 158.160.195.62. Для веб-сервера, на который
# смотрят записи DNS и правила файрвола клиентов, это недопустимо.
#
# Статический адрес — отдельный ресурс. Он существует независимо
# от машины: машину можно удалить и создать заново, адрес останется.
# За закреплённый адрес берут плату, поэтому неиспользуемые адреса
# надо освобождать.

resource "yandex_vpc_address" "web" {
  name = "${var.project_name}-web-ip"

  external_ipv4_address {
    zone_id = var.zone

    # Защита от DDoS подключается здесь же:
    # ddos_protection_provider = "qrator"
  }

  labels = {
    course = "terraform"
    lesson = "5"
  }
}
EOF

Переменные практики собраны в variables.tf. Главное в нём — карта
subnets: подсети заданы данными, а не кодом, поэтому новую зону
можно добавить одной записью, не переписывая ресурсы. Целостность
значений стерегут два блока validation: имя зоны DNS обязано
оканчиваться точкой, а список подсетей не может быть пустым.

  description = "Путь к авторизованному ключу сервисного аккаунта"

variable "ssh_public_key" {
  type        = string
  description = "Путь к публичному SSH-ключу"
}

variable "project_name" {
  type        = string
  description = "Префикс в именах ресурсов"

variable "image_family" {

------------------------------------------------------------------
1. ЗОНАЛЬНЫЕ И ГЛОБАЛЬНЫЕ РЕСУРСЫ
------------------------------------------------------------------

Первое, что нужно усвоить про сети в облаке: ресурсы делятся на два
вида.

  ГЛОБАЛЬНЫЕ — не привязаны к зоне доступности. Облачная сеть,
  бакет Object Storage, DNS-зона, реестр образов.

  ЗОНАЛЬНЫЕ — существуют внутри одной зоны. Подсеть, машина, диск,
  статический адрес, кластер managed-базы.

Из этого следуют практические выводы:

  * ОДНА СЕТЬ — МНОГО ПОДСЕТЕЙ. Сеть создаётся один раз, подсети —
    по одной на каждую зону, в которой планируются ресурсы.
  * ЗОНАЛЬНЫЙ РЕСУРС НЕЛЬЗЯ ПЕРЕНЕСТИ В ДРУГУЮ ЗОНУ. Подсеть из зоны
    ru-central1-a в зону ru-central1-b не переезжает: её можно только
    создать заново, а машины — пересоздать.
  * ЗОНЫ ДОСТУПНОСТИ В ОБЛАКЕ И ВАШИ ПОДСЕТИ — РАЗНЫЕ СПИСКИ.
    Посмотреть зоны облака:

      yc compute zone list

    В Яндекс Облаке сейчас доступны ru-central1-a, -b, -d (рекомендуемая
    для новых проектов), -e, а также -m для baremetal. При этом подсети
    у нас будут только в трёх зонах из пяти: в остальных машину создать
    нельзя, потому что нет подсети.

  ИСПРАВЛЕНО. В прежней версии курса встречалась зона ru-central1-c.
  Такой зоны больше не существует.

  Наша сеть описывается так:

    resource "yandex_vpc_network" "this" {
      name = "${var.project_name}-net"
    }

    resource "yandex_vpc_subnet" "this" {
      for_each = var.subnets

      name           = "${var.project_name}-${each.key}"
      zone           = each.value.zone
      network_id     = yandex_vpc_network.this.id
      v4_cidr_blocks = [each.value.cidr]

      route_table_id = var.enable_nat_gateway ? yandex_vpc_route_table.nat[0].id : null
    }

  Диапазоны подсетей выбираются так, чтобы в будущем их можно было
  объединить в одну маршрутизируемую сеть. Мы используем 10.70.10.0/24,
  10.70.20.0/24 и 10.70.30.0/24 — это три подсети внутри одного
  диапазона 10.70.0.0/16.

Всё, что описано выше, лежит в одном файле network.tf: облачная
сеть и подсети во всех трёх зонах. В нём же NAT-шлюз и таблица
маршрутизации — о них следующий раздел.

cat > network.tf <<'EOF'
# Сеть, подсети в трёх зонах и выход в интернет.
#
# Разбираем три вещи, которые в учебных конфигурациях обычно
# пропускают: зональность ресурсов, маршрутизацию и разницу между
# «подсеть по умолчанию» и своей подсетью.

resource "yandex_vpc_network" "this" {
  name        = "${var.project_name}-net"
  description = "Учебная сеть курса Terraform, практика 5"

  labels = {
    course = "terraform"
    lesson = "5"
  }
}

# Подсети в разных зонах.
#
# Обратите внимание: одна сеть — много подсетей. Сеть глобальная
# (не привязана к зоне), подсеть зональная. Машина может находиться
# только в подсети своей зоны.
resource "yandex_vpc_subnet" "this" {
  for_each = var.subnets

  name = "${var.project_name}-${each.key}"
  zone = each.value.zone

  network_id     = yandex_vpc_network.this.id
  v4_cidr_blocks = [each.value.cidr]

  # Таблица маршрутизации появится ниже; ссылка на неё нужна, чтобы
  # машины без публичных адресов могли ходить в интернет.
  route_table_id = var.enable_nat_gateway ? yandex_vpc_route_table.nat[0].id : null

  labels = {
    course = "terraform"
    lesson = "5"
    zone   = each.value.zone
  }
}

# NAT-шлюз: выход в интернет для машин без публичных адресов.
#
# Подробно разобран в практике 4 — там без него не работала группа
# машин. Здесь он нужен по той же причине: веб-серверы мы ставим
# за балансировщик и публичных адресов им не выдаём.
resource "yandex_vpc_gateway" "nat" {
  count = var.enable_nat_gateway ? 1 : 0

  name = "${var.project_name}-nat"
  shared_egress_gateway {}
}

# Таблица маршрутизации: «весь трафик не в свою сеть — через шлюз».
#
# Таблица создаётся одна на сеть, а подключается к подсетям.
# Если таблицу не подключить, шлюз не заработает: машины просто
# не будут знать, куда отправлять пакеты наружу.
resource "yandex_vpc_route_table" "nat" {
  count = var.enable_nat_gateway ? 1 : 0

  name       = "${var.project_name}-rt"
  network_id = yandex_vpc_network.this.id

  static_route {
    destination_prefix = "0.0.0.0/0"
    gateway_id         = yandex_vpc_gateway.nat[0].id
  }

  labels = {
    course = "terraform"
    lesson = "5"
  }
}

# ПРОВЕРКА ЗОНАЛЬНОСТИ
#
# Полезное наблюдение для самостоятельной работы: список зон облака
# и список ваших подсетей — разные вещи. Посмотреть, какие зоны
# доступны в облаке:
#
#   yc compute zone list
#
# А теперь сравните с тем, что создали мы: подсети есть в зонах a, b
# и d, а зоны e и m остались без подсетей. Машину в зоне без подсети
# создать нельзя — облако ответит ошибкой, что подсеть не найдена.
#
# Именно поэтому подсети создают заранее, по одной на каждую зону,
# в которой планируется размещать ресурсы.
EOF

------------------------------------------------------------------
2. NAT-ШЛЮЗ И ТАБЛИЦА МАРШРУТИЗАЦИИ
------------------------------------------------------------------

Разобрано в практике 4, здесь только напоминание: машина без
публичного адреса не имеет выхода в интернет, пока в сети нет
NAT-шлюза и таблицы маршрутизации, а подсети не ссылаются на эту
таблицу.

  resource "yandex_vpc_gateway" "nat" {
    count = var.enable_nat_gateway ? 1 : 0
    name  = "${var.project_name}-nat"
    shared_egress_gateway {}
  }

  resource "yandex_vpc_route_table" "nat" {
    count      = var.enable_nat_gateway ? 1 : 0
    name       = "${var.project_name}-rt"
    network_id = yandex_vpc_network.this.id

    static_route {
      destination_prefix = "0.0.0.0/0"
      gateway_id         = yandex_vpc_gateway.nat[0].id
    }
  }

Почему таблица отдельный ресурс: одна таблица может обслуживать
несколько подсетей, а в одной сети их может быть несколько — например,
одна для доступа в интернет, вторая для доступа к корпоративной сети
через VPN.

------------------------------------------------------------------
3. СВОИ ГРУППЫ БЕЗОПАСНОСТИ
------------------------------------------------------------------

До этой практики мы пользовались группой безопасности, которую создал
модуль. Теперь разберём, как их описывают всерьёз.

Весь security.tf приведён здесь целиком, а дальше разобран
по частям: так видно и связи между ресурсами, и то, как правило
ссылается на другую группу. В файле три группы безопасности —
web, internal и alb — и правила к ним.

cat > security.tf <<'EOF'
# Группы безопасности: правила отдельными ресурсами.
#
# Разбираем два подхода к описанию правил:
#
#  1. Вложенные блоки ingress/egress внутри группы безопасности.
#     Компактно, но при изменении одного правила Terraform пересоздаёт
#     блок целиком, и в истории изменений это выглядит как правка
#     всей группы.
#
#  2. Отдельные ресурсы yandex_vpc_security_group_rule.
#     Правила видны поштучно, их можно добавлять и удалять
#     независимо, а в плане видно, какое именно правило меняется.
#
# Здесь используем второй подход: он ближе к рабочей практике.

# Группа безопасности веб-серверов.
resource "yandex_vpc_security_group" "web" {
  name        = "${var.project_name}-web-sg"
  description = "Доступ к веб-серверам из интернета"
  network_id  = yandex_vpc_network.this.id

  labels = {
    course = "terraform"
    lesson = "5"
    role   = "web"
  }
}

# Веб-порты из интернета.
resource "yandex_vpc_security_group_rule" "web_public" {
  for_each = toset([for p in var.web_ports : tostring(p)])

  security_group_binding = yandex_vpc_security_group.web.id
  direction              = "ingress"
  description            = "Порт ${each.value} для клиентов"

  protocol       = "TCP"
  port           = tonumber(each.value)
  v4_cidr_blocks = ["0.0.0.0/0"]
}

# SSH. В учебной конфигурации открыт всем, в рабочей — только
# адресам офиса или через бастион:
#
#   v4_cidr_blocks = ["203.0.113.10/32"]
#
# Оставлять 0.0.0.0/0 на 22-й порт в рабочей среде недопустимо:
# перебор паролей и попытки подбора ключей начинаются в первые часы.
resource "yandex_vpc_security_group_rule" "web_ssh" {
  security_group_binding = yandex_vpc_security_group.web.id
  direction              = "ingress"
  description            = "SSH для администратора (на учебном стенде — отовсюду)"

  protocol       = "TCP"
  port           = 22
  v4_cidr_blocks = ["0.0.0.0/0"]
}

# Исходящий трафик: разрешён полностью (см. практику 4 — иначе
# cloud-init не сможет установить пакеты).
resource "yandex_vpc_security_group_rule" "web_egress" {
  security_group_binding = yandex_vpc_security_group.web.id
  direction              = "egress"
  description            = "Исходящий трафик"

  protocol       = "ANY"
  from_port      = 0
  to_port        = 65535
  v4_cidr_blocks = ["0.0.0.0/0"]
}

# Группа безопасности внутренних сервисов.
#
# Правило «откуда» задаётся не адресами, а ССЫЛКОЙ НА ДРУГУЮ ГРУППУ
# БЕЗОПАСНОСТИ. Это важный приём: адреса в облаке меняются (машины
# пересоздаются, подсети расширяются), а группы остаются.
#
# Так описывают доступ «приложение -> база данных», не перечисляя
# адреса приложений.
resource "yandex_vpc_security_group" "internal" {
  name        = "${var.project_name}-internal-sg"
  description = "Доступ к внутренним сервисам только с веб-серверов"
  network_id  = yandex_vpc_network.this.id

  labels = {
    course = "terraform"
    lesson = "5"
    role   = "internal"
  }
}

resource "yandex_vpc_security_group_rule" "internal_from_web" {
  security_group_binding = yandex_vpc_security_group.internal.id
  direction              = "ingress"
  description            = "Трафик от машин группы web"

  protocol = "TCP"
  port     = 8080

  # Источник — идентификатор другой группы безопасности.
  security_group_id = yandex_vpc_security_group.web.id
}

resource "yandex_vpc_security_group_rule" "internal_egress" {
  security_group_binding = yandex_vpc_security_group.internal.id
  direction              = "egress"
  description            = "Исходящий трафик"

  protocol       = "ANY"
  from_port      = 0
  to_port        = 65535
  v4_cidr_blocks = ["0.0.0.0/0"]
}

# Группа безопасности прикладного балансировщика.
#
# Балансировщику нужна своя группа: он принимает клиентский трафик
# из интернета и сам обращается к машинам за проверкой здоровья.
resource "yandex_vpc_security_group" "alb" {
  count = var.create_alb ? 1 : 0

  name        = "${var.project_name}-alb-sg"
  description = "Группа безопасности прикладного балансировщика"

  labels = {
    course = "terraform"
    lesson = "5"
    role   = "alb"
  }
}

resource "yandex_vpc_security_group_rule" "alb_public" {
  for_each = var.create_alb ? toset(["80"]) : toset([])

  security_group_binding = yandex_vpc_security_group.alb[0].id
  direction              = "ingress"

  protocol       = "TCP"

}

resource "yandex_vpc_security_group_rule" "alb_egress" {
  count = var.create_alb ? 1 : 0

  security_group_binding = yandex_vpc_security_group.alb[0].id
  direction              = "egress"
  description            = "Обращения к машинам и служебный трафик"

  protocol       = "ANY"
  from_port      = 0
  to_port        = 65535
  v4_cidr_blocks = ["0.0.0.0/0"]

EOF

ДВА СПОСОБА ОПИСАНИЯ ПРАВИЛ

  Вложенные блоки внутри группы:

    resource "yandex_vpc_security_group" "web" {
      name       = "web-sg"
      network_id = yandex_vpc_network.this.id

      ingress {
        protocol       = "TCP"
        port           = 80
        v4_cidr_blocks = ["0.0.0.0/0"]
      }
    }

  Отдельные ресурсы правил:

    resource "yandex_vpc_security_group" "web" {
      name       = "${var.project_name}-web-sg"
      network_id = yandex_vpc_network.this.id
    }

    resource "yandex_vpc_security_group_rule" "web_public" {
      security_group_binding = yandex_vpc_security_group.web.id
      direction              = "ingress"
      protocol               = "TCP"
      port                   = 80
      v4_cidr_blocks         = ["0.0.0.0/0"]
    }

  В курсе мы используем второй способ, и вот почему: правила видны
  поштучно. В плане и в истории изменений понятно, какое именно
  правило добавлено или изменено, а порядок правил не влияет на
  результат. При первом способе Terraform управляет блоком целиком.

  Обратите внимание на имя аргумента: security_group_binding. Именно
  так в текущей версии провайдера указывается группа, к которой
  привязывается правило.

ПРАВИЛО ПО ССЫЛКЕ НА ДРУГУЮ ГРУППУ

  Самое полезное свойство групп безопасности — возможность указать
  источником не адреса, а другую группу:

    resource "yandex_vpc_security_group_rule" "internal_from_web" {
      security_group_binding = yandex_vpc_security_group.internal.id
      direction              = "ingress"
      protocol               = "TCP"
      port                   = 8080

      # Источник — идентификатор другой группы безопасности.
      security_group_id = yandex_vpc_security_group.web.id
    }

  Читается так: «на 8080-й порт внутренних сервисов пускать машины
  из группы web». Адреса машин при этом не перечисляются, и это
  принципиально: машины пересоздаются, адреса меняются, а группа
  остаётся. Именно так описывают доступ «приложение → база данных».

ПРО ПОРТ 22

  В учебной конфигурации SSH открыт всему интернету — иначе
  подключиться с произвольного адреса не получится. В рабочей среде так
  делать нельзя: попытки подбора ключей начинаются в первые часы после
  появления машины с открытым 22-м портом. Правильно — ограничить
  адресами офиса или пускать через бастион:

    v4_cidr_blocks = ["203.0.113.10/32"]

ПРО ИСХОДЯЩИЙ ТРАФИК

  Разобрано в практике 4: ограничение egress — самая частая причина
  «машина есть, а пакеты не ставятся». В учебной конфигурации исходящий
  трафик разрешён полностью.

4. СТАТИЧЕСКИЙ АДРЕС: ПРОВЕРКА НА ЖИВОМ СТЕНДЕ
------------------------------------------------------------------

Помните, как в практике 1 после изменения размеров машина
перезапустилась, и внешний адрес сменился? Вот что это значит на
практике: запись в DNS, правило файрвола у клиента и белый список
в чужой системе — всё это перестаёт работать. Для сервисов,
к которым обращаются извне, адрес закрепляют.

  resource "yandex_vpc_address" "web" {
    name = "${var.project_name}-web-ip"

    external_ipv4_address {
      zone_id = var.zone
    }
  }

Подключение к машине:

  network_interface {
    subnet_id      = yandex_vpc_subnet.this["web-d"].id
    nat            = true
    nat_ip_address = yandex_vpc_address.web.external_ipv4_address[0].address
    security_group_ids = [yandex_vpc_security_group.web.id]
  }

ПРОВЕРИМ, ЧТО АДРЕС ДЕЙСТВИТЕЛЬНО ПОСТОЯННЫЙ

  До пересоздания:

    terraform output -raw web_static_ip
    84.252.135.180

  Пересоздаём машину (заодно вспомним ключ -replace):

    terraform apply -replace=yandex_compute_instance.web

    yandex_compute_instance.web: Destroying... [id=fv4r9nibjf6mhnbv50ho]
    yandex_compute_instance.web: Creation complete after 38s [id=fv4tqcqeqfi4a1udqt3i]
    Apply complete! Resources: 1 added, 1 changed, 1 destroyed.

    web_private_ip = "10.70.30.15"
    web_static_ip  = "84.252.135.180"

  Внешний адрес не изменился, а внутренний сменился (был 10.70.30.18).
  Это и есть разница: публичный адрес закреплён за вами и живёт
  отдельно от машины, внутренний выдаётся в подсети при создании.

  За закреплённый адрес берут плату, и она выше, когда адрес
  не используется. Поэтому неиспользуемые адреса освобождают:
  terraform destroy удалит и адрес тоже.

------------------------------------------------------------------
5. DNS: ПУБЛИЧНАЯ И ПРИВАТНАЯ ЗОНЫ
------------------------------------------------------------------

В Яндекс Облаке есть два вида зон, и это разделение нужно понимать.

Весь dns.tf приведён здесь целиком, а дальше разобран по частям:
в файле обе зоны и две записи в публичной зоне — служебная
A-запись на закреплённый адрес и TXT для проверки, что зона
отвечает.

cat > dns.tf <<'EOF'
# DNS в облаке: две зоны, и это не случайность.
#
#   ПУБЛИЧНАЯ зона (public = true) отвечает на запросы из интернета.
#   Чтобы она действительно работала, домен нужно делегировать
#   облаку: у регистратора прописать NS-серверы зоны. Пока делегации
#   нет, зона существует, но интернет про неё не знает.
#
#   ПРИВАТНАЯ зона (public = false) видна только машинам указанных
#   сетей. Так решают внутренние имена сервисов, не выходя в интернет.
#
# Важное следствие, на котором легко споткнуться: блок dns_record
# в сетевом интерфейсе машины работает ТОЛЬКО с приватной зоной.
# Попытка указать публичную заканчивается ошибкой:
#
#   Error: ... primary_v4_address_spec.dns_record_specs[0].dns_zone_id:
#   DNS Zone (dns88v0...) has no private_visibility
#
# Логика понятна: запись создаётся для внутреннего адреса машины,
# а внутренние адреса в публичном DNS не публикуют.

# Публичная зона: внешние имена сервисов.
resource "yandex_dns_zone" "public" {
  name        = "${var.project_name}-public-zone"
  description = "Публичная зона для внешних имён"
  zone        = var.dns_zone
  public      = true

  labels = {
    course = "terraform"
    lesson = "5"
  }
}

# Приватная зона: внутренние имена машин.
resource "yandex_dns_zone" "internal" {
  name        = "${var.project_name}-internal-zone"
  description = "Внутренняя зона для имён машин"
  zone        = "${var.project_name}.internal."
  public      = false

  # Зона видна только машинам этой сети.
  private_networks = [yandex_vpc_network.this.id]

  labels = {
    course = "terraform"
    lesson = "5"
  }
}

# Публичная запись: имя сервиса указывает на закреплённый адрес.
#
# Запись создаётся ОТДЕЛЬНЫМ ресурсом, потому что адрес берётся
# не у машины, а у статического адреса. Такую запись можно направить
# на балансировщик, на несколько адресов сразу или на внешний сервис.
resource "yandex_dns_recordset" "service" {
  zone_id = yandex_dns_zone.public.id
  name    = "service.${var.dns_zone}"
  type    = "A"
  ttl     = 300

  data = [yandex_vpc_address.web.external_ipv4_address[0].address]
}

# Текстовая запись: удобна для проверки, что зона отвечает.
resource "yandex_dns_recordset" "health" {
  zone_id = yandex_dns_zone.public.id
  name    = "health.${var.dns_zone}"
  type    = "TXT"
  ttl     = 60

  data = ["ok:created-by-terraform"]
}
EOF

  ПУБЛИЧНАЯ ЗОНА (public = true) отвечает на запросы из интернета —
  но только после того, как домен делегирован облаку: у регистратора
  прописаны NS-серверы зоны. Создать зону можно для любого имени,
  облако не проверяет права на домен; работать она начнёт после
  делегации.

  ПРИВАТНАЯ ЗОНА (public = false) видна только машинам указанных
  сетей. Так решают внутренние имена сервисов.

    resource "yandex_dns_zone" "public" {
      name   = "${var.project_name}-public-zone"
      zone   = var.dns_zone
      public = true
    }

    resource "yandex_dns_zone" "internal" {
      name             = "${var.project_name}-internal-zone"
      zone             = "${var.project_name}.internal."
      public           = false
      private_networks = [yandex_vpc_network.this.id]
    }

ЗАПИСИ СОЗДАЮТСЯ ДВУМЯ СПОСОБАМИ

  Отдельным ресурсом — для любых имён и типов:

    resource "yandex_dns_recordset" "service" {
      zone_id = yandex_dns_zone.public.id
      name    = "service.${var.dns_zone}"
      type    = "A"
      ttl     = 300
      data    = [yandex_vpc_address.web.external_ipv4_address[0].address]
    }

  Прямо в описании машины — но ТОЛЬКО в приватной зоне:

    network_interface {
      # ...
      dns_record {
        fqdn        = "${var.project_name}-web.${yandex_dns_zone.internal.zone}"
        dns_zone_id = yandex_dns_zone.internal.id
        ttl         = 300
        ptr         = false
      }
    }

  Две ошибки, которые здесь гарантированно случаются:

    Попытка указать публичную зону в dns_record:

      Error: ... dns_record_specs[0].dns_zone_id:
      DNS Zone (dns88v0ns14lofbd4inv) has no private_visibility

    Попытка включить обратную запись в приватной зоне:

      Error: ... Auto PTR records are currently not supported
      for private DNS Zones, but got a private-only DNS Zone

  Логика понятна: запись в описании машины создаётся для её ВНУТРЕННЕГО
  адреса, а внутренние адреса в публичном DNS не публикуют и обратных
  записей для них не бывает.

ЧТО ПОЛУЧИЛОСЬ В НАШЕМ ЗАПУСКЕ

  yc dns zone list-records --id dns0q36d560b5ijdkprt

  | NAME                           | TTL  | TYPE | DATA                          |
  | health.tf-course.example.com.  | 60   | TXT  | ok:created-by-terraform       |
  | service.tf-course.example.com. | 300  | A    | 84.252.135.180                |
  | tf-course.example.com.         | 3600 | NS   | ns1.yandexcloud.net.          |
  | tf-course.example.com.         | 3600 | SOA  | ns1.yandexcloud.net. ...      |

  Записи NS и SOA создались сами вместе с зоной. NS-серверы — те самые,
  которые нужно прописать у регистратора, чтобы зона начала работать
  в интернете.

  Полезно знать: команда dig сработает только после делегации домена.
  Пока делегации нет, записи проверяют через yc или изнутри машин —
  приватную зону видят только машины её сети:

    # на машине
    dig +short tf-net-p5-web.tf-net-p5.internal.

6. CLOUD-INIT И СЛУЖБА МЕТАДАННЫХ: ЕЩЁ ОДНА НАХОДКА
------------------------------------------------------------------

В практике 4 мы выяснили, что адрес машины берётся из службы метаданных
по пути computeMetadata/v1 и с заголовком Metadata-Flavor: Google.
Здесь добавим ещё две вещи.

ПЕРВОЕ: посмотреть, какие ключи вообще есть. Не надо угадывать —
служба сама отдаёт список:

  curl -s -H "Metadata-Flavor: Google" \
    http://169.254.169.254/computeMetadata/v1/instance/

  Ожидаемый ответ:

  attributes/
  description
  disks/
  hostname
  id
  maintenance-event
  name
  network-interfaces/
  service-accounts/
  tags
  vendor/
  virtual-clock/
  zone

ВТОРОЕ: идентификатор подсети лежит в ключе с именем network. Ключа
subnet-id не существует, и запрос по нему возвращает «Not Found».
Это проверено на живом стенде:

  curl -s -H "Metadata-Flavor: Google" \
    http://169.254.169.254/computeMetadata/v1/instance/network-interfaces/0/

  Ожидаемый ответ:

  access-configs/
  forwarded-ips/
  ip
  mac
  network              <- идентификатор подсети
  target-instance-ips

  curl -s -H "Metadata-Flavor: Google" \
    http://169.254.169.254/computeMetadata/v1/instance/network-interfaces/0/network
  fl8scj6sgtvq4ftpj82d

Значение ключа zone приходит в виде полного пути
(projects/<cloud>/zones/ru-central1-d), поэтому в скрипте мы обрезаем
его до имени зоны: ${ZONE##*/}.

Мораль: не угадывайте пути службы метаданных, а спрашивайте список.
Ошибка в пути не ломает машину — просто в странице появится «Not Found»,
и искать причину придётся долго.


Начальная настройка машины живёт в отдельном файле, который
передаётся облаку как user-data. Сначала создадим каталог для
него:

  mkdir -p cloud-init

cat > cloud-init/web.yaml <<'EOF'
#cloud-config
# Начальная настройка веб-сервера.
#
# Формат и правила те же, что в практике 4: первая строка #cloud-config,
# отступы только пробелами, файл читается один раз при первой загрузке,
# ошибки видны только в журнале на самой машине.

package_update: true
package_upgrade: false

packages:
  - nginx

write_files:
  - path: /var/www/html/index.html
    owner: root:root
    permissions: "0644"
    content: |
      <!DOCTYPE html>
      <html lang="ru">
      <head>
        <meta charset="utf-8">
        <title>Практика 5: сети</title>
      </head>
      <body>
        <h1>Веб-сервер за прикладным балансировщиком</h1>
        <p>Адреса подставлены скриптом cloud-init из службы метаданных.</p>
      </body>
      </html>

runcmd:
  # Адреса берём из службы метаданных Яндекс Облака.
  # Заголовок Metadata-Flavor: Google обязателен, а путь отличается
  # от пути в AWS (подробно — в практике 4).
  - |
    META=http://169.254.169.254/computeMetadata/v1/instance

    EXTERNAL_IP=$(curl -s -H "Metadata-Flavor: Google" \
      "$META/network-interfaces/0/access-configs/0/external-ip")
    INTERNAL_IP=$(curl -s -H "Metadata-Flavor: Google" \
      "$META/network-interfaces/0/ip")
    HOSTNAME=$(curl -s -H "Metadata-Flavor: Google" "$META/hostname")
    ZONE=$(curl -s -H "Metadata-Flavor: Google" "$META/zone")

    # ВНИМАНИЕ: идентификатор подсети лежит в ключе с именем network.
    # Ключа subnet-id в службе метаданных нет, и запрос по нему
    # возвращает «Not Found» — мы это проверили на живом стенде.
    #
    # Посмотреть, какие ключи есть на самом деле, можно так:
    #   curl -s -H "Metadata-Flavor: Google" \
    #     http://169.254.169.254/computeMetadata/v1/instance/network-interfaces/0/
    SUBNET=$(curl -s -H "Metadata-Flavor: Google" \
      "$META/network-interfaces/0/network")

    {
      printf '<p>Внешний адрес: %s</p>\n' "$EXTERNAL_IP"
      printf '<p>Внутренний адрес: %s</p>\n' "$INTERNAL_IP"
      printf '<p>Имя машины: %s</p>\n' "$HOSTNAME"
      printf '<p>Зона доступности: %s</p>\n' "${ZONE##*/}"
      printf '<p>Подсеть: %s</p>\n' "$SUBNET"
    } >> /var/www/html/index.html

  - systemctl enable nginx
  - systemctl restart nginx

final_message: "Веб-сервер готов за $UPTIME секунд"
EOF

А вот сама машина: она читает этот файл, закрепляет за собой
статический адрес и заводит внутреннюю запись в приватной зоне
DNS.

cat > web-vm.tf <<'EOF'
# Веб-сервер со статическим адресом и записью в DNS.
#
# Машина одна, но описана так, как описывают машины за балансировщиком:
# группа безопасности своя, адрес закреплён, имя в DNS есть.

data "yandex_compute_image" "os" {
  family = var.image_family
}

resource "yandex_compute_instance" "web" {
  name        = "${var.project_name}-web"
  description = "Веб-сервер со статическим адресом"

  # Зона машины должна совпадать с зоной подсети — иначе облако
  # откажет в создании (эту ошибку мы разбирали в практике 3).
  zone        = var.zone
  platform_id = "standard-v3"

  allow_stopping_for_update = true

  resources {
    cores         = 2
    memory        = 2
    core_fraction = 20
  }

  scheduling_policy {
    preemptible = true
  }

  boot_disk {
    initialize_params {
      image_id = data.yandex_compute_image.os.id
      type     = "network-hdd"
      size     = 10
    }
  }

  network_interface {
    # Подсеть той же зоны, что и машина.
    subnet_id = yandex_vpc_subnet.this["web-d"].id

    nat = true

    # Вот он, статический адрес: вместо автоматически выданного
    # используем закреплённый за нами.
    nat_ip_address = yandex_vpc_address.web.external_ipv4_address[0].address

    security_group_ids = [yandex_vpc_security_group.web.id]

    # Внутренняя запись DNS создаётся прямо здесь: облако заведёт
    # A-запись с внутренним адресом машины в ПРИВАТНОЙ зоне.
    #
    # С публичной зоной этот блок не работает — облако отвечает
    # «DNS Zone has no private_visibility»: внутренние адреса машины
    # в публичном DNS не публикуют. Публичные имена мы заводим

    dns_record {
      fqdn        = "${var.project_name}-web.${yandex_dns_zone.internal.zone}"
      dns_zone_id = yandex_dns_zone.internal.id
      ttl         = 300

      # ptr = false обязателен для приватной зоны. Обратная запись
      # (PTR) для приватных зон в Яндекс Облаке не поддерживается:
      #
      #   Auto PTR records are currently not supported for private
      #   DNS Zones, but got a private-only DNS Zone
      ptr = false
    }
  }

  metadata = {
    ssh-keys  = "ubuntu:${file(var.ssh_public_key)}"
    user-data = file("${path.module}/cloud-init/web.yaml")
  }

  labels = {
    course = "terraform"
    lesson = "5"
    role   = "web"
  }

ЧАСТЬ 2. ПРОДОЛЖЕНИЕ: ПРИКЛАДНОЙ БАЛАНСИРОВЩИК
========================================================================

------------------------------------------------------------------
7. ЧЕМ ALB ОТЛИЧАЕТСЯ ОТ NLB
------------------------------------------------------------------

  СЕТЕВОЙ БАЛАНСИРОВЩИК (NLB, практика 4) работает на четвёртом
  уровне: распределяет TCP-соединения по машинам. Он не понимает
  HTTP: не умеет маршрутизировать по путям и заголовкам, не умеет
  терминировать TLS, не умеет менять заголовки.

  ПРИКЛАДНОЙ БАЛАНСИРОВЩИК (ALB) работает на седьмом уровне: понимает
  HTTP. Умеет отправлять /api на одну группу бэкендов, а /images
  на другую, проверять сертификаты, перенаправлять HTTP на HTTPS,
  ограничивать частоту запросов, добавлять заголовки.

ЧТО ВЫБРАТЬ: если приложение — обычный HTTP-сервис, нужен ALB.
NLB берут для не-HTTP трафика (базы данных, MQTT, gRPC без
HTTP-обвязки) или когда нужна минимальная задержка.

------------------------------------------------------------------
8. ИЗ ЧЕГО СОСТОИТ ALB В TERRAFORM
------------------------------------------------------------------

Пять ресурсов, и их постоянно путают. Разберём по порядку.

Весь alb.tf приведён здесь целиком, а дальше разобран по частям:
так видно и связи между ресурсами, и то, что создаются они только
при create_alb = true. Обратите внимание на count у каждого
ресурса — именно он делает балансировщик необязательным.

cat > alb.tf <<'EOF'
# Прикладной балансировщик (Application Load Balancer, L7).
#
# Чем отличается от сетевого (NLB) из практики 4:
#
#   NLB работает на четвёртом уровне: распределяет TCP-соединения,
#   ничего не знает про HTTP, не умеет маршрутизировать по путям
#   и заголовкам.
#
#   ALB работает на седьмом уровне: понимает HTTP, умеет отправлять
#   разные запросы на разные группы бэкендов (маршрутизация по пути
#   и по имени хоста), терминировать HTTPS, добавлять и менять
#   заголовки, ограничивать скорость запросов.
#
# Из чего состоит ALB в Terraform — четыре ресурса, и это важно
# запомнить, потому что их часто путают:
#
#   yandex_alb_target_group    кто принимает трафик (машины и их адреса)
#   yandex_alb_backend_group   как обращаться к машинам и как их проверять
#   yandex_alb_http_router     правила маршрутизации (роутер)
#   yandex_alb_virtual_host    привязка правил и бэкендов (виртуальный хост)
#
# Плюс сам yandex_alb_load_balancer: слушатели, зоны и группы
# безопасности.

resource "yandex_alb_target_group" "web" {
  count = var.create_alb ? 1 : 0

  name = "${var.project_name}-alb-tg"

  target {
    # Цель — наша машина. Адрес внутренний: балансировщик общается
    # с бэкендами внутри облака, наружу смотрит только он сам.
    ip_address = yandex_compute_instance.web.network_interface[0].ip_address
    subnet_id  = yandex_compute_instance.web.network_interface[0].subnet_id
  }

  labels = {
    course = "terraform"
    lesson = "5"
  }
}

resource "yandex_alb_backend_group" "web" {
  count = var.create_alb ? 1 : 0

  name = "${var.project_name}-alb-bg"

  http_backend {
    name = "web-backend"

    weight = 1
    port   = 80

    target_group_ids = [yandex_alb_target_group.web[0].id]

    # Проверка здоровья на стороне балансировщика. Интервалы
    # задаются строками с единицами измерения: "2s", "500ms".
    healthcheck {
      timeout  = "1s"
      interval = "2s"

      healthy_threshold   = 2
      unhealthy_threshold = 2

      http_healthcheck {
        path = "/"
      }
    }
  }
}

resource "yandex_alb_http_router" "web" {
  count = var.create_alb ? 1 : 0

  name = "${var.project_name}-alb-router"

  labels = {
    course = "terraform"
    lesson = "5"
  }
}

resource "yandex_alb_virtual_host" "web" {
  count = var.create_alb ? 1 : 0

  name           = "${var.project_name}-alb-vh"
  http_router_id = yandex_alb_http_router.web[0].id

  # По каким именам хоста отвечает этот виртуальный хост.
  # Пустой список означает «любое имя».
  authority = ["*"]

  route {
    name = "main"

    http_route {
      http_route_action {
        backend_group_id = yandex_alb_backend_group.web[0].id
      }
    }
  }
}

resource "yandex_alb_load_balancer" "web" {
  count = var.create_alb ? 1 : 0

  name = "${var.project_name}-alb"

  network_id = yandex_vpc_network.this.id

  security_group_ids = [yandex_vpc_security_group.alb[0].id]

  # Где размещается балансировщик. Каждый узел живёт в своей подсети,
  # поэтому для отказоустойчивости перечисляют несколько зон со своими
  # подсетями.
  allocation_policy {
    location {
      zone_id   = var.zone
      subnet_id = yandex_vpc_subnet.this["web-d"].id
    }
  }

  # Слушатель: что и на каком порту принимает балансировщик.
  listener {
    name = "http"

    endpoint {
      # Тип адреса надо указать явно. Пустой блок address {}
      # облако не принимает:
      #
      #   Error: Either external ipv4 address or internal ipv4 address
      #   or external ipv6 address should be specified
      #
      # Пустой вложенный блок external_ipv4_address означает «выдай
      # публичный адрес сам». Тот же приём работает и с закреплённым
      # адресом:
      #
      #   external_ipv4_address {
      #     address = yandex_vpc_address.alb.external_ipv4_address[0].address
      #   }
      address {
        external_ipv4_address {}
      }

      ports = [80]
    }

    # Обработка HTTP поручена HTTP-роутеру: именно он решает,
    # на какую группу бэкендов отправить запрос.
    http {
      handler {
        http_router_id = yandex_alb_http_router.web[0].id

        # Здесь же настраивают редирект с HTTP на HTTPS и
        # терминирование TLS сертификатом из Certificate Manager:
        #
        #   redirect_http_to_https = true
        #   certificate_id = yandex_cm_certificate.this.id
      }
    }
  }

  labels = {
    course = "terraform"
    lesson = "5"
  }
}
EOF

  ЦЕЛЕВАЯ ГРУППА — кто принимает трафик:

    resource "yandex_alb_target_group" "web" {
      name = "${var.project_name}-alb-tg"

      target {
        ip_address = yandex_compute_instance.web.network_interface[0].ip_address
        subnet_id  = yandex_compute_instance.web.network_interface[0].subnet_id
      }
    }

  ГРУППА БЭКЕНДОВ — как обращаться к целям и как их проверять:

    resource "yandex_alb_backend_group" "web" {
      name = "${var.project_name}-alb-bg"

      http_backend {
        name = "web-backend"
        port = 80

        target_group_ids = [yandex_alb_target_group.web[0].id]

        healthcheck {
          timeout  = "1s"
          interval = "2s"

          healthy_threshold   = 2
          unhealthy_threshold = 2

          http_healthcheck {
            path = "/"
          }
        }
      }
    }

  Обратите внимание: интервалы здесь СТРОКИ с единицами измерения
  ("2s", "500ms"), а не числа, как у группы машин. Это разные ресурсы
  и разные схемы, и путаница между ними — обычное дело.

  HTTP-РОУТЕР — правила маршрутизации:

    resource "yandex_alb_http_router" "web" {
      name = "${var.project_name}-alb-router"
    }

  ВИРТУАЛЬНЫЙ ХОСТ — привязка имён, правил и бэкендов:

    resource "yandex_alb_virtual_host" "web" {
      name           = "${var.project_name}-alb-vh"
      http_router_id = yandex_alb_http_router.web[0].id

      authority = ["*"]

      route {
        name = "main"

        http_route {
          http_route_action {
            backend_group_id = yandex_alb_backend_group.web[0].id
          }
        }
      }
    }

  Здесь же описывают маршрутизацию по путям: несколько блоков route
  с http_match { path { prefix = "/api" } } и своими бэкендами.

  САМ БАЛАНСИРОВЩИК — слушатели, зоны, группы безопасности:

    resource "yandex_alb_load_balancer" "web" {
      name               = "${var.project_name}-alb"
      network_id         = yandex_vpc_network.this.id
      security_group_ids = [yandex_vpc_security_group.alb[0].id]

      allocation_policy {
        location {
          zone_id   = var.zone
          subnet_id = yandex_vpc_subnet.this["web-d"].id
        }
      }

      listener {
        name = "http"

        endpoint {
          address {
            external_ipv4_address {}
          }
          ports = [80]
        }

        http {
          handler {
            http_router_id = yandex_alb_http_router.web[0].id
          }
        }
      }
    }

  ДВА ВАЖНЫХ МОМЕНТА ПРО СЛУШАТЕЛЬ

    Тип адреса указывается явно. Пустой блок address {} облако
    не принимает:

      Error: Either external ipv4 address or internal ipv4 address
      or external ipv6 address should be specified for the HTTP route

    Пустой вложенный блок external_ipv4_address означает «выдай
    публичный адрес сам». Если адрес нужно закрепить:

      external_ipv4_address {
        address = yandex_vpc_address.alb.external_ipv4_address[0].address
      }

    Создание балансировщика ДОЛГОЕ. В нашем прогоне:

      yandex_alb_load_balancer.web[0]: Still creating... [06m30s elapsed]
      yandex_alb_load_balancer.web[0]: Creation complete after 6m45s

    Почти семь минут. Это надо учитывать заранее: создавайте ALB
    до начала проверок или разбирайте конфигурацию, пока он
    создаётся. Удаляется он тоже не мгновенно.

------------------------------------------------------------------
10. HTTPS И СЕРТИФИКАТ: ЧТО НУЖНО ДОБАВИТЬ
------------------------------------------------------------------

Для HTTPS в ALB нужно три вещи: домен, сертификат и слушатель
с сертификатом. Сертификат Let's Encrypt выпускается в Certificate
Manager и подтверждается через DNS-запись в вашей зоне:

  resource "yandex_cm_certificate" "this" {
    name    = "${var.project_name}-cert"
    domains = ["www.${trimsuffix(var.dns_zone, ".")}"]

    managed {
      challenge_type = "DNS_CNAME"
    }
  }

  # Запись для подтверждения владения доменом создаётся облаком,
  # её нужно перенести в свою DNS-зону:
  resource "yandex_dns_recordset" "cert_challenge" {
    for_each = {
      for ch in yandex_cm_certificate.this.challenges :
      ch.domain => ch
    }

    zone_id = yandex_dns_zone.public.id
    name    = each.value.dns_name
    type    = each.value.dns_type
    ttl     = 600
    data    = [each.value.dns_value]
  }

Затем сертификат подключается к слушателю:

  listener {
    name = "https"

    endpoint {
      address {
        external_ipv4_address {}
      }
      ports = [443]
    }

    tls {
      default_handler {
        certificate_ids = [yandex_cm_certificate.this.id]

        http_handler {
          http_router_id = yandex_alb_http_router.web[0].id
        }
      }
    }
  }

# И перенаправление с HTTP на HTTPS — одной строкой в слушателе порта 80:
#
#   http {
#     handler {
#       http_router_id        = yandex_alb_http_router.web[0].id
#       redirect_http_to_https = true
#     }
#   }

Без делегированного домена этот код не проверить: сертификат останется
в состоянии валидации, а HTTPS не заработает. Поэтому в курсе он дан
как упражнение — и обязательно с проверкой, что домен вам действительно
принадлежит.

11. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

  СИМПТОМ: Error: Invalid index — «The given key does not identify an
  element in this collection value: the collection has no elements»
  ПРИЧИНА: обращение по индексу [0] к пустому списку. У нас так было
  с адресом балансировщика: пока он не создан, адреса нет.
  ЧТО ДЕЛАТЬ: обернуть выражение в try() и вернуть null либо собрать
  значение через one().

  СИМПТОМ: Error: Invalid template interpolation value — «The expression
  result is null. Cannot include a null value in a string template»
  ПРИЧИНА: подстановка null в строку. Возникает в выводах, которые
  собирают команды.
  ЧТО ДЕЛАТЬ: проверять на null явно:

    local.alb_address == null ? "ещё не создан" : "curl -s http://${local.alb_address}/"

  СИМПТОМ: Either external ipv4 address or internal ipv4 address or
  external ipv6 address should be specified for the HTTP route
  ПРИЧИНА: в слушателе ALB указан пустой блок address {}.
  ЧТО ДЕЛАТЬ: явно указать тип адреса — external_ipv4_address {}

  СИМПТОМ: DNS Zone has no private_visibility
  ПРИЧИНА: блок dns_record у машины ссылается на публичную зону.
  ЧТО ДЕЛАТЬ: для записей машин создавать приватную зону
  (public = false + private_networks), а публичные имена заводить
  ресурсом yandex_dns_recordset.

  СИМПТОМ: Auto PTR records are currently not supported for private
  DNS Zones
  ПРИЧИНА: ptr = true в приватной зоне.
  ЧТО ДЕЛАТЬ: ptr = false.

  СИМПТОМ: Public Zone "example.com." is occupied
  ПРИЧИНА: зона для этого домена уже создана — своя же, оставшаяся
  от предыдущего запуска, или чужая, если домен общий на команду.
  Зона уникальна в пределах облака.
  ЧТО ДЕЛАТЬ: найти существующую зону (yc dns zone list) и переиспользовать
  её через источник данных, либо удалить лишнюю.

  СИМПТОМ: страница отдаёт «Not Found» вместо значений метаданных
  ПРИЧИНА: неверный путь в службе метаданных (например, subnet-id
  вместо network).
  ЧТО ДЕЛАТЬ: запросить список ключей (см. раздел 6).

  СИМПТОМ: балансировщик создан, но отвечает ошибкой 503
  ПРИЧИНА: цели не проходят проверку здоровья. Чаще всего: сервис
  не слушает порт, или группа безопасности машины не пускает
  балансировщик.
  ЧТО ДЕЛАТЬ: посмотреть состояние цели:
  yc alb target-group list, проверить healthcheck бэкенда и правила
  группы безопасности (порт должен быть открыт для подсети, из которой
  приходит балансировщик).

  СИМПТОМ: terraform destroy «висит» на балансировщике
  ПРИЧИНА: ALB удаляется несколько минут; это не ошибка.
  ЧТО ДЕЛАТЬ: подождать. В конвейере для таких операций ставят
  увеличенный таймаут.

12. ЗАДАНИЯ
------------------------------------------------------------------

  1. Подсети. Добавьте подсеть в зону ru-central1-e и убедитесь, что
     список зон в выводе zones_covered изменился. Машину в новой
     подсети создавать не нужно — объясните, почему её там нельзя
     создать, пока адрес не выдан в этой зоне.

  2. Правила. Закройте SSH отовсюду и оставьте доступ только с вашего
     адреса. Проверьте: подключение должно работать, а после смены
     адреса в правиле на заведомо чужой — перестать.

  3. Правило по группе. Добавьте вторую машину в группу web и убедитесь,
     что она автоматически получила доступ к внутреннему сервису —
     без правки правил.

  4. Статический адрес. Создайте второй статический адрес и привяжите
     его к машине. Затем удалите машину из конфигурации и убедитесь,
     что адрес остался. Объясните, что теперь надо сделать руками.

  5. Приватная зона. Добейтесь, чтобы машина разрешала своё внутреннее
     имя через приватную зону. Проверьте командой dig на самой машине.

  6. Маршрутизация в ALB. Добавьте второе правило: запросы по пути
     /health должны отдавать простой ответ 200. Подсказка: понадобится
     отдельный виртуальный хост или отдельный маршрут с http_match,
     а проще всего — отдельный бэкенд со своей страницей.

  7. HTTPS. Если у вас есть домен: делегируйте его облаку, выпустите
     сертификат, включите слушатель на 443 и редирект с 80 на 443.
     Если домена нет — объясните словами, какие NS-серверы нужно
     прописать у регистратора и почему без этого HTTPS не заработает.
