ПРАКТИКА 6. ДАННЫЕ И СЕКРЕТЫ: OBJECT STORAGE, БАЗА ДАННЫХ, LOCKBOX, KMS

Продолжительность: 2 академических часа.
Провайдер: yandex-cloud/yandex. Практика выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ЗАНЯТИЯ

  Вы соберёте статический сайт в Object Storage, зашифрованное
  хранилище для приватных данных, кластер Managed Service
  for PostgreSQL с базой и пользователем, секрет в Lockbox и ключи
  KMS. И — что важнее всего — разберёте, почему секрет, «положенный
  в хранилище секретов», всё равно оказывается в файле состояния
  Terraform, если его записывает Terraform.

ЧТО НУЖНО ЗАРАНЕЕ

  * Доступ в облако (практика 1), роль storage.editor у сервисного
    аккаунта (см. раздел 1 — без неё Object Storage не работает).
  * Понимание состояния (практика 2) и модулей (практика 3).

  ВНИМАНИЕ ПРО ДЕНЬГИ. Object Storage и KMS стоят копейки, а вот
  кластер managed-базы данных — десятки рублей в сутки и больше.
  В конфигурации он выключен переменной create_database: включайте
  его на время разбора и выключайте сразу после.

------------------------------------------------------------------
1. ПЕРВАЯ ЛОВУШКА: РОЛИ ДЛЯ OBJECT STORAGE
------------------------------------------------------------------

Object Storage — отдельный сервис со своим API, совместимым с S3.
И права у него свои. На живом стенде мы получили такую картину:
у сервисного аккаунта была роль admin на каталог, бакет создавался
нормально, а вот загрузка объектов падала:

  Error: error creating storage object: error putting object in bucket
  "tf-course-site-p6-2026": AccessDenied: Access Denied
  status code: 403

Причина: для работы через S3 API нужны роли storage.editor
или storage.admin. Роли admin на каталог недостаточно.

  # выдать роль сервисному аккаунту
  yc resource-manager folder add-access-binding <folder_id> \
    --role storage.editor \
    --service-account-id <sa_id>

  # проверить, какие роли уже выданы
  yc resource-manager folder list-access-bindings <folder_id>

Второй момент: для Object Storage нужен СТАТИЧЕСКИЙ КЛЮЧ ДОСТУПА —
не тот же самый, что авторизованный ключ сервисного аккаунта.

  yc iam access-key create --service-account-id <sa_id> \
    --description "доступ к Object Storage"

В ответе два значения, и идентификатор лежит во вложенном объекте:

  {
    "access_key": { "id": "ajetie9irg2oqtm5o0vo",
                    "key_id": "YCAJEXXXXXXXXXXXXXXXXX" },
    "secret": "..."
  }

  В storage_access_key нужно значение key_id (начинается с YCAJE).
  Если подставить весь объект целиком, Object Storage ответит
  «400 Bad Request» вместо понятной ошибки про права.

Ключи передаются провайдеру:

  provider "yandex" {
    cloud_id                 = var.cloud_id
    folder_id                = var.folder_id
    zone                     = var.zone
    service_account_key_file = var.sa_key_file

    storage_access_key = var.storage_access_key
    storage_secret_key = var.storage_secret_key
  }

или переменными окружения AWS_ACCESS_KEY_ID и AWS_SECRET_ACCESS_KEY —
так удобнее в конвейере.

------------------------------------------------------------------
2. СТАТИЧЕСКИЙ САЙТ В БАКЕТЕ
------------------------------------------------------------------

  resource "yandex_storage_bucket" "site" {
    bucket = var.bucket_name

    anonymous_access_flags {
      read        = true
      list        = true
      config_read = false
    }

    versioning {
      enabled = true
    }

    website {
      index_document = var.site_index
      error_document = var.site_error
    }

    force_destroy = true
  }

ТРИ ВЕЩИ, НА КОТОРЫХ СПОТЫКАЮТСЯ ВСЕ

  ПЕРВОЕ: ФЛАГОВ ДОЛЖНО БЫТЬ ДВА — read И list. Документация
  Яндекс Облака говорит прямо: хостинг статического сайта не работает,
  если нет публичного доступа «к объектам И ИХ СПИСКУ». Мы включили
  только read (решив, что список файлов посторонним видеть незачем)
  и получили на живой странице:

    403 Forbidden
    Code: AccessDenied

  при том, что объекты в бакете были, публичный доступ был «включён»
  и служба хостинга работала: запрос к несуществующему файлу честно
  отвечал 404, а к существующему — 403. Разгадка оказалась именно
  в списке: без list служба хостинга не может отдать объект.

  ВТОРОЕ: У БАКЕТА НЕТ АРГУМЕНТА labels. Object Storage — отдельный
  сервис, и метки в нём называются tags:

    tags = { course = "terraform" }

    Error: Unsupported argument
    An argument named "labels" is not expected here.

  ТРЕТЬЕ: force_destroy = true позволяет удалить бакет вместе
  с объектами и версиями. Для занятий удобно, для рабочего бакета
  опасно. По умолчанию false.

ПРОВЕРКА

  terraform output -raw website_endpoint
  tf-data-p6-site.website.yandexcloud.net

  curl -s http://tf-data-p6-site.website.yandexcloud.net/
  <!DOCTYPE html>
  <html lang="ru">
  <head><meta charset="utf-8"><title>Сайт в Object Storage</title>...
  <h1>Статический сайт в Object Storage</h1>

  Ответ 200 означает, что сайт работает.
  Запрос к несуществующему адресу отдаёт страницу ошибки с кодом 404.

  ИСПРАВЛЕНО. В прежней версии курса публичный доступ открывали
  полем acl = "public-read", а когда объекты не загружались,
  предлагалось заменить его на acl = "public-admin". Такого значения
  у бакета не существует, а само поле acl объявлено устаревшим
  (провайдер 0.146.0 и новее). Публичность открывают флагами
  anonymous_access_flags, а для тонких правил есть политика доступа —
  про неё отдельный раздел ниже.

------------------------------------------------------------------
3. ЧТО ЗАГРУЖАЕТСЯ В БАКЕТ И КАК TERRAFORM ЗАМЕЧАЕТ ИЗМЕНЕНИЯ
------------------------------------------------------------------

Главная жалоба новичков звучит так: «я поправил index.html, применил
apply, а на сайте старая страница». Причина — в способе загрузки.

  ЕСЛИ УКАЗАТЬ ФАЙЛ ТОЛЬКО ЧЕРЕЗ source:

    resource "yandex_storage_object" "index" {
      bucket = yandex_storage_bucket.site.id
      key    = "index.html"
      source = "${path.module}/site/index.html"
    }

  Terraform загрузит файл при создании объекта и больше за ним
  не следит: содержимое файла он не читает, поэтому изменения
  не заметит.

  ПРАВИЛЬНО — ЧЕРЕЗ СОДЕРЖИМОЕ ИЛИ ХЭШ:

    # вариант 1: содержимое попадает в конфигурацию
    content_base64 = base64encode(file("${path.module}/site/index.html"))

    # вариант 2: файл читается с диска, но отслеживается его хэш
    source      = "${path.module}/site/assets/${each.key}"
    source_hash = filemd5("${path.module}/site/assets/${each.key}")

Проверим на живом стенде: меняем в странице номер версии с 1 на 2
и смотрим план.

  terraform plan

  # yandex_storage_object.index must be replaced
  + content_base64 = "PCFET0NUWVBFIGh0bWw+CjxodG1sIGxhbmc9InJ1Ij4..."

  Plan: 1 to add, 0 to change, 0 to destroy.

После apply страница действительно обновилась:

  curl -s http://tf-data-p6-site.website.yandexcloud.net/
  <p>Версия страницы: <strong>2</strong>.</p>

Обратите внимание на формулировку в плане: must be replaced. Объект
не «обновляется», а заменяется целиком — для статики это нормально,
но помните, что с версионированием старая версия объекта остаётся
в бакете и занимает место.

ЗАГРУЗКА КАТАЛОГА ЦЕЛИКОМ

  resource "yandex_storage_object" "assets" {
    for_each = fileset("${path.module}/site/assets", "*")

    bucket = yandex_storage_bucket.site.id
    key    = "assets/${each.key}"

    source      = "${path.module}/site/assets/${each.key}"
    source_hash = filemd5("${path.module}/site/assets/${each.key}")

    content_type = lookup({
      "css"  = "text/css"
      "txt"  = "text/plain; charset=utf-8"
      "json" = "application/json"
    }, split(".", each.key)[length(split(".", each.key)) - 1],
       "application/octet-stream")
  }

  fileset перечисляет файлы в каталоге, for_each загружает каждый,
  а lookup подбирает тип содержимого по расширению. Без content_type
  браузер может не понять, что за файл ему отдают, и предложит
  скачать его вместо отображения.

------------------------------------------------------------------
4. ШИФРОВАНИЕ СВОИМ КЛЮЧОМ KMS
------------------------------------------------------------------

Ключ создаётся как обычный ресурс:

  resource "yandex_kms_symmetric_key" "data" {
    name                = "${var.project_name}-key"
    rotation_period     = "8760h"   # ротация раз в год
    deletion_protection = true      # защита от удаления
  }

Зачем свои ключи, если облако и так шифрует данные:

  * доступ к данным определяется не только правами на ресурс, но
    и правами на ключ: отозвали роль на ключ — данные не читает никто;
  * ключ можно ротировать по расписанию;
  * видно, кто и когда обращался к ключу.

Шифрование бакета:

  server_side_encryption_configuration {
    rule {
      apply_server_side_encryption_by_default {
        kms_master_key_id = yandex_kms_symmetric_key.data.id
        sse_algorithm     = "aws:kms"
      }
    }
  }

ЧТО НУЖНО ЗНАТЬ ПРО ЭТОТ БАКЕТ

  ПЕРВОЕ: сервисному аккаунту, который работает с зашифрованным
  бакетом, нужна роль на ключ:

    yc kms symmetric-key add-access-binding --id <key_id> \
      --role kms.keys.encrypterDecrypter \
      --service-account-id <sa_id>

  Без неё он получит AccessDenied, хотя права на сам бакет у него есть.

  ВТОРОЕ И ГЛАВНОЕ: ЗАШИФРОВАННЫЙ БАКЕТ НЕ МОЖЕТ ОТДАВАТЬ
  СТАТИЧЕСКИЙ САЙТ. Документация перечисляет это прямо:
  хостинг не поддерживается в бакетах с включённым шифрованием.
  Логика понятна: чтобы отдать объект анонимному читателю, облаку
  нужно расшифровать его вашим ключом, а у анонимного читателя прав
  на ключ нет.

  Поэтому в практике ДВА бакета:
    * публичный — для сайта, без шифрования;
    * приватный — для данных, с шифрованием своим ключом.

  Проверка приватного бакета: анонимный запрос получает отказ,
  а сервисный аккаунт с ролью на ключ читает объект:

    curl -s -o /dev/null -w '%{http_code}\n' \
      https://<бакет>-private.storage.yandexcloud.net/data.json
    403

------------------------------------------------------------------
5. ПОЛИТИКА ДОСТУПА: КАК ЗАПЕРЕТЬ СЕБЯ СНАРУЖИ
------------------------------------------------------------------

Политика доступа — гибкий инструмент: ею разрешают чтение части
объектов, ограничивают доступ по IP, по времени и по типу запроса.
Но у неё есть ловушка, на которую мы наступили на живом стенде,
и о ней стоит знать заранее.

ЧТО МЫ СДЕЛАЛИ. Добавили политику, разрешающую всем читать объекты:

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid       = "PublicReadForWebsite"
      Effect    = "Allow"
      Principal = "*"
      Action    = ["s3:GetObject"]
      Resource  = "arn:aws:s3:::${var.bucket_name}/*"
    }]
  })

ЧТО ПОЛУЧИЛОСЬ. После применения политики работать с бакетом стало
невозможно:

  Error: error reading Storage Bucket (tf-course-site-p6-2026):
  Forbidden: Forbidden
  status code: 403

  Error: error putting object in bucket "tf-course-site-p6-2026":
  AccessDenied: Access Denied
  status code: 403

Причём доступ потерял не только провайдер, но и владелец облака:
команда yc storage s3api list-objects отвечала AccessDenied.

ПРИЧИНА. Как только к бакету применена политика, доступ начинает
проверяться по ней — и никого, кроме перечисленных в политике,
она не пропускает. В нашей политике был только публичный доступ
на чтение объектов, и этого не хватило ни сервисному аккаунту,
ни владельцу.

КАК ВЫБРАТЬСЯ, ЕСЛИ УЖЕ ЗАПЕРЛИ СЕБЯ

  * поставить политику, в которой есть полные права для вашего
    аккаунта — нам помогло правило с Principal "*" и действиями
    s3:*; после него бакет удалось очистить и удалить;
  * либо удалить бакет и создать заново, если данных нет.

  Заметим: снять политику «в ноль» через командную строку не
  получилось — пустая политика тоже блокирует доступ. Лечится
  перезаписью политики целиком.

ПРАВИЛО: пишете политику — сразу включайте в неё правила для того
аккаунта, которым работаете. А для простого публичного сайта
политика не нужна вовсе: хватает флагов anonymous_access_flags.

Для полноты: политика ограничивающая анонимный доступ к объектам
и списку, ломает и хостинг статического сайта — документация
перечисляет это среди условий, при которых хостинг не работает.

------------------------------------------------------------------
6. КЛАСТЕР БАЗЫ ДАННЫХ
------------------------------------------------------------------

Managed-база — не «PostgreSQL на арендованной машине»: облако само
делает резервные копии, следит за отказоустойчивостью, обновляет
минорные версии и умеет переключать мастер.

  resource "yandex_mdb_postgresql_cluster" "db" {
    count = var.create_database ? 1 : 0

    name        = "${var.project_name}-pg"
    environment = "PRESTABLE"      # или PRODUCTION
    network_id  = module.vpc.network_id

    security_group_ids  = [yandex_vpc_security_group.db.id]
    deletion_protection = false

    config {
      version = var.db_version     # 15, 16, 17, 18, 19

      resources {
        resource_preset_id = var.db_preset     # s2.micro
        disk_type_id       = "network-ssd"
        disk_size          = var.db_disk_size
      }

      backup_window_start {
        hours   = 3
        minutes = 0
      }
    }

    host {
      zone      = var.zone
      subnet_id = module.vpc.subnet_ids["data"]
    }
  }

Разбор ключевых полей:

  ENVIRONMENT — это не «название среды», а режим кластера:
  PRESTABLE (для тестов, обновления приходят раньше) или
  PRODUCTION (рабочий).

  HOST — один хост для занятий. Для отказоустойчивости хосты
  размещают в разных зонах: три хоста дают кворум и автоматическое
  переключение мастера.

  SECURITY_GROUP_IDS — без группы безопасности кластер создастся,
  но подключиться к нему будет нельзя. Правила пишем не на весь
  интернет, а на диапазон или на группу безопасности приложений:

    resource "yandex_vpc_security_group_rule" "db_from_subnet" {
      security_group_binding = yandex_vpc_security_group.db.id
      direction              = "ingress"
      protocol               = "TCP"
      port                   = 6432
      v4_cidr_blocks         = ["10.0.0.0/8"]
    }

БАЗА И ПОЛЬЗОВАТЕЛЬ — ОТДЕЛЬНЫМИ РЕСУРСАМИ

  resource "yandex_mdb_postgresql_database" "app" {
    count      = var.create_database ? 1 : 0
    cluster_id = yandex_mdb_postgresql_cluster.db[0].id
    name       = var.db_name
    owner      = var.db_user
    depends_on = [yandex_mdb_postgresql_user.app]
  }

  resource "yandex_mdb_postgresql_user" "app" {
    count      = var.create_database ? 1 : 0
    cluster_id = yandex_mdb_postgresql_cluster.db[0].id
    name       = var.db_user
    password   = var.db_password
  }

  ИСПРАВЛЕНО. В прежней версии курса база и пользователь описывались
  вложенными блоками внутри кластера. Такие блоки объявлены
  устаревшими: они мешают обновлять кластер и не позволяют менять
  базу, не трогая сам кластер. Кроме того, из примера курса была
  версия СУБД 6.0 (для MongoDB) — сейчас версии устарели.

ЧТО ПОЛУЧИЛОСЬ НА СТЕНДЕ

  yc managed-postgresql cluster list
  | ID                   | NAME          | STATUS | HEALTH  |
  | c9qhph5qiv1m51itcsot | tf-data-p6-pg | ALIVE  | RUNNING |

  версия: 17, окружение: PRESTABLE
  базы: appdb
  пользователи: appuser

Строка подключения собирается из имени хоста:

  postgresql://appuser:<пароль>@
    rc1d-4emu2dbg05hullm5.mdb.yandexcloud.net:6432/appdb?sslmode=require

  (Строка подключения — одна строка; здесь перенесена для читаемости.)

Полезные детали по времени: база внутри кластера создаётся около
минуты, а удаление кластера заняло больше двух минут. Кластер
платный всё время, пока существует, — не забудьте про destroy.

  Обратите внимание на порт: 6432 — это порт пулера соединений
  (Odyssey). Прямое подключение к PostgreSQL идёт на 6432 через
  пулер, что для приложений удобнее: соединения переиспользуются.

7. СЕКРЕТЫ В LOCKBOX
------------------------------------------------------------------

Секрет — это «папка», а значения лежат в его версиях:

  resource "yandex_lockbox_secret" "db" {
    count       = var.create_secret ? 1 : 0
    name        = "${var.project_name}-db-secret"
    kms_key_id  = yandex_kms_symmetric_key.secrets[0].id

    deletion_protection = true
  }

  resource "yandex_lockbox_secret_version" "db" {
    count     = var.create_secret ? 1 : 0
    secret_id = yandex_lockbox_secret.db[0].id

    entries {
      key        = "db_password"
      text_value = var.db_password
    }

    entries {
      key        = "db_host"
      text_value = yandex_mdb_postgresql_cluster.db[0].host[0].fqdn
    }
  }

В секрете оказались четыре ключа:

  yc lockbox secret list-versions --id <secret_id>
  | ID                   | STATUS    | PAYLOAD KEYS                        |
  | e6q504irkhdf4e5lrr7j | ACTIVE    | db_password,db_user,db_name,db_host |

ПРО РОЛИ

  Чтение значений секрета — отдельная роль lockbox.payloadViewer.
  Просмотр метаданных секрета — lockbox.viewer. Разница
  принципиальная: можно дать человеку видеть список секретов,
  но не их содержимое.

РОТАЦИЯ

  Каждое изменение версии создаёт НОВУЮ версию, а прежняя помечается
  на удаление. Вот что мы увидели после того, как в секрете появился
  настоящий адрес базы:

  | e6qcnppssskjaqb8r4ef | ACTIVE                    |
  | e6q504irkhdf4e5lrr7j | SCHEDULED_FOR_DESTRUCTION |

  Это удобно: приложение успевает перейти на новую версию, а старая
  остаётся для отката, пока её не удалят по расписанию.

------------------------------------------------------------------
8. ГЛАВНЫЙ ВЫВОД ПРАКТИКИ: СЕКРЕТ ВСЁ РАВНО В СОСТОЯНИИ
------------------------------------------------------------------

  Хранилище секретов защищает секрет от людей. Но если значение
  записывает Terraform, оно попадает в файл состояния — и лежит там
  открытым текстом.

Проверим на живом стенде:

  terraform state pull | grep -i db_password
  "state_secret_check": "terraform state pull | grep -i db_password"
  "db_password_sensitive": { ... }

А если поискать сам пароль:

  terraform state pull > state.json
  grep -c 'Zayac-47-Polyana' state.json
  1

  Пароль найден в состоянии открытым текстом. Флаг sensitive
  и хранилище секретов на это не влияют: sensitive запрещает печатать
  значение в выводе команд, а Lockbox хранит свою копию.

ЧТО С ЭТИМ ДЕЛАТЬ

  1. ХРАНИТЬ СОСТОЯНИЕ В ЗАЩИЩЁННОМ МЕСТЕ. Бакет с ограниченным
     доступом (практика 2) — минимум. Права на состояние должны быть
     у ограниченного круга людей.

  2. НЕ ЗАПИСЫВАТЬ СЕКРЕТ ЧЕРЕЗ TERRAFORM. Создавайте версию секрета
     средствами Lockbox (консоль, yc, API), а в Terraform только
     читайте её источником данных — тогда в состоянии окажется
     значение, прочитанное при первом плане... то есть тоже окажется.
     Полностью избежать этого нельзя, пока значение проходит через
     Terraform; можно лишь сократить время его жизни.

  3. ГЕНЕРИРОВАТЬ ПАРОЛЬ ВНУТРИ LOCKBOX:

       password_payload_specification {
         password_key = "db_password"
         length       = 24
       }

     Тогда значения нет ни в переменных, ни в конфигурации,
     ни в состоянии. Но и пароль для базы придётся брать из секрета
     в момент настройки приложения, а не в момент apply.

  4. ОГРАНИЧИТЬ ДОСТУП К КЛЮЧУ ШИФРОВАНИЯ. Секрет зашифрован ключом
     KMS: без роли на ключ его содержимое не прочитает даже тот,
     у кого есть доступ к секрету.

------------------------------------------------------------------
9. ЗАЩИТА ОТ УДАЛЕНИЯ: ПРОВЕРКА НА ЖИВОМ СТЕНДЕ
------------------------------------------------------------------

Ключ KMS и секрет Lockbox созданы с защитой:

  deletion_protection = true

Попробуем удалить всё командой destroy:

  terraform destroy

  Error: Failed to Delete resource
  Error while requesting API to delete symmetric_key:
  rpc error: code = FailedPrecondition
  desc = Key with id abjvn18bre9vimsae0br is protected from deletion.
  Change "deletion_protection" flag for deletion.

  Error: error reading secret "e6qn1g0s0ejdhecfrcd4":
  rpc error: code = FailedPrecondition
  desc = Secret with id 'e6qn1g0s0ejdhecfrcd4' is protected
  from deletion. Update 'deletion_protection' field to delete the secret.

Это правильное поведение, а не ошибка. Порядок такой:

  1. поставить в конфигурации deletion_protection = false;
  2. применить изменения (terraform apply);
  3. и только потом удалять.

Правило, которое стоит запомнить: ЗАЩИТА СРАБАТЫВАЕТ ДВАЖДЫ —
в конфигурации (lifecycle prevent_destroy) и на стороне облака
(deletion_protection). Вторая надёжнее: она не зависит от того,
что написано в файлах, и не даст удалить ресурс даже из консоли.

10. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

  СИМПТОМ: AccessDenied при загрузке объекта в бакет
  ПРИЧИНА 1: у сервисного аккаунта нет роли storage.editor
  или storage.admin (роли admin на каталог недостаточно).
  ПРИЧИНА 2: для зашифрованного бакета нет роли
  kms.keys.encrypterDecrypter на ключ.
  ЧТО ДЕЛАТЬ: выдать роли, проверить список:
  yc resource-manager folder list-access-bindings <folder_id>.

  СИМПТОМ: Error: Unsupported argument, An argument named "labels"
  is not expected here (для бакета)
  ПРИЧИНА: у бакета нет меток labels, есть tags.
  ЧТО ДЕЛАТЬ: использовать tags.

  СИМПТОМ: сайт отдаёт 403 Forbidden, хотя объекты в бакете есть
  и публичный доступ «включён»
  ПРИЧИНА 1: включён только флаг read, а нужен ещё list — без
  публичного доступа к списку объектов хостинг статики не работает.
  ПРИЧИНА 2: бакет зашифрован своим ключом KMS — с шифрованием
  хостинг не поддерживается.
  ПРИЧИНА 3: к бакету применена политика, ограничивающая анонимный
  доступ к объектам и списку.
  ПРИЧИНА 4: включён доступ только из сервисных подключений VPC.
  ЧТО ДЕЛАТЬ: проверить все четыре условия. Полезная проверка:
  запрос к несуществующему объекту. Если он даёт 404, служба
  хостинга работает, а дело именно в правах на чтение.

  СИМПТОМ: после добавления политики бакет стал недоступен вообще,
  включая владельца
  ПРИЧИНА: политика заменила модель доступа, а прав для своего
  аккаунта в ней не было.
  ЧТО ДЕЛАТЬ: перезаписать политику, добавив правило с полными
  правами для вашего аккаунта, либо пересоздать бакет.

  СИМПТОМ: страница сайта не обновляется после правки файла
  ПРИЧИНА: объект загружен через source без source_hash.
  ЧТО ДЕЛАТЬ: использовать content_base64 или source_hash.

  СИМПТОМ: бакет не удаляется — «bucket is not empty»
  ПРИЧИНА: включено версионирование, остались версии объектов
  и маркеры удаления. Наш учебный бакет накапливал их с каждой
  правкой страницы.
  ЧТО ДЕЛАТЬ: удалить все версии (см. практику 2), либо поставить
  force_destroy = true в учебной конфигурации.

  СИМПТОМ: кластер базы создан, но подключиться нельзя
  ПРИЧИНА: группа безопасности не пускает трафик на порт 6432,
  либо правило открыто не для той сети.
  ЧТО ДЕЛАТЬ: проверить правила группы безопасности кластера.

  СИМПТОМ: destroy не удаляет ключ KMS или секрет Lockbox
  ПРИЧИНА: deletion_protection = true.
  ЧТО ДЕЛАТЬ: снять флаг, применить изменения, затем удалять.

11. ЗАДАНИЯ
------------------------------------------------------------------

  1. Сайт. Добейтесь, чтобы сайт отдавался по HTTPS-адресу, а не
     только по HTTP. Подсказка: у бакета есть блок https
     с сертификатом; либо поставьте перед бакетом CDN.

  2. Обновление контента. Добавьте в сайт каталог с картинками
     и загружайте их через for_each и fileset. Проверьте, что замена
     картинки приводит к обновлению объекта.

  3. Приватные данные. Положите в приватный бакет файл с условными
     «персональными данными». Убедитесь, что анонимный доступ
     невозможен, а сервисный аккаунт читает файл.

  4. Роли. Отзовите у сервисного аккаунта роль на ключ KMS
     и убедитесь, что доступ к зашифрованному бакету пропал.
     Верните роль.

  5. Секрет без состояния. Переделайте создание секрета так, чтобы
     пароль генерировался внутри Lockbox
     (password_payload_specification), а не приходил переменной.
     Проверьте, что пароля больше нет в состоянии.

  6. База данных. Включите кластер, добавьте второго пользователя
     с правами только на чтение и убедитесь, что он не может
     записывать в базу.

  7. Уборка. Удалите всё созданное и проверьте в облаке, что не
     осталось ни бакетов, ни версий объектов, ни ключей, ни секретов,
     ни кластера.
