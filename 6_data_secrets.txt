ПРАКТИКА 6. ДАННЫЕ И СЕКРЕТЫ: OBJECT STORAGE, БАЗА ДАННЫХ, LOCKBOX, KMS

Продолжительность: 2 академических часа.
Провайдер: yandex-cloud/yandex. Практика выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ПРАКТИКИ

  Вы соберёте статический сайт в Object Storage, зашифрованное
  хранилище для приватных данных, кластер Managed Service
  for PostgreSQL с базой и пользователем, секрет в Lockbox и ключи
  KMS. И — что важнее всего — разберёте, почему секрет, «положенный
  в хранилище секретов», всё равно оказывается в файле состояния
  Terraform, если его записывает Terraform.

ЧТО НУЖНО ЗАРАНЕЕ

  * Доступ в облако (практика 1), роль storage.editor у сервисного
    аккаунта (см. раздел 1 — без неё Object Storage не работает).
  * Понимание состояния (практика 2) и модулей (практика 3).

  ВНИМАНИЕ ПРО ДЕНЬГИ. Object Storage и KMS стоят копейки, а вот
  кластер managed-базы данных — десятки рублей в сутки и больше.
  В конфигурации он выключен переменной create_database: включайте
  его на время разбора и выключайте сразу после.

------------------------------------------------------------------
0. КАТАЛОГ ПРОЕКТА И ФАЙЛЫ
------------------------------------------------------------------

Правило, которое нарушают чаще всего: ОДИН ПРОЕКТ — ОДИН
КАТАЛОГ. Terraform работает с состоянием в пределах каталога,
поэтому файлы разных проектов в одной папке перемешают ресурсы
и состояние.

Создаём каталог практики:

  mkdir -p ~/terraform-course/work/06-data-secrets
  cd ~/terraform-course/work/06-data-secrets

Здесь ~/terraform-course — клон репозитория с материалами курса.
Каталог work/ внутрь репозитория не попадает: он перечислен
в .gitignore, чтобы ваши эксперименты не смешивались
с материалами курса.

СТРУКТУРА ПРОЕКТА

  06-data-secrets/
  ├── db-network.tf
  ├── db.tf
  ├── kms.tf
  ├── lockbox.tf
  ├── outputs.tf
  ├── provider.tf
  ├── site/
  │   ├── assets/
  │   │   └── style.css
  │   ├── error.html
  │   └── index.html
  ├── storage.tf
  ├── terraform.tfvars.example
  ├── variables.tf

  ../modules/vpc/          общий модуль сети (создан в практике 3)
    ├── main.tf

  Плюс файлы, которые создаются при работе и в репозиторий

  Файл .terraform.lock.hcl, наоборот, нужно сохранить в git:
  он фиксирует версии провайдеров.

КАК СОЗДАЁМ ФАЙЛЫ

  Файлы можно набрать по тексту практики. Конструкция
  cat > имя-файла <<'EOF' записывает в файл всё, что введено до
  строки EOF, поэтому такой блок можно скопировать в терминал
  целиком. Строки cat и EOF стоят в первом столбце: отступ сломал
  бы завершение ввода.

  Готовые файлы практики лежат в материалах курса — их можно
  взять вместо набора по тексту:

  cp -r ~/terraform-course/files/06_data_secrets/. .
  mkdir -p ../modules
  cp -r ~/terraform-course/files/modules/vpc ../modules/

  Вторая команда копирует общий модуль сети: в конфигурациях он
  подключается как source = "../modules/vpc", то есть лежит рядом
  с каталогом практики, в каталоге work/modules/vpc. Без модуля
  terraform init остановится с ошибкой:

    Error: Unreadable module directory
    Error: Module not installed

Первый файл практики — variables.tf: входные переменные. От них
зависят имена ресурсов, версия PostgreSQL, размер диска и то,
создавать ли платный кластер базы; здесь же видно, какие
значения помечены чувствительными.

cat > variables.tf <<'EOF'
variable "cloud_id" {
  type        = string
  description = "Идентификатор облака"
}

variable "folder_id" {
  type        = string
  description = "Идентификатор каталога"
}

variable "zone" {
  type        = string
  description = "Зона доступности"
  default     = "ru-central1-d"
}

# Статические ключи доступа к Object Storage.
#
# Значение key_id начинается с YCAJE — это не тот же ключ, что
# авторизованный ключ сервисного аккаунта. Подробности в provider.tf.
# Оба значения — секреты: в репозиторий они не попадают, передаются
# через terraform.tfvars (он в .gitignore) или переменными окружения
# AWS_ACCESS_KEY_ID и AWS_SECRET_ACCESS_KEY.
variable "storage_access_key" {
  type        = string
  description = "Идентификатор статического ключа доступа (key_id)"
  default     = null
  sensitive   = true
}

variable "storage_secret_key" {
  type        = string
  description = "Секретная часть статического ключа доступа"
  default     = null
  sensitive   = true
}

variable "sa_key_file" {
  type        = string
  description = "Путь к авторизованному ключу сервисного аккаунта"
}

variable "project_name" {
  type        = string
  description = "Префикс в именах ресурсов"
  default     = "tf-data"
}

# Имя бакета должно быть уникальным во всём Object Storage.
# Добавьте к имени что-то своё: логин, название команды, дату.
variable "bucket_name" {
  type        = string
  description = "Имя бакета для статического сайта"

  validation {
    condition     = can(regex("^[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]$", var.bucket_name))
    error_message = "Имя бакета: строчные латинские буквы, цифры, точка и дефис."
  }
}

variable "site_index" {
  type        = string
  description = "Главная страница сайта"
  default     = "index.html"
}

variable "site_error" {
  type        = string
  description = "Страница ошибки"
  default     = "error.html"
}

# Версия PostgreSQL. Список допустимых версий смотрите в документации
# провайдера к ресурсу yandex_mdb_postgresql_cluster: сейчас это
# 15, 16, 17, 18 и 19 (варианты с суффиксом -1c — для 1С).
variable "db_version" {
  type        = string
  description = "Версия PostgreSQL"
  default     = "17"
}

variable "db_name" {
  type        = string
  description = "Имя базы данных"
  default     = "appdb"
}

variable "db_user" {
  type        = string
  description = "Имя пользователя базы данных"
  default     = "appuser"
}

# Пароль базы данных.
#
# Флаг sensitive запрещает печатать значение в выводе команд, но НЕ
# убирает его из файла состояния. Об этом подробно в тексте практики.
variable "db_password" {
  type        = string
  description = "Пароль пользователя базы данных"
  sensitive   = true
  default     = ""
}

# Создавать ли кластер базы данных.
#
# По умолчанию выключено: кластер стоит денег, и в учебном стенде его
# включают на время разбора, а потом выключают. Сайт в бакете при этом
# стоит копейки.
variable "create_database" {
  type        = bool
  description = "Создавать ли кластер Managed Service for PostgreSQL"
  default     = false
}

variable "db_disk_size" {
  type        = number
  description = "Размер диска кластера, ГБ"
  default     = 10

  validation {
    condition     = var.db_disk_size >= 10 && var.db_disk_size <= 50
    error_message = "Размер диска кластера: от 10 до 50 ГБ."
  }
}

variable "db_preset" {
  type        = string
  description = "Класс ресурсов хоста базы данных"
  default     = "s2.micro"
}

# Создавать ли секрет в Lockbox.
variable "create_secret" {
  type        = bool
  description = "Создавать ли секрет в Lockbox с паролем базы"
  default     = true
}
EOF

cat > provider.tf <<'EOF'
provider "yandex" {
  cloud_id                 = var.cloud_id
  folder_id                = var.folder_id
  zone                     = var.zone
  service_account_key_file = var.sa_key_file

  # Отдельные ключи для Object Storage.
  #
  # Object Storage работает по S3-совместимому API, и для него нужен
  # СТАТИЧЕСКИЙ КЛЮЧ ДОСТУПА — не тот же самый, что авторизованный
  # ключ сервисного аккаунта. Ключ создаётся отдельно:
  #
  #   yc iam access-key create --service-account-id <sa_id> \
  #     --description "доступ к Object Storage"
  #
  # В ответе два значения, и идентификатор лежит во вложенном объекте:
  #
  #   {
  #     "access_key": { "key_id": "YCAJEXXXXXXXXXXXXXXXXX" },
  #     "secret": "..."
  #   }
  #
  # В storage_access_key нужно значение key_id (начинается с YCAJE).
  # Если подставить весь объект целиком, Object Storage ответит
  # «400 Bad Request» вместо понятной ошибки про права.
  #
  # Значения можно не указывать здесь, а задать переменными окружения
  # AWS_ACCESS_KEY_ID и AWS_SECRET_ACCESS_KEY — так удобнее в конвейере.
  storage_access_key = var.storage_access_key
  storage_secret_key = var.storage_secret_key
}
EOF

cat > kms.tf <<'EOF'
# Ключ шифрования KMS.
#
# Ключ нужен, чтобы шифровать данные в облаке своими ключами: бакет,
# диск кластера, секрет в Lockbox. Смысл в том, что доступ к данным
# определяется не только правами на ресурс, но и правами на ключ:
# отозвали роль на ключ — и зашифрованные данные никто не прочитает.
#
# Ключом управляют так же, как любым ресурсом: он создаётся, ротируется
# и удаляется через Terraform.

resource "yandex_kms_symmetric_key" "data" {
  name        = "${var.project_name}-key"
  description = "Ключ шифрования данных курса Terraform"

  # Автоматическая ротация: раз в год облако создаёт новую версию ключа.
  # Старые версии сохраняются, поэтому уже зашифрованные данные
  # остаются доступными.
  rotation_period = "8760h"

  # Защита от удаления: ключ нельзя удалить, пока флаг не снят.
  # Для ключа шифрования это особенно важно — с удалением ключа
  # теряются все данные, которые им зашифрованы.
  deletion_protection = true

  labels = {
    course = "terraform"
    lesson = "6"
  }
}

# Отдельный ключ для секретов. Смешивать назначения не принято:
# разные ключи — разные права доступа и разные последствия компрометации.
resource "yandex_kms_symmetric_key" "secrets" {
  count = var.create_secret ? 1 : 0

  name                = "${var.project_name}-secrets-key"
  description         = "Ключ шифрования секретов"
  rotation_period     = "8760h"
  deletion_protection = true

  labels = {
    course = "terraform"
    lesson = "6"
  }
}
EOF

------------------------------------------------------------------
1. ПЕРВАЯ ЛОВУШКА: РОЛИ ДЛЯ OBJECT STORAGE
------------------------------------------------------------------

Object Storage — отдельный сервис со своим API, совместимым с S3.
И права у него свои. На живом стенде картина была такой:
у сервисного аккаунта была роль admin на каталог, бакет создавался
нормально, а вот загрузка объектов падала:

  Error: error creating storage object: error putting object in bucket
  "tf-course-site-p6-2026": AccessDenied: Access Denied
  status code: 403

Причина: для работы через S3 API нужны роли storage.editor
или storage.admin. Роли admin на каталог недостаточно.

  # выдать роль сервисному аккаунту
  yc resource-manager folder add-access-binding <folder_id> \
    --role storage.editor \
    --service-account-id <sa_id>

  # проверить, какие роли уже выданы
  yc resource-manager folder list-access-bindings <folder_id>

Второй момент: для Object Storage нужен СТАТИЧЕСКИЙ КЛЮЧ ДОСТУПА —
не тот же самый, что авторизованный ключ сервисного аккаунта.

  yc iam access-key create --service-account-id <sa_id> \
    --description "доступ к Object Storage"

В ответе два значения, и идентификатор лежит во вложенном объекте:

  {
    "access_key": { "id": "ajetie9irg2oqtm5o0vo",
                    "key_id": "YCAJEXXXXXXXXXXXXXXXXX" },
    "secret": "..."
  }

  В storage_access_key нужно значение key_id (начинается с YCAJE).
  Если подставить весь объект целиком, Object Storage ответит
  «400 Bad Request» вместо понятной ошибки про права.

Ключи передаются провайдеру:

  provider "yandex" {
    cloud_id                 = var.cloud_id
    folder_id                = var.folder_id
    zone                     = var.zone
    service_account_key_file = var.sa_key_file

    storage_access_key = var.storage_access_key
    storage_secret_key = var.storage_secret_key
  }

или переменными окружения AWS_ACCESS_KEY_ID и AWS_SECRET_ACCESS_KEY —
так удобнее в конвейере.

------------------------------------------------------------------
2. СТАТИЧЕСКИЙ САЙТ В БАКЕТЕ
------------------------------------------------------------------

Вся работа с хранилищем собрана в файле storage.tf: два бакета —
публичный с сайтом и приватный с шифрованием своим ключом KMS,
а также объекты сайта и данные приложения.

cat > storage.tf <<'EOF'
# Object Storage: два бакета и разные задачи.
#
# Здесь мы разбираем сразу несколько вещей, на которых обычно спотыкаются:
#
#   1) как отдать бакет наружу БЕЗ устаревшего ACL;
#   2) как Terraform понимает, что файл сайта изменился;
#   3) почему публичный сайт и шифрование своим ключом KMS вместе
#      не работают — и как это обойти;
#   4) чем опасна политика доступа к бакету.

# ------------------------------------------------------------------
# БАКЕТ 1: публичный статический сайт
# ------------------------------------------------------------------
#
# У этого бакета НЕТ шифрования своим ключом KMS, и это осознанное
# решение. Мы получили ошибку 403 на живом стенде, когда попробовали
# совместить шифрование KMS и публичный сайт:
#
#   curl -s http://<бакет>.website.yandexcloud.net/
#   403 Forbidden, Code: AccessDenied
#
# Причина: содержимое бакета зашифровано нашим ключом, а анонимный
# читатель не имеет права пользоваться этим ключом — значит, облако
# не может расшифровать объект и отказывает.
#
# ВЫВОД: публичные данные и данные, зашифрованные своим ключом, —
# это разные бакеты. Ниже так и сделано: сайт в одном, приватные
# данные в другом.

resource "yandex_storage_bucket" "site" {
  bucket = var.bucket_name

  # Публичный доступ к бакету.
  #
  # Это современный способ сделать бакет читаемым для всех — вместо
  # устаревшего поля acl = "public-read". Флагов три, и они означают
  # разное:
  #
  #   read        — можно читать объекты;
  #   list        — можно получать список объектов;
  #   config_read — можно читать настройки бакета.
  #
  # ВНИМАНИЕ: ДЛЯ СТАТИЧЕСКОГО САЙТА НУЖНЫ ОБА ФЛАГА — И read, И list.
  #
  # Документация Яндекс Облака говорит об этом прямо: хостинг
  # статического сайта не работает, если нет публичного доступа
  # «к объектам И ИХ СПИСКУ». Мы на этом споткнулись: включили только
  # read (рассудив, что список файлов посторонним видеть незачем),
  # и сайт отвечал
  #
  #   403 Forbidden, Code: AccessDenied
  #
  # при том, что объекты в бакете были и публичный доступ был
  # «включён». Несуществующий объект при этом давал честный 404 —
  # то есть служба хостинга работала, а анонимное чтение запрещалось.
  #
  # Там же в документации перечислены другие условия, при которых
  # хостинг не работает: шифрование бакета (см. ниже — поэтому у сайта
  # нет шифрования своим ключом) и политика доступа, ограничивающая
  # анонимный доступ к объектам и списку.
  anonymous_access_flags {
    read        = true
    list        = true
    config_read = false
  }

  # Версионирование: облако хранит предыдущие версии объектов.
  # Спасает от случайной перезаписи и от «мы залили не тот файл».
  # Обратите внимание: с версионированием объекты занимают больше места,
  # а удалить бакет можно только вместе с версиями (практика 2).
  versioning {
    enabled = true
  }

  # Настройки статического сайта: какая страница главная, какая —
  # при ошибке. Именно они превращают бакет в веб-сервер.
  website {
    index_document = var.site_index
    error_document = var.site_error
  }

  # force_destroy = true позволит удалить бакет вместе с объектами
  # и версиями. Для учебного стенда это удобно, для рабочего — опасно:
  # по умолчанию стоит false, и это правильно.
  force_destroy = true

  # Обратите внимание: у бакета НЕТ аргумента labels, в отличие
  # от машин, сетей и баз данных. Object Storage — отдельный сервис
  # со своим API, и метки в нём называются tags:
  #
  #   tags = { course = "terraform" }
  #
  # Попытка указать labels заканчивается ошибкой:
  #
  #   Error: Unsupported argument
  #   An argument named "labels" is not expected here.
  tags = {
    course  = "terraform"
    lesson  = "6"
    purpose = "public-site"
  }
}

# ------------------------------------------------------------------
# БАКЕТ 2: приватные данные с шифрованием своим ключом
# ------------------------------------------------------------------

resource "yandex_storage_bucket" "private" {
  bucket = "${var.bucket_name}-private"

  versioning {
    enabled = true
  }

  # Шифрование на стороне сервера своим ключом KMS.
  #
  # Данные шифруются в облаке, а доступ к ним определяется ещё и
  # правами на ключ: отозвали роль на ключ — зашифрованные данные
  # не прочитает никто, включая того, у кого есть доступ к бакету.
  #
  # Важно помнить про две вещи:
  #   * анонимный доступ к такому бакету невозможен (см. выше);
  #   * сервисному аккаунту, который работает с бакетом, нужна роль
  #     kms.keys.encrypterDecrypter на ключ — иначе он получит
  #     AccessDenied, хотя роль на бакет у него есть.
  server_side_encryption_configuration {
    rule {
      apply_server_side_encryption_by_default {
        kms_master_key_id = yandex_kms_symmetric_key.data.id
        sse_algorithm     = "aws:kms"
      }
    }
  }

  force_destroy = true

  tags = {
    course  = "terraform"
    lesson  = "6"
    purpose = "private-data"
  }
}

# ------------------------------------------------------------------
# ПОЛИТИКА ДОСТУПА К БАКЕТУ: инструмент, которым легко запереть себя
# ------------------------------------------------------------------
#
# Политика — более тонкий инструмент, чем флаги анонимного доступа:
# ею можно разрешить чтение части объектов, ограничить доступ по IP
# или по времени. Но есть ловушка, на которую мы наступили на стенде.
#
# ЧТО ПРОИЗОШЛО. Мы добавили политику, разрешающую всем читать
# объекты (s3:GetObject), и после этого работать с бакетом стало
# невозможно:
#
#   Error: error reading Storage Bucket: Forbidden: Forbidden
#   Error: error putting object in bucket: AccessDenied
#
# Причём «сломался» доступ не только у провайдера, но и у владельца
# облака: команда yc storage s3api list-objects отвечала AccessDenied.
#
# ПРИЧИНА: как только к бакету применена политика, доступ начинает
# проверяться по ней, и никого, кроме перечисленных в ней, она
# не пропускает. В нашей политике был только публичный доступ
# на чтение объектов.
#
# КАК ВЫБРАТЬСЯ. Если политика уже применена и доступ потерян:
#   * поставить политику с полными правами для своего аккаунта —
#     нам помогло правило с Principal "*" и действиями s3:*,
#     после чего бакет удалось очистить и удалить;
#   * либо удалить бакет и создать заново (если данных нет).
#
# ПРАВИЛО: когда пишете политику, всегда включайте в неё правила для
# того аккаунта, которым вы работаете. И помните, что для публичного
# сайта достаточно флагов anonymous_access_flags.
#
# Образец политики с двумя правилами (мы им не пользуемся, но он
# пригодится, когда понадобится тонкий доступ):
#
#   resource "yandex_storage_bucket_policy" "private" {
#     bucket = yandex_storage_bucket.private.id
#
#     policy = jsonencode({
#       Version = "2012-10-17"
#       Statement = [
#         {
#           Sid       = "OwnerFullAccess"
#           Effect    = "Allow"
#           Principal = "*"
#           Action    = ["s3:*"]
#           Resource = [
#             "arn:aws:s3:::${var.bucket_name}-private",
#             "arn:aws:s3:::${var.bucket_name}-private/*",
#           ]
#         },
#       ]
#     })
#   }
#
# ИСПРАВЛЕНО. В прежней версии курса публичность открывали полем acl,
# а при проблемах с загрузкой файлов предлагалось заменить
# acl = "public-read" на acl = "public-admin". Такого значения
# не существует; кроме того, поле acl объявлено устаревшим
# (провайдер 0.146.0 и новее).

# ------------------------------------------------------------------
# ОБЪЕКТЫ САЙТА
# ------------------------------------------------------------------
#
# ВАЖНАЯ ДЕТАЛЬ: как Terraform узнаёт, что файл изменился.
#
# Если указать source = "site/index.html", Terraform загрузит файл
# при создании объекта и больше не будет за ним следить: содержимое
# файла он не читает, а значит изменения не заметит. Правка страницы
# не приведёт ни к чему — это одна из самых частых жалоб новичков.
#
# Два способа решить это:
#
#   1. content_base64 = base64encode(file(...)) — содержимое попадает
#      в конфигурацию, и Terraform сравнивает его при каждом плане;
#
#   2. source = "..." плюс source_hash = filemd5("...") — содержимое
#      не попадает в конфигурацию, но хэш файла отслеживается.
#
# Мы используем первый способ для страниц (они небольшие) и второй —
# для больших файлов (например, картинок).

resource "yandex_storage_object" "index" {
  bucket = yandex_storage_bucket.site.id
  key    = var.site_index

  content_base64 = base64encode(file("${path.module}/site/index.html"))
  content_type   = "text/html; charset=utf-8"
}

resource "yandex_storage_object" "error_page" {
  bucket = yandex_storage_bucket.site.id
  key    = var.site_error

  content_base64 = base64encode(file("${path.module}/site/error.html"))
  content_type   = "text/html; charset=utf-8"
}

# Второй способ: файл на диске и его хэш.
#
# Обратите внимание на for_each по результату fileset: так загружают
# целый каталог, не перечисляя файлы руками.
resource "yandex_storage_object" "assets" {
  for_each = fileset("${path.module}/site/assets", "*")

  bucket = yandex_storage_bucket.site.id
  key    = "assets/${each.key}"

  source      = "${path.module}/site/assets/${each.key}"
  source_hash = filemd5("${path.module}/site/assets/${each.key}")

  # Тип содержимого по расширению: без него браузер может не понять,
  # что это за файл, и предложит его скачать вместо отображения.
  content_type = lookup({
    "css"  = "text/css"
    "txt"  = "text/plain; charset=utf-8"
    "json" = "application/json"
    "js"   = "application/javascript"
  }, split(".", each.key)[length(split(".", each.key)) - 1], "application/octet-stream")
}

# Объект в приватном бакете: данные приложения.
#
# Проверить, что он недоступен анонимно, можно так:
#
#   curl -s -o /dev/null -w '%{http_code}\n' \
#     https://<бакет>-private.storage.yandexcloud.net/data.json
#   # 403
#
# А сам сервисный аккаунт с ролью на ключ KMS его читает.
resource "yandex_storage_object" "private_data" {
  bucket = yandex_storage_bucket.private.id
  key    = "data.json"

  content = jsonencode({
    service   = "terraform-course"
    lesson    = 6
    encrypted = true
  })
  content_type = "application/json"
}
EOF

  ПЕРВОЕ: ФЛАГОВ ДОЛЖНО БЫТЬ ДВА — read И list. Документация
  Яндекс Облака говорит прямо: хостинг статического сайта не работает,

  живая страница отвечает:

  ВТОРОЕ: У БАКЕТА НЕТ АРГУМЕНТА labels. Object Storage — отдельный

Главная жалоба новичков звучит так: «я поправил index.html, применил
apply, а на сайте старая страница». Причина — в способе загрузки.

  ЕСЛИ УКАЗАТЬ ФАЙЛ ТОЛЬКО ЧЕРЕЗ source:

    resource "yandex_storage_object" "index" {
      bucket = yandex_storage_bucket.site.id
      key    = "index.html"
      source = "${path.module}/site/index.html"
    }

  Terraform загрузит файл при создании объекта и больше за ним
  не следит: содержимое файла он не читает, поэтому изменения
  не заметит.

  ПРАВИЛЬНО — ЧЕРЕЗ СОДЕРЖИМОЕ ИЛИ ХЭШ:

    # вариант 1: содержимое попадает в конфигурацию
    content_base64 = base64encode(file("${path.module}/site/index.html"))

    # вариант 2: файл читается с диска, но отслеживается его хэш
    source      = "${path.module}/site/assets/${each.key}"
    source_hash = filemd5("${path.module}/site/assets/${each.key}")

Проверим на живом стенде: меняем в странице номер версии с 1 на 2
и смотрим план.

  terraform plan

  # yandex_storage_object.index must be replaced
  + content_base64 = "PCFET0NUWVBFIGh0bWw+CjxodG1sIGxhbmc9InJ1Ij4..."

  Plan: 1 to add, 0 to change, 0 to destroy.

После apply страница действительно обновилась:

  curl -s http://tf-data-p6-site.website.yandexcloud.net/
  <p>Версия страницы: <strong>2</strong>.</p>

Обратите внимание на формулировку в плане: must be replaced. Объект
не «обновляется», а заменяется целиком — для статики это нормально,
но помните, что с версионированием старая версия объекта остаётся
в бакете и занимает место.

ЗАГРУЗКА КАТАЛОГА ЦЕЛИКОМ

  resource "yandex_storage_object" "assets" {
    for_each = fileset("${path.module}/site/assets", "*")

    bucket = yandex_storage_bucket.site.id
    key    = "assets/${each.key}"

ЧАСТЬ 2. ПРОДОЛЖЕНИЕ

------------------------------------------------------------------
4. ШИФРОВАНИЕ СВОИМ КЛЮЧОМ KMS
------------------------------------------------------------------

Ключ создаётся как обычный ресурс:

  resource "yandex_kms_symmetric_key" "data" {
    name                = "${var.project_name}-key"
    rotation_period     = "8760h"   # ротация раз в год
    deletion_protection = true      # защита от удаления
  }

Зачем свои ключи, если облако и так шифрует данные:

  * доступ к данным определяется не только правами на ресурс, но
    и правами на ключ: отозвали роль на ключ — данные не читает никто;
  * ключ можно ротировать по расписанию;
  * видно, кто и когда обращался к ключу.

Шифрование бакета:

  server_side_encryption_configuration {
    rule {
      apply_server_side_encryption_by_default {
        kms_master_key_id = yandex_kms_symmetric_key.data.id
        sse_algorithm     = "aws:kms"
      }
    }
  }

ЧТО НУЖНО ЗНАТЬ ПРО ЭТОТ БАКЕТ

  ПЕРВОЕ: сервисному аккаунту, который работает с зашифрованным
  бакетом, нужна роль на ключ:

    yc kms symmetric-key add-access-binding --id <key_id> \
      --role kms.keys.encrypterDecrypter \
      --service-account-id <sa_id>

  Без неё он получит AccessDenied, хотя права на сам бакет у него есть.

  ВТОРОЕ И ГЛАВНОЕ: ЗАШИФРОВАННЫЙ БАКЕТ НЕ МОЖЕТ ОТДАВАТЬ
  СТАТИЧЕСКИЙ САЙТ. Документация перечисляет это прямо:
  хостинг не поддерживается в бакетах с включённым шифрованием.
  Логика понятна: чтобы отдать объект анонимному читателю, облаку
  нужно расшифровать его вашим ключом, а у анонимного читателя прав
  на ключ нет.

  Поэтому в практике ДВА бакета:
    * публичный — для сайта, без шифрования;
    * приватный — для данных, с шифрованием своим ключом.

  Проверка приватного бакета: анонимный запрос получает отказ,
  а сервисный аккаунт с ролью на ключ читает объект:

    curl -s -o /dev/null -w '%{http_code}\n' \
      https://<бакет>-private.storage.yandexcloud.net/data.json
    403

------------------------------------------------------------------
5. ПОЛИТИКА ДОСТУПА: КАК ЗАПЕРЕТЬ СЕБЯ СНАРУЖИ
------------------------------------------------------------------

Политика доступа — гибкий инструмент: ею разрешают чтение части
объектов, ограничивают доступ по IP, по времени и по типу запроса.
Но у неё есть ловушка, на которую легко наступить, и о ней
стоит знать заранее.

ЧТО БЫЛО СДЕЛАНО. В бакет добавили политику, разрешающую всем
читать объекты:

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid       = "PublicReadForWebsite"
      Effect    = "Allow"
      Principal = "*"
      Action    = ["s3:GetObject"]
      Resource  = "arn:aws:s3:::${var.bucket_name}/*"
    }]
  })

ЧТО ПОЛУЧИЛОСЬ. После применения политики работать с бакетом стало
невозможно:

  Error: error reading Storage Bucket (tf-course-site-p6-2026):
  Forbidden: Forbidden
  status code: 403

  Error: error putting object in bucket "tf-course-site-p6-2026":
  AccessDenied: Access Denied
  status code: 403

Причём доступ потерял не только провайдер, но и владелец облака:
команда yc storage s3api list-objects отвечала AccessDenied.

ПРИЧИНА. Как только к бакету применена политика, доступ начинает
проверяться по ней — и никого, кроме перечисленных в политике,
она не пропускает. В такой политике оказался только публичный
доступ на чтение объектов, и этого не хватило ни сервисному
аккаунту, ни владельцу.

КАК ВЫБРАТЬСЯ, ЕСЛИ УЖЕ ЗАПЕРЛИ СЕБЯ

  * поставить политику, в которой есть полные права для вашего
    аккаунта — помогает правило с Principal "*" и действиями
    s3:*; после него бакет удаётся очистить и удалить;
  * либо удалить бакет и создать заново, если данных нет.

  Заметьте: снять политику «в ноль» через командную строку не
  получится — пустая политика тоже блокирует доступ. Лечится
  перезаписью политики целиком.

ПРАВИЛО: пишете политику — сразу включайте в неё правила для того
аккаунта, которым работаете. А для простого публичного сайта
политика не нужна вовсе: хватает флагов anonymous_access_flags.

Для полноты: политика ограничивающая анонимный доступ к объектам
и списку, ломает и хостинг статического сайта — документация
перечисляет это среди условий, при которых хостинг не работает.

------------------------------------------------------------------
6. КЛАСТЕР БАЗЫ ДАННЫХ
------------------------------------------------------------------

Managed-база — не «PostgreSQL на арендованной машине»: облако само
делает резервные копии, следит за отказоустойчивостью, обновляет
минорные версии и умеет переключать мастер.

Сеть и группа безопасности для кластера описаны в файле
db-network.tf: модуль vpc создаёт подсеть data, а правило группы
безопасности пускает в базу трафик только из внутренней сети.

cat > db-network.tf <<'EOF'
# Сеть для базы данных.
#
# База данных живёт в подсети и доступна по внутренним адресам.
# Публичный доступ к managed-базе включают редко: это отдельный флаг
# у хоста, и он открывает кластер всему интернету.

module "vpc" {
  source = "../modules/vpc"

  network_name = "${var.project_name}-net"

  subnets = {
    data = {
      zone = var.zone
      cidr = "10.80.10.0/24"
    }
  }

  # Наружу ничего не открываем: в этой практике машин нет, а к базе
  # обращаются изнутри сети.
  allowed_ports = []

  labels = {
    course = "terraform"
    lesson = "6"
  }
}

# Группа безопасности для кластера базы данных.
#
# Правило «пускать только из подсети» показывает типовой подход:
# источник задаётся диапазоном адресов приложений, а не 0.0.0.0/0.
# В рабочей среде здесь был бы не диапазон, а ссылка на группу
# безопасности приложений (приём из практики 5).
resource "yandex_vpc_security_group" "db" {
  name        = "${var.project_name}-db-sg"
  description = "Доступ к базе данных только изнутри сети"
  network_id  = module.vpc.network_id

  labels = {
    course = "terraform"
    lesson = "6"
    role   = "database"
  }
}

resource "yandex_vpc_security_group_rule" "db_from_subnet" {
  security_group_binding = yandex_vpc_security_group.db.id
  direction              = "ingress"
  description            = "PostgreSQL из внутренней сети"

  protocol       = "TCP"
  port           = 6432
  v4_cidr_blocks = ["10.0.0.0/8"]
}

resource "yandex_vpc_security_group_rule" "db_egress" {
  security_group_binding = yandex_vpc_security_group.db.id
  direction              = "egress"
  description            = "Исходящий трафик"

  protocol       = "ANY"
  from_port      = 0
  to_port        = 65535
  v4_cidr_blocks = ["0.0.0.0/0"]
}
EOF

Сам кластер, база и пользователь — в файле db.tf. Кластер
включается переменной create_database, а база и пользователь
создаются отдельными ресурсами.

cat > db.tf <<'EOF'
# Кластер Managed Service for PostgreSQL.
#
# Managed-база — это не «PostgreSQL на арендованной машине»: облако
# само делает резервные копии, следит за отказоустойчивостью,
# обновляет минорные версии и умеет переключать мастер.
#
# ЧТО ЗДЕСЬ СТОИТ ДЕНЕГ: кластер платный даже в простое. Минимальный
# класс s2.micro с диском 10 ГБ — это несколько десятков рублей
# в сутки. Поэтому в учебном стенде кластер включают переменной
# create_database на время разбора и обязательно удаляют.

resource "yandex_mdb_postgresql_cluster" "db" {
  count = var.create_database ? 1 : 0

  name        = "${var.project_name}-pg"
  description = "Учебный кластер PostgreSQL курса Terraform"

  # environment — это не «название среды», а режим кластера:
  #   PRESTABLE — для тестов, PRODUCTION — для рабочей нагрузки.
  # Разница в частоте обновлений и в поддержке.
  environment = "PRESTABLE"

  network_id = module.vpc.network_id

  security_group_ids = [yandex_vpc_security_group.db.id]

  # Защита от удаления: пока флаг true, кластер не удалится
  # ни через Terraform, ни через консоль.
  deletion_protection = false

  labels = {
    course = "terraform"
    lesson = "6"
  }

  config {
    version = var.db_version

    # Класс ресурсов хоста и диск.
    resources {
      resource_preset_id = var.db_preset
      disk_type_id       = "network-ssd"
      disk_size          = var.db_disk_size
    }

    # Окно резервного копирования: время, когда облако снимает копию.
    # По умолчанию выбирается автоматически; здесь указано явно,
    # чтобы показать, что это настраивается.
    backup_window_start {
      hours   = 3
      minutes = 0
    }
  }

  # Хосты кластера. Один хост — учебный вариант: он не переживёт
  # отказа зоны. Для отказоустойчивости хосты размещают в разных
  # зонах: три хоста дают кворум и автоматическое переключение.
  host {
    zone      = var.zone
    subnet_id = module.vpc.subnet_ids["data"]
  }
}

# База данных создаётся ОТДЕЛЬНЫМ ресурсом.
#
# ИСПРАВЛЕНО. В прежней версии курса база и пользователь описывались
# вложенными блоками внутри кластера (database {...}, user {...}).
# Такие блоки объявлены устаревшими: они мешают обновлять кластер
# и не позволяют менять базу, не трогая сам кластер. Современный
# подход — отдельные ресурсы.
resource "yandex_mdb_postgresql_database" "app" {
  count = var.create_database ? 1 : 0

  cluster_id = yandex_mdb_postgresql_cluster.db[0].id

  name  = var.db_name
  owner = var.db_user

  # Владелец должен существовать раньше базы.
  depends_on = [yandex_mdb_postgresql_user.app]
}

resource "yandex_mdb_postgresql_user" "app" {
  count = var.create_database ? 1 : 0

  cluster_id = yandex_mdb_postgresql_cluster.db[0].id

  name     = var.db_user
  password = var.db_password
}
EOF

Разбор ключевых полей:

  ENVIRONMENT — это не «название среды», а режим кластера:
  PRESTABLE (для тестов, обновления приходят раньше) или
  PRODUCTION (рабочий).

  HOST — один хост: учебный вариант. Для отказоустойчивости хосты
  размещают в разных зонах: три хоста дают кворум и автоматическое
  переключение мастера.

  SECURITY_GROUP_IDS — без группы безопасности кластер создастся,
  но подключиться к нему будет нельзя. Правила пишем не на весь
  интернет, а на диапазон или на группу безопасности приложений:

    resource "yandex_vpc_security_group_rule" "db_from_subnet" {
      security_group_binding = yandex_vpc_security_group.db.id
      direction              = "ingress"
      protocol               = "TCP"
      port                   = 6432
      v4_cidr_blocks         = ["10.0.0.0/8"]
    }

БАЗА И ПОЛЬЗОВАТЕЛЬ — ОТДЕЛЬНЫМИ РЕСУРСАМИ

  resource "yandex_mdb_postgresql_database" "app" {
    count      = var.create_database ? 1 : 0
    cluster_id = yandex_mdb_postgresql_cluster.db[0].id
    name       = var.db_name
    owner      = var.db_user
    depends_on = [yandex_mdb_postgresql_user.app]
  }

  resource "yandex_mdb_postgresql_user" "app" {
    count      = var.create_database ? 1 : 0
    cluster_id = yandex_mdb_postgresql_cluster.db[0].id
    name       = var.db_user
    password   = var.db_password
  }

  ИСПРАВЛЕНО. В прежней версии курса база и пользователь описывались
  вложенными блоками внутри кластера. Такие блоки объявлены
  устаревшими: они мешают обновлять кластер и не позволяют менять
  базу, не трогая сам кластер. Кроме того, из примера курса была
  версия СУБД 6.0 (для MongoDB) — сейчас версии устарели.

ЧТО ПОЛУЧИЛОСЬ НА СТЕНДЕ

  yc managed-postgresql cluster list
  | ID                   | NAME          | STATUS | HEALTH  |
  | c9qhph5qiv1m51itcsot | tf-data-p6-pg | ALIVE  | RUNNING |

  версия: 17, окружение: PRESTABLE
  базы: appdb
  пользователи: appuser

Строка подключения собирается из имени хоста:

  postgresql://appuser:<пароль>@
    rc1d-4emu2dbg05hullm5.mdb.yandexcloud.net:6432/appdb?sslmode=require

  (Строка подключения — одна строка; здесь перенесена для читаемости.)

Полезные детали по времени: база внутри кластера создаётся около
минуты, а удаление кластера длилось больше двух минут. Кластер
платный всё время, пока существует, — не забудьте про destroy.

  Обратите внимание на порт: 6432 — это порт пулера соединений
  (Odyssey). Прямое подключение к PostgreSQL идёт на 6432 через
  пулер, что для приложений удобнее: соединения переиспользуются.

------------------------------------------------------------------
7. СЕКРЕТЫ В LOCKBOX
------------------------------------------------------------------

Секрет — это «папка», а значения лежат в его версиях: сам объект
секрета хранит только метаданные, а пароль и адрес базы — версия.
Всё это собрано в файле lockbox.tf.

cat > lockbox.tf <<'EOF'
# Lockbox: хранилище секретов.
#
# Задача: пароль базы данных не должен лежать в коде, в репозитории
# и в переписке. Правильное место для него — хранилище секретов,
# где у каждого секрета свои права доступа, своя история версий
# и свой журнал обращений.

resource "yandex_lockbox_secret" "db" {
  count = var.create_secret ? 1 : 0

  name        = "${var.project_name}-db-secret"
  description = "Пароль базы данных курса Terraform"

  # Секрет шифруется нашим ключом KMS: без права на ключ его
  # содержимое не прочитает даже тот, у кого есть доступ к секрету.
  kms_key_id = yandex_kms_symmetric_key.secrets[0].id

  # Защита от удаления: секрет нельзя удалить, пока флаг не снят.
  deletion_protection = true

  labels = {
    course = "terraform"
    lesson = "6"
  }
}

# Версия секрета: именно в ней лежат значения.
#
# Секрет без версии бесполезен: сам объект — это «папка», а значения
# хранятся в версиях. Версий может быть много, и это удобно для
# ротации: добавили новую версию — приложения перешли на неё,
# старая осталась для отката.
resource "yandex_lockbox_secret_version" "db" {
  count = var.create_secret ? 1 : 0

  secret_id   = yandex_lockbox_secret.db[0].id
  description = "Параметры подключения к базе данных"

  entries {
    key        = "db_password"
    text_value = var.db_password
  }

  entries {
    key        = "db_user"
    text_value = var.db_user
  }

  entries {
    key        = "db_name"
    text_value = var.db_name
  }

  entries {
    key        = "db_host"
    text_value = var.create_database ? yandex_mdb_postgresql_cluster.db[0].host[0].fqdn : "база не создавалась"
  }
}

# ЧТО ЗДЕСЬ ВАЖНО ПОНЯТЬ
#
# 1. Значение секрета ЗАПИСЫВАЕТСЯ ЧЕРЕЗ TERRAFORM, а значит попадает
#    в файл состояния. Хранилище секретов защищает секрет от людей,
#    но не от состояния Terraform. Проверить это можно так:
#
#      terraform state pull | grep -i db_password
#
#    Увидите свой пароль в открытом виде.
#
# 2. Как избежать этого:
#    * создавать версию секрета средствами Lockbox (консоль, yc, API),
#      а в Terraform только читать её через источник данных;
#    * генерировать пароль внутри Lockbox:
#
#        password_payload_specification {
#          password_key = "db_password"
#          length       = 24
#        }
#
#      тогда значения нет ни в переменных, ни в конфигурации, ни в
#      состоянии — но и пароль для базы придётся брать из секрета
#      в момент настройки приложения, а не в момент apply;
#    * хранить состояние в бакете с ограниченным доступом (практика 2).
#
# 3. Роли. Чтение значения секрета — отдельная роль:
#    lockbox.payloadViewer. Просмотр метаданных секрета —
#    lockbox.viewer. Разница принципиальная: можно дать человеку
#    видеть список секретов, но не их содержимое.
EOF

В секрете оказались четыре ключа:

  yc lockbox secret list-versions --id <secret_id>
  | ID                   | STATUS    | PAYLOAD KEYS                        |
  | e6q504irkhdf4e5lrr7j | ACTIVE    | db_password,db_user,db_name,db_host |

ПРО РОЛИ

  Чтение значений секрета — отдельная роль lockbox.payloadViewer.
  Просмотр метаданных секрета — lockbox.viewer. Разница
  принципиальная: можно дать человеку видеть список секретов,
  но не их содержимое.

РОТАЦИЯ

  Каждое изменение версии создаёт НОВУЮ версию, а прежняя помечается
  на удаление. Вот что видно после того, как в секрете появился
  настоящий адрес базы:

  | e6qcnppssskjaqb8r4ef | ACTIVE                    |
  | e6q504irkhdf4e5lrr7j | SCHEDULED_FOR_DESTRUCTION |

  Это удобно: приложение успевает перейти на новую версию, а старая
  остаётся для отката, пока её не удалят по расписанию.

------------------------------------------------------------------
8. ГЛАВНЫЙ ВЫВОД ПРАКТИКИ: СЕКРЕТ ВСЁ РАВНО В СОСТОЯНИИ
------------------------------------------------------------------

  Хранилище секретов защищает секрет от людей. Но если значение
  записывает Terraform, оно попадает в файл состояния — и лежит там
  открытым текстом.

Проверим на живом стенде:

  terraform state pull | grep -i db_password
  "state_secret_check": "terraform state pull | grep -i db_password"
  "db_password_sensitive": { ... }

А если поискать сам пароль:

  terraform state pull > state.json
  grep -c 'Zayac-47-Polyana' state.json
  1

  Пароль найден в состоянии открытым текстом. Флаг sensitive
  и хранилище секретов на это не влияют: sensitive запрещает печатать
  значение в выводе команд, а Lockbox хранит свою копию.

ЧТО С ЭТИМ ДЕЛАТЬ

  1. ХРАНИТЬ СОСТОЯНИЕ В ЗАЩИЩЁННОМ МЕСТЕ. Бакет с ограниченным
     доступом (практика 2) — минимум. Права на состояние должны быть
     у ограниченного круга людей.

  2. НЕ ЗАПИСЫВАТЬ СЕКРЕТ ЧЕРЕЗ TERRAFORM. Создавайте версию секрета
     средствами Lockbox (консоль, yc, API), а в Terraform только
     читайте её источником данных — тогда в состоянии окажется
     значение, прочитанное при первом плане... то есть тоже окажется.
     Полностью избежать этого нельзя, пока значение проходит через
     Terraform; можно лишь сократить время его жизни.

  3. ГЕНЕРИРОВАТЬ ПАРОЛЬ ВНУТРИ LOCKBOX:

       password_payload_specification {
         password_key = "db_password"
         length       = 24
       }

     Тогда значения нет ни в переменных, ни в конфигурации,
     ни в состоянии. Но и пароль для базы придётся брать из секрета
     в момент настройки приложения, а не в момент apply.

  4. ОГРАНИЧИТЬ ДОСТУП К КЛЮЧУ ШИФРОВАНИЯ. Секрет зашифрован ключом
     KMS: без роли на ключ его содержимое не прочитает даже тот,
     у кого есть доступ к секрету.

Значения, которые печатались выше, объявлены в файле outputs.tf:
здесь и адрес сайта, и подсказка со строкой подключения, и готовая
проверка состояния с поиском пароля.

cat > outputs.tf <<'EOF'
# Выводы практики 6.
#
# Обратите внимание: адрес сайта — это обычный публичный адрес бакета,
# по которому отдаётся статика. Работает он по HTTP: чтобы отдавать
# сайт по HTTPS, перед бакетом ставят CDN или прикладной балансировщик.

output "website_endpoint" {
  description = "Адрес статического сайта"
  value       = yandex_storage_bucket.site.website_endpoint
}

output "bucket_name" {
  description = "Имя бакета"
  value       = yandex_storage_bucket.site.bucket
}

output "bucket_domain" {
  description = "Доменное имя бакета"
  value       = yandex_storage_bucket.site.bucket_domain_name
}

output "kms_key_id" {
  description = "Идентификатор ключа шифрования данных"
  value       = yandex_kms_symmetric_key.data.id
}

output "secret_id" {
  description = "Идентификатор секрета в Lockbox"
  value       = var.create_secret ? yandex_lockbox_secret.db[0].id : null
}

# Вывод с содержимым секрета помечен как чувствительный: в терминале
# вместо значения будет <sensitive>. В состоянии значение лежит
# открытым текстом — об этом в тексте практики.
output "db_password_sensitive" {
  description = "Пароль базы данных (скрыт в выводе команд)"
  value       = var.db_password
  sensitive   = true
}

output "db_connection_hint" {
  description = "Как выглядит строка подключения (пароль подставьте сами)"
  value = var.create_database ? format(
    "postgresql://%s:<пароль>@%s:6432/%s?sslmode=require",
    var.db_user,
    yandex_mdb_postgresql_cluster.db[0].host[0].fqdn,
    var.db_name,
  ) : "база не создавалась"
}

output "db_host" {
  description = "Имя хоста базы данных"
  value       = var.create_database ? yandex_mdb_postgresql_cluster.db[0].host[0].fqdn : null
}

output "check_commands" {
  description = "Готовые команды для проверки"
  value = {
    open_site          = "curl -s ${yandex_storage_bucket.site.website_endpoint}/"
    list_objects       = "yc storage s3api list-objects --bucket ${yandex_storage_bucket.site.bucket}"
    secret_versions    = var.create_secret ? "yc lockbox secret list-versions --id ${yandex_lockbox_secret.db[0].id}" : "секрет не создавался"
    state_secret_check = "terraform state pull | grep -i db_password"
  }
}
EOF

------------------------------------------------------------------
9. ЗАЩИТА ОТ УДАЛЕНИЯ: ПРОВЕРКА НА ЖИВОМ СТЕНДЕ
------------------------------------------------------------------

Ключ KMS и секрет Lockbox созданы с защитой:

  deletion_protection = true

Попробуем удалить всё командой destroy:

  terraform destroy

  Error: Failed to Delete resource
  Error while requesting API to delete symmetric_key:
  rpc error: code = FailedPrecondition
  desc = Key with id abjvn18bre9vimsae0br is protected from deletion.
  Change "deletion_protection" flag for deletion.

  Error: error reading secret "e6qn1g0s0ejdhecfrcd4":
  rpc error: code = FailedPrecondition
  desc = Secret with id 'e6qn1g0s0ejdhecfrcd4' is protected
  from deletion. Update 'deletion_protection' field to delete the secret.

Это правильное поведение, а не ошибка. Порядок такой:

  1. поставить в конфигурации deletion_protection = false;
  2. применить изменения (terraform apply);
  3. и только потом удалять.

Правило, которое стоит запомнить: ЗАЩИТА СРАБАТЫВАЕТ ДВАЖДЫ —
в конфигурации (lifecycle prevent_destroy) и на стороне облака
(deletion_protection). Вторая надёжнее: она не зависит от того,
что написано в файлах, и не даст удалить ресурс даже из консоли.

10. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

  СИМПТОМ: AccessDenied при загрузке объекта в бакет
  ПРИЧИНА 1: у сервисного аккаунта нет роли storage.editor
  или storage.admin (роли admin на каталог недостаточно).
  ПРИЧИНА 2: для зашифрованного бакета нет роли
  kms.keys.encrypterDecrypter на ключ.
  ЧТО ДЕЛАТЬ: выдать роли, проверить список:
  yc resource-manager folder list-access-bindings <folder_id>.

  СИМПТОМ: Error: Unsupported argument, An argument named "labels"
  is not expected here (для бакета)
  ПРИЧИНА: у бакета нет меток labels, есть tags.
  ЧТО ДЕЛАТЬ: использовать tags.

  СИМПТОМ: сайт отдаёт 403 Forbidden, хотя объекты в бакете есть
  и публичный доступ «включён»
  ПРИЧИНА 1: включён только флаг read, а нужен ещё list — без
  публичного доступа к списку объектов хостинг статики не работает.
  ПРИЧИНА 2: бакет зашифрован своим ключом KMS — с шифрованием
  хостинг не поддерживается.
  ПРИЧИНА 3: к бакету применена политика, ограничивающая анонимный
  доступ к объектам и списку.
  ПРИЧИНА 4: включён доступ только из сервисных подключений VPC.
  ЧТО ДЕЛАТЬ: проверить все четыре условия. Полезная проверка:
  запрос к несуществующему объекту. Если он даёт 404, служба
  хостинга работает, а дело именно в правах на чтение.

  СИМПТОМ: после добавления политики бакет стал недоступен вообще,
  включая владельца
  ПРИЧИНА: политика заменила модель доступа, а прав для своего
  аккаунта в ней не было.
  ЧТО ДЕЛАТЬ: перезаписать политику, добавив правило с полными
  правами для вашего аккаунта, либо пересоздать бакет.

  СИМПТОМ: страница сайта не обновляется после правки файла
  ПРИЧИНА: объект загружен через source без source_hash.
  ЧТО ДЕЛАТЬ: использовать content_base64 или source_hash.

  СИМПТОМ: бакет не удаляется — «bucket is not empty»
  ПРИЧИНА: включено версионирование, остались версии объектов
  и маркеры удаления. Наш учебный бакет накапливал их с каждой
  правкой страницы.
  ЧТО ДЕЛАТЬ: удалить все версии (см. практику 2), либо поставить
  force_destroy = true в учебной конфигурации.

  СИМПТОМ: кластер базы создан, но подключиться нельзя
  ПРИЧИНА: группа безопасности не пускает трафик на порт 6432,
  либо правило открыто не для той сети.
  ЧТО ДЕЛАТЬ: проверить правила группы безопасности кластера.

  СИМПТОМ: destroy не удаляет ключ KMS или секрет Lockbox
  ПРИЧИНА: deletion_protection = true.
  ЧТО ДЕЛАТЬ: снять флаг, применить изменения, затем удалять.

11. ЗАДАНИЯ
------------------------------------------------------------------

  1. Сайт. Добейтесь, чтобы сайт отдавался по HTTPS-адресу, а не
     только по HTTP. Подсказка: у бакета есть блок https
     с сертификатом; либо поставьте перед бакетом CDN.

  2. Обновление контента. Добавьте в сайт каталог с картинками
     и загружайте их через for_each и fileset. Проверьте, что замена
     картинки приводит к обновлению объекта.

  3. Приватные данные. Положите в приватный бакет файл с условными
     «персональными данными». Убедитесь, что анонимный доступ
     невозможен, а сервисный аккаунт читает файл.

  4. Роли. Отзовите у сервисного аккаунта роль на ключ KMS
     и убедитесь, что доступ к зашифрованному бакету пропал.
     Верните роль.

  5. Секрет без состояния. Переделайте создание секрета так, чтобы
     пароль генерировался внутри Lockbox
     (password_payload_specification), а не приходил переменной.
     Проверьте, что пароля больше нет в состоянии.

  6. База данных. Включите кластер, добавьте второго пользователя
     с правами только на чтение и убедитесь, что он не может
     записывать в базу.

  7. Уборка. Удалите всё созданное и проверьте в облаке, что не
     осталось ни бакетов, ни версий объектов, ни ключей, ни секретов,
     ни кластера.
