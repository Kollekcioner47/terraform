ПРАКТИКА 8. ПРОМЫШЛЕННАЯ ЭКСПЛУАТАЦИЯ: ОКРУЖЕНИЯ, КОНВЕЙЕР, ТЕСТЫ

Продолжительность: 2 академических часа.
Провайдер: yandex-cloud/yandex. Практика выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ЗАНЯТИЯ

  Вы разделите один и тот же код на два окружения с независимыми
  состояниями, научитесь проверять конфигурацию тестами без обращения
  к облаку, настроите фиксацию версии провайдера для разных платформ
  и соберёте конвейер, который считает план на каждый merge request,
  а применяет — только вручную и только из основной ветки. В конце
  развернёте итоговый стенд курса одной командой и так же его снесёте.

ЧТО НУЖНО ЗАРАНЕЕ

  * Все предыдущие практики: доступ, состояние, модули, машины,
    сети, данные и секреты, Kubernetes.
  * Репозиторий с курсом (или свой) и понимание, что такое
    merge request.
  * Сервисный аккаунт с ролью storage.editor — состояние живёт в бакете.

ГДЕ ЭТО МОЖНО ПРИМЕНИТЬ НА ПРАКТИКЕ

  Навыки этой практики не проверяются «в облаке» — они проверяются
  в работе: именно они отличают человека, который умеет запускать
  terraform apply, от человека, которому можно доверить инфраструктуру
  в общем окружении.

ЧАСТЬ 1. БАЗОВАЯ

------------------------------------------------------------------
1. ДВА ОКРУЖЕНИЯ ИЗ ОДНОГО КОДА
------------------------------------------------------------------

Задача: один и тот же код должен разворачивать и dev, и prod, причём
изменения в одном окружении не должны задевать второе.

Есть два подхода, и оба рабочие.

  ПОДХОД 1: ОТДЕЛЬНЫЙ КАТАЛОГ НА ОКРУЖЕНИЕ

    environments/
      dev/    backend.tf, main.tf, terraform.tfvars
      prod/   backend.tf, main.tf, terraform.tfvars

  Состояния независимы по построению: у каждого каталога свой файл
  состояния. Минус — копирование конфигурации: два файла, которые
  должны оставаться одинаковыми, но живут отдельно.

  ПОДХОД 2: ОДИН КОД, РАЗНЫЕ ЗНАЧЕНИЯ И РАЗНЫЕ КЛЮЧИ СОСТОЯНИЯ

  Конфигурация одна, а отличаются две вещи:

    ключ состояния      — какой объект в бакете читать;
    файл значений       — какие значения у переменных.

  В курсе используется второй подход, потому что он нагляднее
  показывает суть: ОКРУЖЕНИЕ — ЭТО НЕ КОПИЯ КОДА, А ДРУГОЕ СОСТОЯНИЕ
  И ДРУГИЕ ЗНАЧЕНИЯ.

Настройки хранилища вынесены в отдельные файлы:

  # env/backend-dev.tfvars
  bucket = "tf-course-state-ivan"
  key    = "final/dev/terraform.tfstate"

  # env/backend-prod.tfvars
  bucket = "tf-course-state-prod"
  key    = "final/prod/terraform.tfstate"

Инициализация и работа:

  terraform init -backend-config=env/backend-dev.tfvars
  terraform apply -var-file=env/dev.tfvars

  terraform init -backend-config=env/backend-prod.tfvars -reconfigure
  terraform apply -var-file=env/prod.tfvars

  Ключ -reconfigure нужен потому, что настройки хранилища изменились:
  без него Terraform предложит перенести состояние
  (init -migrate-state), а нам это не нужно — состояния разные.

ЧТО МЫ УВИДЕЛИ НА ЖИВОМ СТЕНДЕ

  В бакете появились два независимых состояния:

    yc storage s3api list-objects --bucket tf-course-state-r8-2026
    - key: final/dev/terraform.tfstate
    - key: final/prod/terraform.tfstate

  После этого можно переключаться между окружениями и убедиться,
  что в плане видны только ресурсы текущего окружения.

ЧЕГО НЕ ДЕЛАТЬ: WORKSPACES

  У Terraform есть механизм workspaces — несколько состояний
  в одном каталоге. Для разделения окружений он не подходит,
  и вот почему:

    * окружения оказываются «спрятаны» внутри одного состояния:
      нельзя дать разработчику доступ к dev, но не к prod;
    * нельзя задать разные бэкенды, разные версии провайдера
      и разные наборы переменных;
    * забыл переключить workspace — применил не туда. Ошибка
      тихая: terraform apply просто сработает в другом окружении.

  Workspaces годятся для временных копий: «сделать стенд на время
  эксперимента и удалить». Для dev и prod — отдельные состояния
  в отдельных ключах или бакетах.

И ЧТО ЕЩЁ ВАЖНО: ИМЕНА РЕСУРСОВ

  На живом стенде мы получили такую ошибку:

    Error: Error while requesting API to create subnet:
    code = AlreadyExists desc = Subnet with name app already exists

  Причина: модуль сети называл подсеть просто по ключу словаря —
  «app». Два окружения в одном каталоге столкнулись по имени.

  Лечится это на уровне модуля:

    resource "yandex_vpc_subnet" "this" {
      for_each = var.subnets

      name = "${var.network_name}-${each.key}"
    }

  Правило: если ресурс может существовать в двух окружениях
  в одном каталоге, имя должно включать окружение. Иначе рано
  или поздно окружения столкнутся.

------------------------------------------------------------------
2. ТЕСТЫ КОНФИГУРАЦИИ: TERRAFORM TEST
------------------------------------------------------------------

Terraform 1.6 добавил встроенный механизм проверки конфигурации.
Тест описывает, что должно получиться, а Terraform проверяет условия.

  # tests/basics.tftest.hcl
  variables {
    cloud_id       = "b1gtest0000000000000"
    folder_id      = "b1gtest0000000000001"
    sa_key_file    = "/tmp/test-key.json"
    ssh_public_key = "/tmp/test-key.pub"
    environment    = "dev"
    site_bucket    = "tf-test-bucket-000"
    create_app     = false
  }

  # Заглушка провайдера: обращения к облаку не происходят.
  mock_provider "yandex" {}

  run "network_is_created" {
    command = plan

    assert {
      condition     = module.vpc.subnet_count == 1
      error_message = "Модуль сети должен создать ровно одну подсеть."
    }
  }

Запуск:

  terraform test

  tests/basics.tftest.hcl... in progress
    run "network_is_created"... pass
    run "names_include_environment"... pass
    run "bucket_name_is_valid"... pass
    run "production_gets_more_resources"... pass
    run "dev_is_not_bigger_than_prod"... pass
    run "invalid_environment_is_rejected"... pass
    run "prod_protects_resources"... pass
  Success! 7 passed, 0 failed.

ЧТО ЗДЕСЬ ГЛАВНОЕ

  MOCK_PROVIDER. Строка mock_provider "yandex" {} означает, что
  провайдер не ходит в облако, а подставляет выдуманные значения.
  Тест выполняется за секунды, без ключей и без денег — а значит,
  его можно (и нужно) запускать в конвейере на каждый коммит.

  ДВА ВИДА ПРОВЕРОК:
    command = plan   — проверяем план, ничего не создавая;
    command = apply  — создаём реальные ресурсы, проверяем, удаляем.
  Второй вид нужен для того, что видно только после создания
  (например, что машина действительно получила адрес).

  РАЗНЫЕ ЗНАЧЕНИЯ В РАЗНЫХ ПРОВЕРКАХ — через блок variables
  внутри run: так проверяют и dev, и prod одним набором тестов.

  ОЖИДАЕМАЯ ОШИБКА проверяется блоком expect_failures: тест
  «падает правильно» — это тоже тест.

    run "invalid_environment_is_rejected" {
      command = plan

      variables {
        environment = "testing"
      }

      expect_failures = [var.environment]
    }

  ЧЕГО ЖДАТЬ ОТ ТЕСТОВ. Они не заменяют plan перед apply:
  тесты проверяют логику конфигурации (имена, условия, проверки
  переменных), а не инфраструктуру. Если тест прошёл, это значит
  «конфигурация непротиворечива», а не «всё создастся правильно».

------------------------------------------------------------------
3. ЛОВУШКА ШАБЛОНОВ: ДВОЙНОЙ ДОЛЛАР
------------------------------------------------------------------

Как только cloud-init стал шаблоном (templatefile), все подстановки
в нём обрабатывает Terraform, а не bash. И тут же вылезает ошибка,
которую мы получили на стенде:

  Error: Invalid function argument
  while calling templatefile(path, vars)
  Invalid value for "vars" parameter: vars map does not contain
  key "ZONE", referenced at ./cloud-init/app.yaml

Причина: в скрипте была строка

  printf '<p>Зона: %s</p>\n' "${ZONE##*/}"

Terraform увидел ${ZONE} и пошёл искать переменную ZONE в своей
конфигурации.

Правильно — удваивать доллар:

  printf '<p>Зона: %s</p>\n' "$${ZONE##*/}"

Опасность в том, что «поймать» это можно где угодно: Terraform
читает шаблон целиком, включая комментарии. Мы наступили на это
дважды — сначала в самой команде, потом в комментарии, который
объяснял эту же ошибку.

ПРАВИЛО: если файл передаётся в templatefile, все подстановки,
предназначенные оболочке внутри машины, удваиваются. Привычка
проверять `grep -n '\${' файл` перед первым запуском экономит
полчаса.

------------------------------------------------------------------
4. ФИКСАЦИЯ ПРОВАЙДЕРА ДЛЯ РАЗНЫХ ПЛАТФОРМ
------------------------------------------------------------------

Файл .terraform.lock.hcl фиксирует версию провайдера и его
контрольные суммы. Он должен попадать в репозиторий: тогда у всех
будет один и тот же провайдер.

Проблема: при установке через зеркало в файле оказываются суммы
только для вашей платформы. Если вы работаете в Windows, а конвейер
в Linux, установка провайдера в конвейере упадёт.

Лечится командой:

  terraform providers lock -platform=windows_amd64 -platform=linux_amd64

ЧТО МЫ ПРОВЕРИЛИ НА СТЕНДЕ

  Команда без указания зеркала падает:

    Error: Could not retrieve providers for locking
    Terraform failed to fetch the requested providers for linux_amd64
    - registry.terraform.io/yandex-cloud/yandex:
    host registry.terraform.io does not offer a Terraform provider registry

  Причина: providers lock НЕ использует настройки provider_installation
  из файла terraform.rc. Зеркало надо указать явно:

    terraform providers lock \
      -net-mirror=https://terraform-mirror.yandexcloud.net/ \
      -platform=windows_amd64 -platform=linux_amd64

    - Obtained yandex-cloud/yandex checksums for linux_amd64;
      Additional checksums for this platform are now tracked in the lock file
    Success! Terraform has updated the lock file.

  Запомните этот ключ: без него в конвейере провайдер не установится,
  и ошибка будет выглядеть как «проблема с реестром», хотя дело
  в отсутствии -net-mirror.

5. ЗАЩИТА ОТ РАЗРУШЕНИЯ
------------------------------------------------------------------

У Terraform две защиты, и они дополняют друг друга.

  ЗАЩИТА В КОНФИГУРАЦИИ — lifecycle.prevent_destroy:

    resource "yandex_compute_instance" "app" {
      # ...
      lifecycle {
        prevent_destroy = true
      }
    }

  Попытка удалить или заменить такой ресурс заканчивается ошибкой:

    Error: Instance cannot be destroyed
    Resource yandex_compute_instance.app[0] has lifecycle.prevent_destroy
    set, but the plan calls for this resource to be destroyed.

  ЗАЩИТА НА СТОРОНЕ ОБЛАКА — deletion_protection (проверяли
  в практике 6): ресурс не удалит ни Terraform, ни человек в консоли.

ЧТО ВАЖНО ЗНАТЬ ПРО prevent_destroy

  * Значение можно задать переменной (она известна до плана),
    но нельзя — вычисляемым значением из источника данных.
  * Защита срабатывает и при замене ресурса: замена — это удаление.
    Поэтому включённый prevent_destroy иногда мешает плановому
    обновлению, и его снимают на время.
  * В учебной конфигурации он выключен: иначе стенд не удалить
    командой terraform destroy.

Кроме технических защит, есть организационная — и она сильнее всех:
применение инфраструктуры только после того, как план прочитал
человек. Об этом следующий раздел.

------------------------------------------------------------------
6. КОНВЕЙЕР: ПРОВЕРКА, ПЛАН, ПРИМЕНЕНИЕ
------------------------------------------------------------------

Логика одинакова для GitLab CI, GitHub Actions и Jenkins:

  1. ПРОВЕРКА — fmt, validate, test. Быстро, без облака,
     на каждый коммит.
  2. ПЛАН — что именно изменится. Публикуется в обсуждение
     merge request или pull request.
  3. ПРИМЕНЕНИЕ — только вручную и только из основной ветки.

В материалах курса два готовых примера:

  files/08_production/ci/gitlab-ci.yml
  files/08_production/ci/github-actions.yml

ЧТО В НИХ СТОИТ РАЗОБРАТЬ

  ФИКСАЦИЯ ВЕРСИИ TERRAFORM. В конвейере указывается конкретная
  версия, а не «последняя»: иначе однажды сборка сломается сама
  по себе, без изменений в коде.

  СОХРАНЕНИЕ ПЛАНА. План считается один раз и сохраняется в файл:

    terraform plan -out=plan.tfplan

  Применяется именно этот файл:

    terraform apply plan.tfplan

  Так гарантируется, что применено то, что человек прочитал.
  Без этого между «показали план» и «применили» может пройти время,
  за которое кто-то другой изменит инфраструктуру — и применённый
  план окажется другим.

  СЕКРЕТЫ — В ЗАЩИЩЁННЫХ ПЕРЕМЕННЫХ CI. Ключи доступа к состоянию
  и идентификаторы облака лежат в переменных проекта (в GitLab —
  Settings → CI/CD → Variables, в GitHub — Secrets), а не в файлах.

  РУЧНОЙ ЗАПУСК ПРИМЕНЕНИЯ. В GitLab это when: manual, в GitHub —
  environment с обязательным одобрением. Автоматическое применение
  инфраструктуры на каждый коммит — почти всегда плохая идея.

  ЗАВИСИМОСТЬ ОТ ПЛАНА. Шаг apply берёт артефакт шага plan:
  если план не собрался, применение не начнётся.

ЧТО МОЖНО ПРОВЕРИТЬ БЕЗ КОНВЕЙЕРА

  Все команды, которые выполняет конвейер, стоит прогнать руками:

    terraform fmt -check -recursive
    terraform init -backend=false
    terraform validate
    terraform test
    terraform plan -input=false -out=plan.tfplan
    terraform show -no-color plan.tfplan

  Если они работают локально, конвейер почти наверняка соберётся.
  Если какая-то падает — она упадёт и в конвейере, только искать
  причину будет дольше.

7. ИТОГОВЫЙ СТЕНД КУРСА
------------------------------------------------------------------

Всё, что мы делали по курсу, собрано в одну конфигурацию
(files/08_production). Она разворачивается одной командой:

  terraform init -backend-config=env/backend-dev.tfvars
  terraform apply -var-file=env/dev.tfvars

Что создаётся:

  * сеть и подсеть с группой безопасности (из модуля практики 3);
  * машина приложения с инициализацией через cloud-init;
  * бакет со статическим сайтом.

Что получается в выводе:

  app_external_ip = "158.160.177.75"
  site_endpoint   = "tf-final-dev-site-p8-2026.website.yandexcloud.net"

  environment   = "dev"
  name_prefix   = "tf-final-dev"
  app_cores     = 2
  app_memory    = 2
  preemptible   = true

Проверка приложения:

  curl -s http://158.160.177.75/
  <h1>Стенд поднят Terraform</h1>
  <p>Окружение: dev</p>
  <p>Внешний адрес: 158.160.177.75</p>
  <p>Имя машины: fv4oka5a2hj8merc10iu.auto.internal</p>
  <p>Зона: ru-central1-d</p>

Проверка сайта:

  curl -s http://tf-final-dev-site-p8-2026.website.yandexcloud.net/
  <h1>Статический сайт итогового стенда</h1>
  <p>Окружение: <strong>dev</strong></p>

Обратите внимание: и страница машины, и страница сайта показывают
окружение. Это не украшение, а проверка: если вы запутались
в окружениях, страница скажет об этом сразу.

Уборка:

  terraform destroy -var-file=env/dev.tfvars
  terraform init -backend-config=env/backend-prod.tfvars -reconfigure
  terraform destroy -var-file=env/prod.tfvars

------------------------------------------------------------------
8. ЧТО ДЕЛАТЬ, КОГДА ИНФРАСТРУКТУРА РАСТЁТ
------------------------------------------------------------------

На курсе всё помещается в один каталог. В работе так не бывает,
и вот что делают, когда конфигурация разрастается.

  РАЗДЕЛЕНИЕ НА СЛОИ (layers). Сеть живёт отдельно от приложений,
  приложения — отдельно от данных: у каждого слоя своё состояние.

    network/    сети, подсети, группы безопасности, DNS
    data/       базы данных, бакеты с данными
    apps/       машины, Kubernetes, приложения

  Слои связываются выводами: одному слою нужен идентификатор сети
  из другого. Два способа:

    data "terraform_remote_state" "network" {
      backend = "s3"

      config = {
        endpoints = { s3 = "https://storage.yandexcloud.net" }
        bucket    = "tf-course-state-ivan"
        key       = "network/terraform.tfstate"
        region    = "ru-central1"
      }
    }

    # использование
    subnet_id = data.terraform_remote_state.network.outputs.subnet_id

  или источники данных облака (по имени ресурса):

    data "yandex_vpc_network" "this" {
      name = "prod-net"
    }

  Первый способ надёжнее: имя ресурса может измениться, ключ состояния —
  нет. Второй проще и не требует доступа к бакету со стороны.

  ЗАЧЕМ РАЗДЕЛЯТЬ. Разные скорости изменений: сеть меняется раз
  в полгода, приложения — каждый день. Общее состояние заставляет
  пересчитывать всё сразу и увеличивает риск: ошибка в описании
  приложения может задеть сеть.

  ЧЕГО НЕ ДЕЛАТЬ: не дробите ради дробления. Пять состояний для
  учебного стенда — это пять мест, где нужно не забыть обновить
  конфигурацию.

------------------------------------------------------------------
9. РАБОТА С СУЩЕСТВУЮЩЕЙ ИНФРАСТРУКТУРОЙ
------------------------------------------------------------------

Реальность: инфраструктура уже есть, и она не описана в Terraform.

Порядок действий:

  1. Начать с ЧТЕНИЯ, а не с записи: собрать список ресурсов
     (yc ... list), понять зависимости, нарисовать схему.
  2. Импортировать по одному ресурсу, начиная с самых «нижних»
     (сеть, затем подсети, затем машины).
  3. После каждого импорта — проверять, что план пуст. Пустой план
     означает, что описание совпало с реальностью, и ничего
     не сломается.
  4. Только после этого менять что-то через Terraform.

  terraform import yandex_vpc_network.prod enpXXXXXXXXXXXX
  terraform plan   # должен быть пустым

Или блоками import (практика 2) — они предпочтительнее, потому что
остаются в истории изменений.

ЧЕГО НЕ ДЕЛАТЬ: не запускать apply, когда план показывает изменения
в чужих ресурсах, которые вы только что импортировали. Сначала
привести описание к реальности, потом менять.

------------------------------------------------------------------
10. ОБНОВЛЕНИЕ ПРОВАЙДЕРА БЕЗ СЮРПРИЗОВ
------------------------------------------------------------------

Провайдер обновляют осознанно, а не «за компанию с terraform init».

  1. Посмотреть доступные версии и changelog провайдера.
  2. Изменить ограничение версии в required_providers.
  3. Удалить (или обновить) .terraform.lock.hcl:
       terraform init -upgrade
  4. Пересчитать суммы для всех платформ:
       terraform providers lock -net-mirror=... -platform=... -platform=...
  5. Выполнить terraform plan и ПРОЧИТАТЬ его целиком: обновление
     провайдера иногда меняет поведение ресурсов (например, поле
     становится вычисляемым или появляется замена).
  6. Применить в dev, посмотреть, затем в prod.

Совет: обновление провайдера — отдельный merge request. Смешивать
его с изменением инфраструктуры нельзя: если что-то сломается,
не будет понятно, что именно.

------------------------------------------------------------------
11. СТОИМОСТЬ КАК ПАРАМЕТР КОНФИГУРАЦИИ
------------------------------------------------------------------

Инфраструктура как код хороша ещё и тем, что расходы можно
планировать заранее.

  * Прерываемые машины и core_fraction = 20 — для dev.
  * Минимальные пресеты баз данных и диски нужного размера, не «на вырост».
  * Политики очистки реестра образов и жизненного цикла бакетов.
  * Удаление стенда после занятий и проверка: yc compute instance list,
    yc vpc address list, yc storage bucket list.

Полезная привычка: в выводе конфигурации показывать сводку
(summary), чтобы перед применением видеть, какие параметры
выбраны для окружения, и не перепутать dev с prod.

  output "summary" {
    value = {
      environment = var.environment
      name_prefix = local.name_prefix
      app_cores   = local.app_cores
      preemptible = var.preemptible
    }
  }

  terraform plan показывает эту сводку в разделе Changes to Outputs —
  то есть расходы видны ещё до применения.

12. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

  СИМПТОМ: два окружения в одном каталоге сталкиваются по именам
  («Subnet with name app already exists»)
  ПРИЧИНА: имена ресурсов не включают окружение.
  ЧТО ДЕЛАТЬ: добавить префикс окружения в имена — лучше внутри
  модуля, а не в каждом вызове.

  СИМПТОМ: изменения dev видны в prod (или наоборот)
  ПРИЧИНА: оба окружения используют один и тот же ключ состояния.
  ЧТО ДЕЛАТЬ: разные ключи (или разные бакеты), проверять
  terraform init -backend-config=... перед работой.

  СИМПТОМ: terraform init предлагает перенести состояние
  ПРИЧИНА: изменились настройки бэкенда, а ключ не указан.
  ЧТО ДЕЛАТЬ: для переключения окружений — -reconfigure;
  -migrate-state нужен только тогда, когда вы действительно
  переносите состояние.

  СИМПТОМ: в конвейере провайдер не устанавливается, хотя локально
  всё работает
  ПРИЧИНА: в .terraform.lock.hcl нет сумм для платформы конвейера.
  ЧТО ДЕЛАТЬ: terraform providers lock -platform=linux_amd64
  (и -net-mirror при работе через зеркало).

  СИМПТОМ: Invalid value for "vars" parameter, vars map does not
  contain key ...
  ПРИЧИНА: в шаблоне templatefile осталась подстановка, которая
  предназначена оболочке внутри машины (например, подстановка
  переменной ZONE).
  ЧТО ДЕЛАТЬ: удвоить доллар ($${ZONE}). Проверять и команды,
  и комментарии в шаблоне.

  СИМПТОМ: тест конфигурации пытается создать ресурсы в облаке
  ПРИЧИНА: в тесте указано command = apply либо не подключён
  mock_provider.
  ЧТО ДЕЛАТЬ: для проверок логики — command = plan и mock_provider.

  СИМПТОМ: terraform destroy не удаляет ресурсы в prod
  ПРИЧИНА: prevent_destroy или deletion_protection.
  ЧТО ДЕЛАТЬ: снять защиту, применить изменение, затем удалять.
  Это правильное поведение — именно оно спасает от случайного
  удаления.

  СИМПТОМ: apply применил не тот план, который обсуждали
  ПРИЧИНА: план считался заново, а не взят сохранённый.
  ЧТО ДЕЛАТЬ: terraform plan -out=plan.tfplan и terraform apply
  plan.tfplan; в конвейере передавать план артефактом.

13. ЗАДАНИЯ
------------------------------------------------------------------

  1. Окружения. Добавьте третье окружение stage: свой файл значений,
     свой ключ состояния. Убедитесь, что все три состояния
     независимы.

  2. Тесты. Допишите тест, который проверяет, что имя бакета
     в prod содержит слово prod. Запустите terraform test
     и убедитесь, что он ловит нарушение.

  3. Лок-файл. Добавьте в .terraform.lock.hcl суммы для платформы
     linux_amd64 и объясните, почему без этого конвейер на Linux
     не соберётся.

  4. Конвейер. Возьмите пример из ci/ и адаптируйте под свой
     репозиторий: включите шаги fmt, validate, test и plan.
     Шаг apply сделайте ручным.

  5. Защита. Включите prevent_destroy для машины приложения
     и убедитесь, что terraform destroy отказывается работать.
     Объясните, как теперь удалить стенд.

  6. План в обсуждении. Настройте публикацию плана в обсуждении
     merge request (в GitLab это artifact + отчёт, в GitHub —
     комментарий). Опишите, что должен проверить ревьюер в плане.

  7. Итог. Разверните итоговый стенд в dev, проверьте страницу
     приложения и сайт, затем удалите всё и убедитесь командами yc,
     что в облаке не осталось ресурсов.
