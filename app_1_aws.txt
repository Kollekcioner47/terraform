ПРИЛОЖЕНИЕ 1. ТО ЖЕ САМОЕ В AWS

Зачем это приложение

  Terraform везде одинаков, а провайдеры разные. Выучив работу
  с состоянием, циклами, модулями и планом, вы переносите навык
  в другое облако — переучиваться приходится только на имена
  ресурсов, модель прав и способ аутентификации.

  Здесь собрано сопоставление «как в Яндекс Облаке — как в AWS»
  и то, что действительно отличается, а не просто называется иначе.

Что в этом приложении проверено, а что нет

  Версии провайдеров и модулей, аргументы бэкенда и поведение
  блокировки состояния проверены по официальной документации
  (даты указаны). Общие рекомендации отмечены как практика.

  Материал этого приложения НЕ проверялся в живом AWS: аккаунта
  у автора курса нет. Всё, что здесь написано, — пересказ
  документации, а не результат прогона. В Яндекс Облаке каждый шаг
  курса проверен на стенде.


========================================================================
1. ПРОВАЙДЕР
========================================================================

  terraform {
    required_version = ">= 1.6.3"

    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 6.66.0"
      }
    }
  }

  provider "aws" {
    region = var.region
  }

Отличия от Яндекс Облака, которые сразу бросаются в глаза:

  * провайдер публикуется HashiCorp, а не самим облаком;
  * модули и провайдеры лежат в публичном реестре Terraform,
    зеркало не обязательно;
  * изоляция — аккаунт и регион, а не «облако и каталог»;
  * аутентификация настраивается не ключом в файле, а переменными
    окружения или ролью: ключи доступа в коде — антипаттерн.

ПРИНЦИПАЛЬНАЯ РАЗНИЦА В АУТЕНТИФИКАЦИИ

  Яндекс Облако: сервисный аккаунт + авторизованный ключ (файл)
  или IAM-токен.

  AWS: IAM-пользователь с ключами (плохо), IAM-роль для сервиса
  (хорошо) или IAM-роль через федерацию (лучше всего — короткоживущие
  учётные данные без хранения секретов вообще).

  Практический вывод: в AWS «правильный» способ не требует хранения
  ключей, поэтому конфигурация выглядит проще — но настроить роль
  сложнее, чем выпустить ключ. В конвейере это делается через
  федерацию удостоверений (OIDC).


========================================================================
2. СОПОСТАВЛЕНИЕ РЕСУРСОВ
========================================================================

  Изоляция
      Яндекс Облако: облако + каталог (cloud_id, folder_id)
      AWS:           аккаунт + регион (account_id, region)

  Зона доступности
      Яндекс Облако: zone = "ru-central1-d"
      AWS:           availability_zone = "eu-west-1a"

      Имена зон не переносятся: у каждого облака свои. В AWS зона
      выбирается у подсети, а инстанс попадает в зону своей подсети —
      как и в Яндекс Облаке.

  Сеть
      Яндекс Облако: yandex_vpc_network
      AWS:           aws_vpc

  Подсеть
      Яндекс Облако: yandex_vpc_subnet
      AWS:           aws_subnet

  Группа безопасности
      Яндекс Облако: yandex_vpc_security_group
                     + yandex_vpc_security_group_rule
      AWS:           aws_security_group
                     + aws_vpc_security_group_ingress_rule
                     + aws_vpc_security_group_egress_rule

      В AWS правила отдельными ресурсами — актуальная рекомендация
      провайдера, и это тот же приём, что мы разбирали в практике 5:
      одно правило = один ресурс (в AWS ещё и один CIDR на правило).

  Виртуальная машина
      Яндекс Облако: yandex_compute_instance
      AWS:           aws_instance

  Образ
      Яндекс Облако: data.yandex_compute_image (по family)
      AWS:           data.aws_ami (по owner и фильтру)

      В AWS образы ищут по владельцу (owner) и фильтрам, потому что
      публичных «семейств» в том же смысле там нет.

  Диск
      Яндекс Облако: yandex_compute_disk
      AWS:           aws_ebs_volume

  Статический адрес
      Яндекс Облако: yandex_vpc_address
      AWS:           aws_eip

  Объектное хранилище
      Яндекс Облако: yandex_storage_bucket, yandex_storage_object
      AWS:           aws_s3_bucket и модуль terraform-aws-modules/s3-bucket

  Секреты
      Яндекс Облако: yandex_lockbox_secret
      AWS:           aws_secretsmanager_secret
                     или aws_ssm_parameter (SecureString)

  Ключ шифрования
      Яндекс Облако: yandex_kms_symmetric_key
      AWS:           aws_kms_key

  Managed-база данных
      Яндекс Облако: yandex_mdb_postgresql_cluster
      AWS:           aws_db_instance или aws_rds_cluster

  Kubernetes
      Яндекс Облако: yandex_kubernetes_cluster
                     + yandex_kubernetes_node_group
      AWS:           aws_eks_cluster
                     + aws_eks_node_group
                     или модуль terraform-aws-modules/eks/aws

  Сетевой балансировщик
      Яндекс Облако: yandex_lb_network_load_balancer
      AWS:           aws_lb (тип network)

  Прикладной балансировщик
      Яндекс Облако: yandex_alb_load_balancer и четыре ресурса вокруг
      AWS:           aws_lb (тип application) + aws_lb_listener
                     + aws_lb_target_group + aws_lb_listener_rule

      Обратите внимание: в AWS прикладной и сетевой балансировщики —
      это один ресурс с разным type, а в Яндекс Облаке — разные
      ресурсы с разными наборами вложенных блоков.


========================================================================
3. СОСТОЯНИЕ В AWS: S3 И БЛОКИРОВКА
========================================================================

  terraform {
    backend "s3" {
      bucket       = "my-terraform-state"
      key          = "prod/terraform.tfstate"
      region       = "eu-west-1"

      # Нативная блокировка состояния: Terraform создаёт рядом
      # с состоянием объект <ключ>.tflock.
      use_lockfile = true

      # Шифрование состояния на стороне сервера.
      encrypt = true
    }
  }

ГЛАВНОЕ ОТЛИЧИЕ ОТ СТАРЫХ КУРСОВ

  Раньше для блокировки состояния в AWS создавали таблицу DynamoDB
  и указывали её в параметре dynamodb_table. С версии Terraform 1.11
  этот способ объявлен устаревшим:

    DynamoDB-based locking is deprecated and will be removed
    in a future minor version.

  Поэтому в новых конфигурациях:

    * dynamodb_table НЕ указывают;
    * отдельную таблицу DynamoDB НЕ создают;
    * блокировка обеспечивается параметром use_lockfile = true
      (Terraform 1.10 и новее), как и в Яндекс Облаке.

  Ирония в том, что документация Яндекс Облака отстаёт ровно так же:
  она до сих пор описывает блокировку через YDB и таблицу LockID.
  В обеих ситуациях вывод одинаковый: смотрите на версию Terraform,
  а не только на документацию облака.

ПРАВА ДЛЯ БЛОКИРОВКИ

  Для работы use_lockfile нужны права на объект-замок:
  s3:GetObject, s3:PutObject, s3:DeleteObject на
  arn:aws:s3:::<бакет>/<ключ>.tflock. Права на удаление самого
  состояния не требуются — Terraform его не удаляет.

ЧЕГО НЕТ В ЯНДЕКС ОБЛАКЕ

  Параметра encrypt: шифрование бакета состояния в Object Storage
  настраивается на самом бакете (server_side_encryption_configuration
  с ключом KMS). В AWS тот же результат дают encrypt = true
  и kms_key_id.

  Флагов skip_*: в AWS они не нужны, потому что S3 полностью
  совместим сам с собой. В Яндекс Облаке без них бэкенд не работает.


========================================================================
4. ИДЕНТИЧНОСТЬ И ПРАВА
========================================================================

Как это выглядит в AWS:

  # Роль, которой будет пользоваться сервис (например, EC2)
  resource "aws_iam_role" "app" {
    name = "app-role"

    assume_role_policy = jsonencode({
      Version = "2012-10-17"
      Statement = [{
        Effect    = "Allow"
        Principal = { Service = "ec2.amazonaws.com" }
        Action    = "sts:AssumeRole"
      }]
    })
  }

  # Профиль экземпляра: то, что подключается к машине
  resource "aws_iam_instance_profile" "app" {
    role = aws_iam_role.app.name
  }

  # Права роли
  resource "aws_iam_role_policy" "app" {
    role = aws_iam_role.app.id

    policy = jsonencode({
      Version = "2012-10-17"
      Statement = [{
        Effect   = "Allow"
        Action   = ["s3:GetObject"]
        Resource = "arn:aws:s3:::my-bucket/*"
      }]
    })
  }

Сопоставление понятий:

  Яндекс Облако                          AWS
  сервисный аккаунт                      IAM-роль
  авторизованный ключ сервисного аккаунта ключи IAM-пользователя
  IAM-токен (до 12 часов)                временные учётные данные STS
  роли на каталог                        политики на ресурс
  iam.serviceAccounts.user               iam:PassRole
  сервисный аккаунт на машине            профиль экземпляра

  Ключевое отличие в модели: в Яндекс Облаке роли вешают на каталог
  (папку), а в AWS — на конкретный ресурс через политику. Поэтому
  в AWS «выдать права на бакет» — это отдельная политика с ARN,
  а не роль на каталог.

  Общее правило одинаково в обоих облаках: чем уже права, тем меньше
  последствия ошибки. В курсе мы выдавали узкие роли
  (compute.editor, vpc.user) вместо editor — в AWS это
  соответствует политике на конкретные действия вместо
  AdministratorAccess.


========================================================================
5. МОДУЛИ: ГДЕ ИХ БЕРУТ
========================================================================

В AWS модули публикуются в реестре Terraform, и это меняет форму
подключения: версия указывается отдельным аргументом version,
а не через ?ref=, как при установке из git.

  Проверенные актуальные версии:

    terraform-aws-modules/vpc/aws            6.7.3
    terraform-aws-modules/eks/aws           21.26.0
    terraform-aws-modules/rds/aws            7.2.2
    terraform-aws-modules/security-group/aws 6.0.0
    terraform-aws-modules/s3-bucket/aws      5.16.1

  Пример вызова:

    module "vpc" {
      source  = "terraform-aws-modules/vpc/aws"
      version = "6.7.3"

      name = "app-vpc"
      cidr = "10.0.0.0/16"

      azs             = ["eu-west-1a", "eu-west-1b"]
      private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
      public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]

      enable_nat_gateway = true
    }

  Сравните с Яндекс Облаком:

    module "vpc" {
      source = "git::https://github.com/terraform-yc-modules/terraform-yc-vpc?ref=1.0.9"
    }

  Разница только в способе доставки модуля. Смысл одинаковый:
  не писать сеть руками.

  Из этого следует практический вывод для курса: привычка «сначала
  посмотри, есть ли готовый модуль» работает в любом облаке. Свой
  модуль пишут тогда, когда готовый не подходит по составу ресурсов
  или по внутренним правилам компании.


========================================================================
6. СЕКРЕТЫ: SECRETS MANAGER И PARAMETER STORE
========================================================================

В AWS два сервиса, и их часто путают.

  SSM PARAMETER STORE — хранилище параметров: String, StringList,
  SecureString. Подходит для конфигурации: адреса, имена, флаги,
  размеры. Ротации у параметров нет («Credential rotation: None»),
  стандартный уровень бесплатный.

  SECRETS MANAGER — хранилище секретов: пароли баз данных, ключи API,
  токены. Умеет автоматическую ротацию (через Lambda), шифрует
  значения ключом KMS, платный (за секрет в месяц и за обращения).

  Документация AWS отвечает на вопрос выбора прямо: для паролей,
  ключей и токенов рекомендуется Secrets Manager, а Parameter Store —
  для параметров конфигурации.

  Это соответствует паре «Lockbox + обычные переменные» в Яндекс
  Облаке: секреты в Lockbox, остальное — в переменных и тегах.

ТА ЖЕ ЛОВУШКА, ЧТО И В ЯНДЕКС ОБЛАКЕ

  Секрет, переданный аргументом ресурса, попадает в файл состояния
  в открытом виде. Это не особенность Яндекс Облака, а свойство
  Terraform: состояние хранит значения всех атрибутов.

    resource "aws_secretsmanager_secret_version" "db" {
      secret_id     = aws_secretsmanager_secret.db.id
      secret_string = var.db_password   # <-- окажется в состоянии
    }

  Что с этим делают:

    * ограничивают доступ к состоянию (шифрование, права, отдельный
      бакет для prod);
    * используют write-only аргументы — механизм, при котором
      значение передаётся в облако, но не сохраняется в состоянии
      (поддерживается провайдерами, которые его реализовали);
    * создают секреты вне Terraform (в консоли, в CLI, в системе
      управления секретами) и читают их источником данных только
      там, где это действительно нужно.

  Запомните главный вывод практики 6, он верен для всех облаков:
  вопрос не «какой сервис секретов выбрать», а «кто имеет доступ
  к файлу состояния».


========================================================================
7. KUBERNETES В AWS
========================================================================

  Сопоставление:

    Яндекс Облако: Managed Service for Kubernetes
    AWS:           Elastic Kubernetes Service (EKS)

    yandex_kubernetes_cluster      ↔ aws_eks_cluster
    yandex_kubernetes_node_group   ↔ aws_eks_node_group

  Через модуль:

    module "eks" {
      source  = "terraform-aws-modules/eks/aws"
      version = "21.26.0"

      cluster_name    = "app-cluster"
      cluster_version = "1.35"

      vpc_id     = module.vpc.vpc_id
      subnet_ids = module.vpc.private_subnets
    }

ЧТО ПРИНЦИПИАЛЬНО ОТЛИЧАЕТСЯ

  * В AWS узлы EKS обычно работают от управляемой группы, а права
    узлам выдаются через роли и профили экземпляров. В Яндекс Облаке
    это два сервисных аккаунта (кластера и узлов) с ролями
    на каталог — как в практике 7.
  * В AWS есть IAM Roles for Service Accounts: под получает права
    через сервисный аккаунт Kubernetes. В Яндекс Облаке аналогичный
    механизм устроен иначе.
  * Модули: в AWS кластер обычно собирают модулем целиком (VPC + EKS
    вместе), в Яндекс Облаке модули сети и кластера раздельные.

  Общее: мастер платный (в AWS — за часы работы управляющей части),
  узлы — обычные машины, и кластер стоит денег круглосуточно.
  Привычка «не держать кластер между занятиями» одинакова.


========================================================================
8. ЧТО ПЕРЕНОСИТСЯ, А ЧТО НЕТ
========================================================================

  ПЕРЕНОСИТСЯ ПОЛНОСТЬЮ

    * цикл init → plan → apply и чтение плана;
    * понятие состояния, блокировка, импорт, moved и removed;
    * переменные, locals, циклы, dynamic-блоки, модули;
    * структура репозитория и разделение окружений;
    * конвейер: fmt → validate → test → plan → apply вручную;
    * правило «секрет из состояния никуда не денется»;
    * привычка проверять план перед применением.

  ПЕРЕПИСЫВАЕТСЯ ПРИ ПЕРЕЕЗДЕ

    * имена ресурсов и аргументы (их не угадать — только документация);
    * аутентификация и роли;
    * настройки бэкенда (endpoint, skip-флаги, encrypt);
    * образы и их поиск;
    * зоны и регионы;
    * подход к модулям (git с ?ref= против реестра с version).

  НЕ ПЕРЕНОСИТСЯ ВООБЩЕ

    * конкретные идентификаторы ресурсов;
    * файл состояния: состояние одного облака нельзя «перенести»
      в другое, инфраструктуру там придётся создавать заново;
    * имена зон и типов машин: s2.micro и t3.micro — разные вещи.

ПРАКТИЧЕСКИЙ ВЫВОД

  Переезд между облаками — это не «поменять provider и имена».
  Это переписывание ресурсов с проверкой каждого шага: сеть,
  машины, данные, права. Состояние при этом начинается с нуля,
  а старая инфраструктура живёт, пока новая не будет проверена.
