ПРИЛОЖЕНИЕ 2. ТО ЖЕ САМОЕ В VK CLOUD

Зачем это приложение

  VK Cloud — облако, построенное на OpenStack. Это видно и в провайдере:
  имена ресурсов начинаются с vkcs_, а внутри — сущности Neutron,
  Nova, Barbican. Понимание «как это же делается в VK Cloud» полезно
  тем, кто работает с российскими облаками и хочет видеть общее
  между ними.

Что проверено, а что нет

  Версии провайдера, имена ресурсов и аргументы в этом приложении
  взяты из документации провайдера версии 0.17.3 (проверено
  по репозиторию и реестру Terraform).

  Материал НЕ проверялся в живом облаке VK Cloud: доступа к нему
  у автора курса нет. Всё, что здесь написано, — пересказ
  документации. Отдельно отмечено то, что в документации
  подтверждения не нашло: этого в курсе лучше не повторять
  как факт.

ОБЩЕЕ С ЯНДЕКС ОБЛАКОМ

  Terraform один и тот же: init, plan, apply, состояние, модули,
  циклы. Отличаются провайдер, аутентификация и имена ресурсов.
  Блокировка состояния и бэкенд — тоже S3-совместимые.


========================================================================
1. ПРОВАЙДЕР: ВНИМАНИЕ К ИМЕНИ
========================================================================

Провайдер называется vk-cs/vkcs — с дефисом в названии организации:

  terraform {
    required_version = ">= 1.6.3"

    required_providers {
      vkcs = {
        source  = "vk-cs/vkcs"
        version = "~> 0.17.3"
      }
    }
  }

  ПОЧЕМУ ЭТО ВАЖНО. В старых конспектах и статьях встречается адрес
  vkcs/vkcs — такого провайдера в реестре НЕ СУЩЕСТВУЕТ, запрос
  к реестру возвращает «не найдено». Если Terraform пишет

    Failed to query available provider packages
    Could not retrieve the list of available versions for provider
    vkcs/vkcs

  первым делом проверьте источник: правильно — vk-cs/vkcs.

  Проверка текущей версии — в реестре Terraform или в релизах
  репозитория провайдера. На момент написания курса актуальна 0.17.3.

  Требования к Terraform: документация провайдера говорит
  о Terraform 1.1.5 и новее. Для параметра endpoints в блоке backend
  нужен Terraform 1.6 и новее (как и в Яндекс Облаке).


========================================================================
2. АУТЕНТИФИКАЦИЯ
========================================================================

Провайдер работает с проектом OpenStack, а не с «сервисным аккаунтом»:

  provider "vkcs" {
    username     = var.username        # пользователь проекта
    password     = var.password        # его пароль
    project_id   = var.project_id
    region       = "ru-msk"
    auth_url     = "https://infra.mail.ru:35357/v3/"  # адрес Keystone
  }

УДОБНЫЙ ПРИЁМ: файл конфигурации из консоли

  В настройках проекта есть вкладка Terraform — оттуда скачивается
  готовый файл vkcs_provider.tf, в котором уже подставлены username,
  project_id, region и auth_url. Останется дописать пароль.
  Это самый быстрый способ не ошибиться в адресе Keystone.

ЧЕМ ЭТО ОТЛИЧАЕТСЯ ОТ ЯНДЕКС ОБЛАКА

  Яндекс Облако: сервисный аккаунт, авторизованный ключ (файл)
  или IAM-токен. Роли на каталог.

  VK Cloud: пользователь проекта, пароль, идентификатор проекта
  и адрес службы аутентификации. Права — на уровне проекта.

  Практический вывод: в VK Cloud конфигурация изначально содержит
  долгоживущий пароль, поэтому требования к хранению секретов выше:
  переменные окружения или хранилище секретов, но не файл в
  репозитории.

  Есть и способ без пароля — временный access_token, но он живёт
  около часа и не обновляется автоматически, поэтому для конвейера
  он годится только с отдельным шагом получения нового токена.
  Документация рекомендует для долгой работы аутентификацию
  по учётным данным.

ЧТО НЕ ПОДТВЕРЖДЕНО

  Переменные окружения вида VKCS_USERNAME, VKCS_PASSWORD и им
  подобные в документации провайдера не упомянуты. Подтверждены
  только OS_AUTH_TOKEN и OS_PASSWORD (общие для OpenStack).
  Не пишите VKCS_* в конфигурацию, не проверив: скорее всего,
  они просто не читаются.

  Поддержки application credentials (Application Credential ID/Secret)
  в схеме провайдера нет: поддерживаются username/password
  и access_token.


========================================================================
3. СОСТОЯНИЕ: S3-СОВМЕСТИМЫЙ БЭКЕНД
========================================================================

VK Cloud предоставляет S3-совместимое объектное хранилище, поэтому
бэкенд тот же — s3, но с двумя особенностями: обязательные skip-флаги
и явный endpoint.

  terraform {
    backend "s3" {
      endpoints = {
        s3 = "https://hb.ru-msk.vkcloud-storage.ru"
      }

      bucket = "terraform-state"
      region = "ru-msk"
      key    = "prod/terraform.tfstate"

      skip_region_validation      = true
      skip_credentials_validation = true

      # Нативная блокировка состояния (Terraform 1.10 и новее).
      # В документации провайдера приводится именно этот приём.
      use_lockfile = true
    }
  }

ЧТО ЗДЕСЬ ЗНАКОМО

  Всё, кроме адреса и региона, мы уже видели в Яндекс Облаке:
  бэкенд s3, skip-флаги, use_lockfile, ключ состояния с путём
  к окружению.

ЧТО ЗАПОМНИТЬ

  * Схема «S3 + отдельная таблица для блокировок» (как DynamoDB
    в AWS или YDB в Яндекс Облаке) уходит в прошлое: достаточно
    use_lockfile.
  * Endpoint и region у каждого облака свои, переносить их между
    конфигурациями нельзя.
  * Бакет для состояния стоит создавать в том же облаке, где живёт
    инфраструктура: ближе по сети и проще с правами.


========================================================================
4. БАЗОВЫЕ РЕСУРСЫ
========================================================================

  resource "vkcs_networking_network" "app" {
    name = "app-net"

    # SDN — программно-определяемая сеть: neutron (классическая)
    # или sprut (новая). По умолчанию берётся та, что в проекте.
    sdn = "neutron"
  }

  resource "vkcs_networking_subnet" "app" {
    name       = "app-subnet"
    network_id = vkcs_networking_network.app.id
    cidr       = "10.10.0.0/24"
  }

  resource "vkcs_networking_secgroup" "app" {
    name = "app-sg"

    # Правила, созданные облаком по умолчанию (обычно разрешающий
    # egress), Terraform не контролирует, пока этот флаг не включён.
    # Если правила должны управляться полностью — включите.
    delete_default_rules = true
  }

  resource "vkcs_networking_secgroup_rule" "ssh" {
    direction         = "ingress"
    ethertype         = "IPv4"
    protocol          = "tcp"
    port_range_min    = 22
    port_range_max    = 22
    remote_ip_prefix  = "0.0.0.0/0"
    security_group_id = vkcs_networking_secgroup.app.id
  }

  resource "vkcs_compute_instance" "app" {
    name = "app-vm"

    # В VK Cloud зона доступности и класс машины ОБЯЗАТЕЛЬНЫ.
    availability_zone = "MS1"
    flavor_id         = data.vkcs_compute_flavor.basic.id

    block_device {
      uuid                  = data.vkcs_images_image.debian.id
      source_type           = "image"
      destination_type      = "volume"
      volume_size           = 10
      boot_index            = 0
      delete_on_termination = true
    }

    network {
      uuid = vkcs_networking_network.app.id
    }

    security_group_ids = [vkcs_networking_secgroup.app.id]

    # Сеть должна быть подключена к роутеру — иначе у машины
    # не будет выхода наружу. Порядок задаётся явно.
    depends_on = [vkcs_networking_router_interface.app]
  }

ЧТО БРОСАЕТСЯ В ГЛАЗА ПОСЛЕ ЯНДЕКС ОБЛАКА

  * Имена классов машин (flavor) и образов берутся источниками
    данных: data.vkcs_compute_flavor, data.vkcs_images_image.
    В Яндекс Облаке мы брали образ по семейству, а пресет писали
    строкой (s2.micro).
  * Диск описывается внутри машины блоком block_device, а не
    отдельным ресурсом. В Яндекс Облаке boot_disk и дополнительный
    диск — разные сущности.
  * Правила группы безопасности — отдельные ресурсы, как и в нашем
    курсе (мы делали так же с yandex_vpc_security_group_rule).
  * Сеть нужно явно подключить к роутеру: без этого нет выхода
    в интернет. В Яндекс Облаке эту задачу решает NAT-шлюз
    и таблица маршрутизации (практика 4).


========================================================================
5. MANAGED-СЕРВИСЫ
========================================================================

БАЗЫ ДАННЫХ (DBaaS)

  vkcs_db_instance    — одиночный экземпляр базы;
  vkcs_db_cluster     — кластер (для PostgreSQL и других СУБД);
  vkcs_db_database, vkcs_db_user — база и пользователь;
  vkcs_db_config_group — группа настроек (аналог параметров кластера).

  Сопоставление с Яндекс Облаком:

    yandex_mdb_postgresql_cluster  ↔ vkcs_db_cluster
    yandex_mdb_postgresql_database ↔ vkcs_db_database
    yandex_mdb_postgresql_user     ↔ vkcs_db_user

  Общее: база создаётся в подсети, нужна группа безопасности,
  и всё это платно круглосуточно.

KUBERNETES

  Здесь важное предупреждение из документации. У ресурсов Kubernetes
  есть два поколения:

    vkcs_kubernetes_cluster      — ПЕРВОЕ поколение;
    vkcs_kubernetes_node_group   — ПЕРВОЕ поколение;

  про них документация говорит прямо: «должны использоваться только
  для кластеров первого поколения и НЕ должны использоваться
  для новых развёртываний». В новых конфигурациях применяют:

    vkcs_kubernetes_cluster_v2
    vkcs_kubernetes_node_group_v2

  Две особенности кластера v2:

  1. Сеть обязана быть на SDN Sprut (sdn = "sprut"), иначе сетевая
     подсистема кластера (CNI) не заработает.
  2. Подсеть должна быть подключена к роутеру до создания кластера —
     отсюда depends_on на vkcs_networking_router_interface.

  Сопоставление:

    yandex_kubernetes_cluster    ↔ vkcs_kubernetes_cluster_v2
    yandex_kubernetes_node_group ↔ vkcs_kubernetes_node_group_v2

  Проверить, какой SDN доступен в проекте, можно источником данных
  vkcs_networking_sdn. Если Sprut недоступен — это вопрос к поддержке
  облака, своими силами его не включить.


========================================================================
6. СЕКРЕТЫ: KEY MANAGER
========================================================================

Аналог Lockbox в VK Cloud — Key Manager (совместим с OpenStack
Barbican):

  resource "vkcs_keymanager_secret" "db_password" {
    name        = "db-password"
    secret_type = "opaque"

    payload        = var.db_password
    payload_content_type = "text/plain"
  }

Сопоставление:

  Яндекс Облако: yandex_lockbox_secret + yandex_lockbox_secret_version
  VK Cloud:      vkcs_keymanager_secret
  AWS:           aws_secretsmanager_secret

ТА ЖЕ ЛОВУШКА, ЧТО ВЕЗДЕ

  Документация провайдера предупреждает: аргументы ресурса,
  включая пароли, сохраняются в файле состояния открытым текстом.
  Мы это проверяли в Яндекс Облаке в практике 6 — нашли пароль
  в состоянии поиском по строке.

  Вывод одинаков для всех облаков: важно не то, какой сервис
  секретов вы выбрали, а кто имеет доступ к состоянию Terraform.


========================================================================
7. ЧТО ЗАПОМНИТЬ О VK CLOUD
========================================================================

  1. Провайдер — vk-cs/vkcs. Адрес vkcs/vkcs не существует.
  2. Аутентификация — учётные данные проекта и адрес Keystone;
     готовый файл можно скачать в консоли проекта.
  3. Бэкенд состояния — S3-совместимый, с явным endpoint
     и skip-флагами, блокировка через use_lockfile.
  4. Сеть — OpenStack: сеть, подсеть, роутер, группы безопасности.
     Без подключения к роутеру у машины нет выхода в интернет.
  5. Managed-базы — vkcs_db_*, Kubernetes — только второго поколения
     (v2) и только на Sprut.
  6. Секреты — Key Manager, но состояние всё равно содержит значения.
  7. Терминология: проект (вместо каталога), flavor (вместо пресета),
     SDN (вместо «тип сети»).

  И то же общее правило, что в курсе: не угадывайте имена ресурсов
  и аргументов. Смотрите документацию провайдера и схему:

    terraform providers schema -json | <разбор>

  Мы пользовались этой командой, когда разбирали ALB и группу машин
  в Яндекс Облаке, и она же выручит в любом другом облаке.
