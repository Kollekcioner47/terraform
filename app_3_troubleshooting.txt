ПРИЛОЖЕНИЕ 3. РАЗБОР ПОЛОМОК: СВОДНАЯ ТАБЛИЦА ОШИБОК

Как пользоваться этим приложением

  Здесь собраны ошибки, которые мы получили НА ЖИВОМ СТЕНДЕ
  в Яндекс Облаке, пока писали этот курс. Для каждой указано:
  как выглядит сообщение, в чём причина и что делать.

  Ошибка — это не признак того, что вы всё делаете неправильно.
  Половина из них возникает у всех, потому что сообщение облака
  не описывает настоящую причину. Умение быстро отличить
  «состояние» от «прав» и от «сети» экономит часы.

  Как читать: сначала найдите похожее сообщение, затем проверьте
  причину. В девяти случаях из десяти помогает одна из трёх команд:

    terraform state list
    terraform plan
    yc <сервис> <ресурс> list


========================================================================
1. АУТЕНТИФИКАЦИЯ, ПРАВА И ДОСТУП
========================================================================

  СИМПТОМ: Error: Invalid provider configuration
           no such file or directory (key.json)
  ПРИЧИНА: неверный путь к ключу сервисного аккаунта.
  ЧТО ДЕЛАТЬ: проверить, что файл существует и путь указан
  с прямыми слэшами даже в Windows: "C:/Users/user/.yc/key.json".
  Обратные слэши в путях Terraform — частая причина «файл
  не найден» там, где файл есть.
  Практика: 1.

  СИМПТОМ: AccessDenied (403) при загрузке объекта в бакет,
           при этом бакет создаётся нормально
  ПРИЧИНА: у сервисного аккаунта нет роли storage.editor
  или storage.admin. Роли admin на каталог для операций через
  S3-совместимый API НЕДОСТАТОЧНО.
  ЧТО ДЕЛАТЬ:

    yc resource-manager folder add-access-binding <folder_id> \
      --role storage.editor \
      --service-account-id <sa_id>

  Проверить выданные роли:

    yc resource-manager folder list-access-bindings <folder_id>

  Мы получили эту ошибку при первой же загрузке объекта
  в практике 6.
  Практики: 2, 6, 7.

  СИМПТОМ: AccessDenied для зашифрованного бакета, хотя роль
           на бакет выдана
  ПРИЧИНА: бакет зашифрован ключом KMS, а у сервисного аккаунта
  нет прав на ключ.
  ЧТО ДЕЛАТЬ:

    yc kms symmetric-key add-access-binding --id <key_id> \
      --role kms.keys.encrypterDecrypter \
      --service-account-id <sa_id>

  Практика: 6.

  СИМПТОМ: 400 Bad Request или AuthorizationHeaderMalformed
           при обращении к Object Storage
  ПРИЧИНА: неверный или неполный ключ доступа. Самая частая
  ошибка: в переменную попал весь объект ключа из вывода yc
  вместо значения key_id.
  ЧТО ДЕЛАТЬ: в ответе yc iam access-key create идентификатор
  лежит во вложенном объекте:

    { "access_key": { "key_id": "YCAJE3_..." }, "secret": "..." }

  В storage_access_key нужно именно key_id (начинается с YCAJE).
  Обратите внимание: облако отвечает 400, а не 403 — сообщение
  сбивает с толку.
  Практики: 2, 6.

  СИМПТОМ: Error: Failed to Update IAM Policy
           Role 'functions.invoker' not found
  ПРИЧИНА: неверное имя роли. Логичное на вид имя не существует.
  ЧТО ДЕЛАТЬ: правильное имя — functions.functionInvoker.
  Точные идентификаторы ролей смотрите в документации сервиса:
  у них свой стиль именования, догадаться не получится.
  Практика: 7.

  СИМПТОМ: Permission denied / Permission to resource denied
           при создании ресурса
  ПРИЧИНА: у сервисного аккаунта нет роли на каталог.
  ЧТО ДЕЛАТЬ: посмотреть выданные роли и добавить недостающую.
  Каждому сервису — своя роль: storage.admin для бакетов,
  mdb.admin для баз данных, lockbox.admin для секретов,
  container-registry.admin для реестра, kms.admin для ключей.
  Практики: 1, 4, 6, 7.

  СИМПТОМ: Error: quota limit exceeded
  ПРИЧИНА: исчерпана квота облака (машины, ядра, память, адреса).
  ЧТО ДЕЛАТЬ: проверить квоты в консоли, удалить лишнее или
  запросить увеличение. При группе студентов в одном облаке
  квота на ядра заканчивается быстрее всего.
  Практика: 1.

  СИМПТОМ: ssh: connect to host ... port 22: Connection refused
  ПРИЧИНА 1: машина ещё загружается (первые 30–60 секунд).
  ПРИЧИНА 2: неверный пользователь: в образах Ubuntu это ubuntu.
  ПРИЧИНА 3: в метаданных ключ записан без имени пользователя.
  ЧТО ДЕЛАТЬ: подождать, проверить метаданные. Формат обязательно
  «пользователь:ключ»:

    ssh-keys = "ubuntu:${file("~/.ssh/id_ed25519.pub")}"

  Практика: 1 (в прежней версии курса ключ был без пользователя,
  и вход по ключу не работал).

2. ПРОВАЙДЕР, ЗЕРКАЛО И ВЕРСИИ
========================================================================

  СИМПТОМ: Failed to query available provider packages
           host registry.terraform.io does not offer
           a Terraform provider registry
  ПРИЧИНА: не настроено зеркало, а публичный реестр недоступен
  из вашей сети.
  ЧТО ДЕЛАТЬ: настроить ~/.terraformrc (в Windows — %APPDATA%\terraform.rc)
  с network_mirror на https://terraform-mirror.yandexcloud.net/.
  Помните про ДВА разных зеркала: дистрибутив Terraform лежит
  на hashicorp-releases.yandexcloud.net, а провайдеры — на
  terraform-mirror.yandexcloud.net. Адреса не взаимозаменяемы.
  Практика: 1.

  СИМПТОМ: terraform providers lock падает с сообщением
           «host registry.terraform.io does not offer
           a Terraform provider registry»
  ПРИЧИНА: команда providers lock НЕ использует настройки
  provider_installation из terraform.rc. Зеркало надо указать явно.
  ЧТО ДЕЛАТЬ:

    terraform providers lock \
      -net-mirror=https://terraform-mirror.yandexcloud.net/ \
      -platform=linux_amd64 -platform=windows_amd64

  Практика: 8. Ответ: файл .terraform.lock.hcl получит суммы
  для обеих платформ.

  СИМПТОМ: Unsupported Terraform Core version
  ПРИЧИНА: версия Terraform старее указанной в required_version.
  ЧТО ДЕЛАТЬ: обновить Terraform. Для состояния в Object Storage
  нужен 1.6.3 и новее, для нативной блокировки (use_lockfile) —
  1.10 и новее.
  Практики: 1, 2.

  СИМПТОМ: в конвейере провайдер не устанавливается, локально
           всё работает
  ПРИЧИНА: в .terraform.lock.hcl нет контрольных сумм для платформы
  конвейера (например, вы работаете в Windows, а конвейер в Linux).
  ЧТО ДЕЛАТЬ: terraform providers lock -platform=linux_amd64
  (и -net-mirror при работе через зеркало). Файл закоммитить.
  Практика: 8.

3. СОСТОЯНИЕ И БЛОКИРОВКА
========================================================================

  СИМПТОМ: Error acquiring the state lock
           StatusCode: 412, api error PreconditionFailed
  ПРИЧИНА: работает другой процесс Terraform или остался замок
  от прерванного запуска. Код 412 — это сработавшая защита.
  ЧТО ДЕЛАТЬ: убедиться, что никто не применяет изменения;
  если процесс не работает — снять замок:

    terraform force-unlock <ID из текста ошибки>

  Практики: 2.

  СИМПТОМ: Backend configuration changed / Initialization required
  ПРИЧИНА: изменились настройки блока backend (имя бакета, ключ
  состояния).
  ЧТО ДЕЛАТЬ: terraform init -reconfigure — если вы переключаетесь
  между окружениями; terraform init -migrate-state — если
  действительно переносите состояние в другое хранилище.
  Практики: 2, 8.

  СИМПТОМ: Error: Variables not allowed (в блоке backend)
  ПРИЧИНА: в блоке backend использована переменная Terraform.
  Блок читается до того, как становятся известны значения
  переменных.
  ЧТО ДЕЛАТЬ: имя бакета и ключ состояния писать текстом,
  а секреты передавать через -backend-config или переменные
  окружения.
  Практика: 2.

  СИМПТОМ: InvalidBucketName: The specified bucket is not valid
  ПРИЧИНА: в имени бакета недопустимые символы — русские буквы,
  заглавные, подчёркивания. Часто появляется, когда имя
  подставлялось скриптом и «поехало» из-за кодировки файла.
  ЧТО ДЕЛАТЬ: только строчные латинские буквы, цифры, точка
  и дефис.
  Практика: 2 (мы получили эту ошибку именно из-за кодировки).

  СИМПТОМ: бакет не удаляется — «bucket is not empty»,
           хотя объектов в списке нет
  ПРИЧИНА: включено версионирование: остались предыдущие версии
  объектов и маркеры удаления.
  ЧТО ДЕЛАТЬ: удалить все версии, а не только текущие объекты.
  В учебной конфигурации помогает force_destroy = true.
  Сколько версий накапливается: за практику 2 — 24, за практику 8 —
  23. То есть версионирование работает, и место занимает.
  Практики: 2, 6, 8.

  СИМПТОМ: план предлагает создать ресурс, который уже есть
           в облаке
  ПРИЧИНА: ресурс «потерян» — он есть в облаке, но его нет
  в состоянии (правка состояния руками, работа из другого каталога,
  потерянный файл состояния, прерванный apply).
  ЧТО ДЕЛАТЬ: НЕ применять план. Сначала вернуть ресурс
  под управление импортом (практика 2), затем проверить план.
  Если ресурс «завис» и не нужен — удалить его в облаке и создать
  заново.
  Практики: 2, 7 (мы сами наступили на это, прервав apply).

  СИМПТОМ: terraform state rm не помогает: ресурс возвращается
  ПРИЧИНА: ресурс остался в конфигурации; после удаления
  из состояния следующий apply создаст его заново.
  ЧТО ДЕЛАТЬ: либо убрать описание из конфигурации, либо
  использовать блок removed (практика 2) — он оставляет намерение
  в истории изменений.
  Практика: 2.

4. ПЛАН И НЕОЖИДАННЫЕ ИЗМЕНЕНИЯ
========================================================================

  СИМПТОМ: план хочет ПЕРЕСОЗДАТЬ машину (must be replaced)
  ПРИЧИНА 1: обновился образ в семействе, которое вы указали.
  ПРИЧИНА 2: изменилось поле, которое нельзя менять на ходу
             (зона, платформа, тип диска).
  ПРИЧИНА 3: изменился ключ в for_each или индекс в count.
  ЧТО ДЕЛАТЬ: найти строку с «forces replacement» и решить
  осознанно: принять замену, закрепить версию образа, добавить
  lifecycle ignore_changes или блок moved.
  Практики: 1, 3.

  СИМПТОМ: план показывает изменения, хотя ничего не менялось
  ПРИЧИНА 1: кто-то правил ресурс руками в консоли (дрейф).
  ПРИЧИНА 2: изменился публичный адрес после перезапуска машины —
             в состоянии остались старые выводы.
  ЧТО ДЕЛАТЬ: посмотреть plan -refresh-only (только расхождения,
  без изменений) и решить: принять ручное изменение или вернуть
  как в конфигурации.
  Практики: 1, 2.

  СИМПТОМ: план собирается, но apply падает на середине
  ПРИЧИНА: часть ресурсов уже создана, часть — нет. Состояние
  остаётся в промежуточном виде.
  ЧТО ДЕЛАТЬ: прочитать ошибку, исправить конфигурацию и запустить
  apply снова — Terraform продолжит с места остановки. НЕ удаляйте
  состояние руками.
  Практики: 4, 7.

  СИМПТОМ: apply применил не тот план, который обсуждали
  ПРИЧИНА: план считался заново, а не взят сохранённый.
  ЧТО ДЕЛАТЬ: terraform plan -out=plan.tfplan и terraform apply
  plan.tfplan; в конвейере передавать план артефактом.
  Практика: 8.

5. МАШИНЫ, ДИСКИ, ГРУППЫ МАШИН
========================================================================

  СИМПТОМ: Error: Illegal argument subnet_id.
           Zone in subnet does not match expected zone
  ПРИЧИНА: машина создаётся в одной зоне, а подсеть — в другой.
  В Яндекс Облаке зона машины обязана совпадать с зоной подсети.
  Типовая причина: подсеть выбрана «первым ключом словаря»
  (keys() возвращает ключи отсортированными!), а зона — отдельной
  переменной.
  ЧТО ДЕЛАТЬ: брать зону из той же подсети:

    zone      = var.subnets[local.подсеть].zone
    subnet_id = module.vpc.subnet_ids[local.подсеть]

  Мы получили эту ошибку в практике 3.
  Практики: 3, 5.

  СИМПТОМ: Error: Instance does not allow stopping for update
  ПРИЧИНА: параметр нельзя менять на работающей машине.
  ЧТО ДЕЛАТЬ: allow_stopping_for_update = true и помнить, что
  машина будет остановлена (сервис недоступен).
  Практика: 1.

  СИМПТОМ: машина создана, но сервиса нет; в журнале cloud-init
           ошибки apt, «connection timed out»
  ПРИЧИНА 1: правило egress группы безопасности не пускает
             исходящий трафик (установка пакетов идёт на 80/443,
             DNS — на 53).
  ПРИЧИНА 2: у машины нет публичного адреса и нет NAT-шлюза —
             маршрута по умолчанию просто нет.
  ЧТО ДЕЛАТЬ: смотреть журнал на машине:

    sudo cloud-init status --long
    sudo cat /var/log/cloud-init-output.log

  Именно так мы и нашли причину в практике 4: сначала разрешили
  исходящий трафик, потом добавили NAT-шлюз.
  Практики: 4, 7.

  СИМПТОМ: в страницу, созданную cloud-init, не подставляется адрес
  ПРИЧИНА: запрос к службе метаданных сделан по пути AWS
  (169.254.169.254/latest/meta-data/...) или без заголовка.
  ЧТО ДЕЛАТЬ: правильный путь и заголовок:

    curl -H "Metadata-Flavor: Google" \
      "http://169.254.169.254/computeMetadata/v1/instance/..."

  ИСПРАВЛЕНО: в прежней версии курса использовался именно путь AWS,
  и скрипт не работал.
  Практика: 4.

  СИМПТОМ: вместо значения из метаданных приходит «Not Found»
  ПРИЧИНА: ключа с таким именем нет. Например, идентификатор
  подсети лежит в ключе network, а ключа subnet-id не существует.
  ЧТО ДЕЛАТЬ: не угадывать, а спрашивать список ключей:

    curl -s -H "Metadata-Flavor: Google" \
      http://169.254.169.254/computeMetadata/v1/instance/network-interfaces/0/

  Практика: 5.

  СИМПТОМ: машины группы висят в CHECKING_HEALTH,
           «Instance is unhealthy for 9m 21s»
  ПРИЧИНА 1: у машин нет публичных адресов и нет NAT-шлюза, поэтому
             cloud-init не смог установить пакеты.
  ПРИЧИНА 2: сервис не слушает порт проверки или порт закрыт
             группой безопасности.
  ЧТО ДЕЛАТЬ: проверить маршрут в интернет и порт. В учебной
  конфигурации включает NAT-шлюз переменная create_nat_gateway.
  Практики: 4, 7.

  СИМПТОМ: Error: Unsupported block type
           Blocks of type "healthcheck" are not expected here.
           Did you mean "health_check"?
  ПРИЧИНА: у группы машин блок называется health_check (без имени
  внутри), а у балансировщика — healthcheck (и name там обязателен).
  ЧТО ДЕЛАТЬ: убрать name у группы машин и оставить у балансировщика.
  Практика: 4.

  СИМПТОМ: expected deploy_policy.0.strategy to be one of
           ["proactive" "opportunistic"], got rolling
  ПРИЧИНА: значения rolling у группы машин нет (в отличие
  от Kubernetes).
  ЧТО ДЕЛАТЬ: proactive (менять сразу после правки шаблона)
  или opportunistic.
  Практика: 4.

  СИМПТОМ: Error: Cannot index a set value
  ПРИЧИНА: вложенные блоки объявлены МНОЖЕСТВАМИ, а множества
  не адресуются по индексу. Мы встретили это у балансировщика
  (listener, external_address_spec).
  ЧТО ДЕЛАТЬ: доставать значение выражением for и функцией one():

    one([for l in resource.listener : one(l.external_address_spec).address])

  Практика: 4.

  СИМПТОМ: узлы группы узлов Kubernetes не создаются, apply «висит»
  ПРИЧИНА: размер загрузочного диска узла меньше минимального.
  Причина видна только в состоянии группы машин:

    yc compute instance-group list-instances <instance_group_id>
    STATUS: CREATING_INSTANCE [27m]
    [INVALID_ARGUMENT] Disk size must be greater or equal than 30.0 GB

  ЧТО ДЕЛАТЬ: диск узла — 30 ГБ или больше. Terraform при этом
  не падает, а ждёт: сообщение об ошибке ищите в группе машин.
  Практика: 7.

  СИМПТОМ: после занятия остались диски и адреса
  ПРИЧИНА: auto_delete = false у дополнительного диска, статические
  адреса и NAT-шлюзы живут отдельно от машин.
  ЧТО ДЕЛАТЬ: проверять списки командой yc: compute instance list,
  compute disk list, vpc address list, vpc gateway list.
  Практики: 4, 5.

6. СЕТИ И БАЛАНСИРОВЩИКИ
========================================================================

  СИМПТОМ: Error: Invalid index
           the collection has no elements
  ПРИЧИНА: обращение по индексу [0] к пустому списку — например,
  адрес балансировщика, который ещё не создан.
  ЧТО ДЕЛАТЬ: обернуть в try() или использовать one().
  Практика: 5.

  СИМПТОМ: The expression result is null.
           Cannot include a null value in a string template
  ПРИЧИНА: подстановка null в строку вывода (часто в выводах,
  собирающих готовые команды).
  ЧТО ДЕЛАТЬ: проверять на null явно:

    x == null ? "ещё не создан" : "curl -s http://${x}/"

  Практика: 5.

  СИМПТОМ: Either external ipv4 address or internal ipv4 address
           or external ipv6 address should be specified
  ПРИЧИНА: у слушателя прикладного балансировщика указан пустой
  блок address {}.
  ЧТО ДЕЛАТЬ: указать тип явно: external_ipv4_address {} —

7. OBJECT STORAGE И СТАТИЧЕСКИЕ САЙТЫ
========================================================================

  СИМПТОМ: Error: Unsupported argument
           An argument named "labels" is not expected here (у бакета)
  ПРИЧИНА: у бакета Object Storage нет меток labels — есть tags.
  Это отдельный сервис со своим API.
  ЧТО ДЕЛАТЬ: использовать tags.
  Практика: 6.

  СИМПТОМ: сайт отдаёт 403 Forbidden, хотя объекты в бакете есть
           и публичный доступ «включён»
  ПРИЧИНА 1: включён только флаг read, а нужен ещё list. Документация
  Облака говорит прямо: хостинг не работает без публичного доступа
  «к объектам И ИХ СПИСКУ».
  ПРИЧИНА 2: бакет зашифрован своим ключом KMS — с шифрованием
  хостинг статики не поддерживается.
  ПРИЧИНА 3: к бакету применена политика, ограничивающая анонимный
  доступ к объектам и списку.
  ПРИЧИНА 4: включён доступ только из сервисных подключений VPC.
  ЧТО ДЕЛАТЬ: проверить все четыре условия. Полезная проверка:
  запрос к НЕСУЩЕСТВУЮЩЕМУ объекту. Если он даёт 404, служба
  хостинга работает, а дело именно в правах на чтение.
  Практика: 6 — мы прошли по всем четырём причинам, прежде чем
  нашли настоящую.

  СИМПТОМ: после добавления политики бакет стал недоступен вообще,
           включая владельца облака
  ПРИЧИНА: политика заменила модель доступа, а прав для своего
  аккаунта в ней не было.
  ЧТО ДЕЛАТЬ: перезаписать политику, добавив правило с полными
  правами для своего аккаунта, либо пересоздать бакет.
  Запомните: снять политику «в ноль» не получится — пустая политика
  тоже блокирует доступ.
  Практика: 6.

  СИМПТОМ: страница сайта не обновляется после правки файла
  ПРИЧИНА: объект загружен через source без source_hash — Terraform
  не читает содержимое файла и не видит изменений.
  ЧТО ДЕЛАТЬ: content_base64 = base64encode(file(...))
  или source плюс source_hash = filemd5(...).
  Практика: 6.

  СИМПТОМ: Error: error reading Storage Bucket: Forbidden (403)
           при работе с бакетом, к которому применена политика
  ПРИЧИНА: политика перекрыла доступ, и провайдер не может даже
  прочитать состояние бакета.
  ЧТО ДЕЛАТЬ: восстановить доступ средствами командной строки
  (перезаписать политику) — Terraform в этой ситуации уже
  не помощник.
  Практика: 6.

9. СЕКРЕТЫ И ЗАЩИТА ОТ УДАЛЕНИЯ
========================================================================

  СИМПТОМ: значение sensitive всё равно видно в файле состояния
  ПРИЧИНА: так и должно быть. sensitive защищает вывод команд,
  но не состояние. Секрет из Lockbox тоже попадает в состояние,
  если его записывает Terraform.
  ЧТО ДЕЛАТЬ: проверить самостоятельно:

    terraform state pull | grep -i <имя_секрета>

  Мы нашли пароль базы данных в состоянии открытым текстом.
  Меры: доступ к состоянию, шифрование бакета, генерация пароля
  внутри Lockbox, write-only аргументы там, где провайдер
  их поддерживает.
  Практика: 6.

  СИМПТОМ: terraform destroy не удаляет ключ KMS или секрет Lockbox
  ПРИЧИНА: deletion_protection = true.
  Текст ошибки:

    Key with id ... is protected from deletion.
    Change "deletion_protection" flag for deletion.
    Secret with id ... is protected from deletion.

  ЧТО ДЕЛАТЬ: снять флаг в конфигурации, применить изменение
  (terraform apply), и только потом удалять. Это правильное
  поведение защиты, а не сбой.
  Практика: 6.

  СИМПТОМ: Error: Instance cannot be destroyed
           Resource ... has lifecycle.prevent_destroy set
  ПРИЧИНА: защита от удаления в конфигурации.
  ЧТО ДЕЛАТЬ: снять prevent_destroy, применить, затем удалять.
  Помните: защита срабатывает и при замене ресурса — замена
  тоже удаление.
  Практика: 8.

  СИМПТОМ: Error: Invalid function argument
           while calling templatefile(path, vars)
           Invalid value for "vars" parameter: vars map does not
           contain key "ZONE"
  ПРИЧИНА: в шаблоне для templatefile осталась подстановка,

    printf '%s\n' "$${ZONE##*/}"

  Полезная привычка: перед первым запуском найти все подстановки:

    grep -n '\${' cloud-init/*.yaml

  Практика: 8 (мы наступили на это дважды — в команде
  и в комментарии, который объяснял эту же ошибку).

  ПРИЧИНА: в тесте указано command = apply, либо не подключён
  mock_provider.
  ЧТО ДЕЛАТЬ: для проверок логики — command = plan

  и без денег.
  Практика: 8.

11. ЧТО ДЕЛАТЬ, КОГДА НЕ ПОНЯТНО, ЧТО ПРОИСХОДИТ
========================================================================

  Порядок действий, который экономит время:

  1. ПРОЧИТАТЬ ОШИБКУ ЦЕЛИКОМ. Не первую строку, а весь текст.
     Часто настоящая причина — в третьей строке, а не в первой.
     Например, у группы узлов Kubernetes ошибка была вообще
     не в выводе Terraform.

  2. ПОСМОТРЕТЬ НА ОБЛАКО, А НЕ НА TERRAFORM:

       yc compute instance list
       yc vpc network list
       yc vpc security-group list-rules <id>
       yc managed-kubernetes cluster list

  3. ПРОВЕРИТЬ СОСТОЯНИЕ:

       terraform state list
       terraform state show <адрес>

  4. СВЕРИТЬ ИМЕНА АРГУМЕНТОВ СО СХЕМОЙ ПРОВАЙДЕРА — не по памяти
     и не по статьям:

       terraform providers schema -json > schema.json

     Мы так нашли точные имена блоков health_check и healthcheck,
     поля retained_top у политики очистки реестра и структуру
     вложенных блоков балансировщика.

  5. ПРОВЕРИТЬ ВЕРСИИ: terraform version, terraform providers.
     Половина «непонятных» ошибок — это устаревшие примеры
     из интернета на актуальной версии провайдера.

  6. ИСКАТЬ В ДОКУМЕНТАЦИИ ПРОВАЙДЕРА И ОБЛАКА ПАРАЛЛЕЛЬНО.
     Иногда права: документация облака описывает поведение сервиса,
     а провайдер — имена аргументов. Правда бывает в обоих местах.

  И главное: если что-то не работает, а план выглядит безобидно —
  остановитесь и не применяйте. Разобраться дешевле, чем
  восстанавливать.
