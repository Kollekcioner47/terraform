ПРИЛОЖЕНИЕ. БАКЕТ OBJECT STORAGE СО СТАТИЧЕСКИМ САЙТОМ

Продолжительность: 1 академический час.
Провайдер: yandex-cloud/yandex. Приложение выполняется в Яндекс Облаке.

ЧТО БУДЕТ К КОНЦУ ПРАКТИКИ

  Вы создадите бакет Object Storage, загрузите в него страницы сайта,
  включите хостинг статического сайта и откроете сайт в браузере.
  По дороге разберётесь, зачем для хостинга нужны ДВА флага публичного
  доступа, почему публичный сайт нельзя зашифровать своим ключом KMS,
  как Terraform замечает правку файла на диске и почему бакет
  с версионированием не удаляется «просто так». В конце вы уберёте
  за собой: удалите бакет вместе с объектами и версиями.

ЧТО НУЖНО ЗАРАНЕЕ

  * Доступ в облако: идентификаторы облака и каталога, сервисный
    аккаунт и его авторизованный ключ (практика 1).
  * Роль storage.editor у сервисного аккаунта. Без неё бакет
    создаётся, а загрузка объектов заканчивается AccessDenied.
  * Статические ключи доступа к Object Storage — их выдают
    в практике 2 командой yc iam access-key create.
  * Клиент curl: им проверяют, что сайт отвечает.

  ВНИМАНИЕ ПРО ДЕНЬГИ. Object Storage стоит копейки: платят
  за хранение гигабайт и за запросы. Виртуальной машины здесь нет,
  поэтому платить за вычислительные ресурсы не придётся.

------------------------------------------------------------------
0. КАТАЛОГ ПРОЕКТА И ФАЙЛЫ
------------------------------------------------------------------

Правило, которое нарушают чаще всего: ОДИН ПРОЕКТ — ОДИН КАТАЛОГ.
Terraform работает с состоянием в пределах каталога, поэтому файлы
разных проектов в одной папке перемешают ресурсы и состояние.

Создаём каталог приложения:

  mkdir -p ~/terraform-course/work/bucket-site
  cd ~/terraform-course/work/bucket-site

Здесь ~/terraform-course — клон репозитория с материалами курса.
Каталог work/ внутрь репозитория не попадает: он перечислен
в .gitignore, чтобы ваши эксперименты не смешивались с материалами
курса.

СТРУКТУРА ПРОЕКТА

  bucket-site/
  ├── outputs.tf
  ├── provider.tf
  ├── site/
  │   ├── assets/
  │   │   └── style.css
  │   ├── error.html
  │   └── index.html
  ├── storage.tf
  ├── terraform.tfvars.example
  ├── variables.tf
  └── versions.tf

  Плюс файлы, которые создаются при работе и в репозиторий
  не попадают: terraform.tfvars (значения переменных),
  terraform.tfstate (состояние), .terraform/ (провайдеры).
  Файл .terraform.lock.hcl, наоборот, нужно сохранить в git:
  он фиксирует версии провайдеров.

  Сети, машин и модуля сети тут нет: бакет и объекты — ресурсы
  уровня каталога.

КАК СОЗДАЁМ ФАЙЛЫ

  Файлы можно набрать по тексту приложения. Конструкция
  cat > имя-файла <<'EOF' записывает в файл всё, что введено до
  строки EOF, поэтому такой блок можно скопировать в терминал
  целиком. Строки cat и EOF стоят в первом столбце: отступ сломал
  бы завершение ввода.

  Весь код каждого файла приведён в тексте такими блоками — от
  versions.tf до site/assets/style.css. Готовые файлы приложения
  лежат в материалах курса, и их можно взять вместо набора
  по тексту:

    cp -r ~/terraform-course/files/app_bucket/. .

  Начнём с versions.tf: в нём указано, какая версия Terraform нужна
  и какая версия провайдера используется. Эти ограничения одинаковы
  во всех практиках курса — так конфигурации не разъедутся
  по версиям.

cat > versions.tf <<'EOF'
terraform {
  required_version = ">= 1.6.3"

  required_providers {
    yandex = {
      source  = "yandex-cloud/yandex"
      version = "~> 0.229.0"
    }
  }
}
EOF

Дальше — provider.tf. Провайдер подключается к облаку по ключу
сервисного аккаунта, но для Object Storage этого мало: бакет
и объекты создаются через S3-совместимый API, а он работает
по статическому ключу доступа. Поэтому в блоке провайдера есть
обе пары значений.

cat > provider.tf <<'EOF'
provider "yandex" {
  cloud_id                 = var.cloud_id
  folder_id                = var.folder_id
  zone                     = var.zone
  service_account_key_file = var.sa_key_file

  # Отдельные ключи для Object Storage.
  #
  # Object Storage работает по S3-совместимому API, и для него нужен
  # СТАТИЧЕСКИЙ КЛЮЧ ДОСТУПА — не тот же самый, что авторизованный
  # ключ сервисного аккаунта. В этом приложении без него не обойтись:
  # бакет и объекты создаются именно через S3-совместимый API.
  # Ключ создаётся отдельно:
  #
  #   yc iam access-key create --service-account-id <sa_id> \
  #     --description "доступ к Object Storage"
  #
  # В ответе два значения, и идентификатор лежит во вложенном объекте:
  #
  #   {
  #     "access_key": { "key_id": "YCAJEXXXXXXXXXXXXXXXXX" },
  #     "secret": "..."
  #   }
  #
  # В storage_access_key нужно значение key_id (начинается с YCAJE).
  # Если подставить весь объект целиком, Object Storage ответит
  # «400 Bad Request» вместо понятной ошибки про права.
  #
  # Значения можно не указывать здесь, а задать переменными окружения
  # AWS_ACCESS_KEY_ID и AWS_SECRET_ACCESS_KEY — так удобнее в конвейере.
  storage_access_key = var.storage_access_key
  storage_secret_key = var.storage_secret_key
}
EOF

variables.tf описывает входные данные приложения. Значения приходят
из terraform.tfvars или из переменных окружения TF_VAR_*. Обратите
внимание на две вещи: ключи доступа помечены sensitive (значения
не печатаются в выводе команд) и у имени бакета есть блок validation
с проверкой допустимых символов.

cat > variables.tf <<'EOF'
# Переменные приложения: бакет Object Storage со статическим сайтом.
#
# Переменные описываются один раз, а значения приходят из
# terraform.tfvars или из переменных окружения TF_VAR_*.
# Подробно про переменные — в практике 3.

variable "cloud_id" {
  type        = string
  description = "Идентификатор облака"
}

variable "folder_id" {
  type        = string
  description = "Идентификатор каталога"
}

variable "zone" {
  type        = string
  description = "Зона по умолчанию для ресурсов провайдера"
  default     = "ru-central1-d"
}

variable "sa_key_file" {
  type        = string
  description = "Путь к авторизованному ключу сервисного аккаунта"
}

# Статические ключи доступа к Object Storage.
#
# Они нужны потому, что бакет и объекты создаются через
# S3-совместимый API: провайдер обращается к хранилищу не по
# авторизованному ключу сервисного аккаунта, а по статическому
# ключу доступа. Его выдают командой:
#
#   yc iam access-key create --service-account-id <sa_id>
#
# В storage_access_key попадает значение key_id (начинается с YCAJE),
# а в storage_secret_key — поле secret из того же ответа (практика 2).
#
# Оба значения — секреты: в репозиторий они не попадают, передаются
# через terraform.tfvars (он в .gitignore) или переменными окружения
# AWS_ACCESS_KEY_ID и AWS_SECRET_ACCESS_KEY.
variable "storage_access_key" {
  type        = string
  description = "Идентификатор статического ключа доступа (key_id)"
  default     = null
  sensitive   = true
}

variable "storage_secret_key" {
  type        = string
  description = "Секретная часть статического ключа доступа"
  default     = null
  sensitive   = true
}

variable "project_name" {
  type        = string
  description = "Префикс в именах ресурсов"
  default     = "tf-bucket"
}

# Имя бакета. Смотрите на две вещи.
#
# Первое: имя должно быть УНИКАЛЬНЫМ во всём Object Storage — оно
# попадает в адрес сайта, поэтому занятое имя не получится взять
# даже в другом облаке. Добавьте к имени что-то своё: логин,
# название команды, дату.
#
# Второе: правила именования. Только строчные латинские буквы,
# цифры, точка и дефис; начинаться и заканчиваться имя должно
# буквой или цифрой. Блок validation проверяет это до обращения
# к облаку — иначе ошибку придётся разбирать по сообщению API.
variable "bucket_name" {
  type        = string
  description = "Имя бакета для статического сайта"

  validation {
    condition     = can(regex("^[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]$", var.bucket_name))
    error_message = "Имя бакета: строчные латинские буквы, цифры, точка и дефис."
  }
}

# Страницы сайта. Эти имена — ключи объектов в бакете, поэтому они
# должны совпадать с тем, что загружает storage.tf: site_index —
# главная страница, site_error — страница ошибки. Те же значения
# подставляются в блок website самого бакета.
variable "site_index" {
  type        = string
  description = "Главная страница сайта"
  default     = "index.html"
}

variable "site_error" {
  type        = string
  description = "Страница ошибки"
  default     = "error.html"
}
EOF

Последний файл раздела — terraform.tfvars.example. Это образец,
а не рабочий файл: значения в нём подставные. Копируем его
в terraform.tfvars и заполняем своими:

  cp terraform.tfvars.example terraform.tfvars

cat > terraform.tfvars.example <<'EOF'
# Пример значений переменных приложения.
#
# Скопируйте файл в terraform.tfvars и подставьте свои значения:
#
#   cp terraform.tfvars.example terraform.tfvars
#
# Файл terraform.tfvars в репозиторий не попадает (см. .gitignore):
# в нём лежат статические ключи доступа к Object Storage.

cloud_id    = "b1gXXXXXXXXXXXXXXX"
folder_id   = "b1gYYYYYYYYYYYYYYY"
zone        = "ru-central1-d"
sa_key_file = "/home/user/.yc/tf-course-key.json"

# Статические ключи доступа (создаются в практике 2).
#
# В storage_access_key попадает значение key_id из ответа команды
# yc iam access-key create, а не весь объект ключа целиком.
storage_access_key = "YCAJEXXXXXXXXXXXXXXXXX"
storage_secret_key = "SECRETXXXXXXXXXXXXXXXXXXXX"

project_name = "tf-bucket"

# Имя бакета уникально во всём Object Storage: его занимают все
# пользователи облака, поэтому добавьте к имени что-то своё —
# логин, название команды или дату.
bucket_name = "tf-bucket-ivan-2026"

site_index = "index.html"
site_error = "error.html"
EOF

  Обратите внимание: terraform.tfvars в репозиторий не попадает
  (он в .gitignore), потому что в нём лежат статические ключи
  доступа. Если файл terraform.tfvars отсутствует, Terraform
  спросит значения переменных в терминале — кроме тех, у которых
  есть default.

  Дальше обычный порядок работы: terraform init (скачивает
  провайдер), terraform plan (показывает, что будет сделано)
  и terraform apply (создаёт ресурсы). Состояние появится
  в terraform.tfstate в этом же каталоге.


------------------------------------------------------------------
1. ЗАЧЕМ БАКЕТ БЕЗ ВИРТУАЛЬНОЙ МАШИНЫ
------------------------------------------------------------------

Object Storage — это хранилище объектов: файлов с содержимым
и именем-ключом. Объекты складывают в бакеты, а доступ к ним идёт
по S3-совместимому API. Бакет — ресурс уровня каталога: ни машины,
ни подсети, ни сети ему не нужно.

У бакета есть режим ХОСТИНГА СТАТИЧЕСКОГО САЙТА. Включается он
блоком website, и после этого облако само отдаёт файлы по HTTP:
главную страницу — на корневой запрос, страницу ошибки — на запрос
к несуществующему объекту. Веб-сервер, nginx, обновления
безопасности и открытый порт 80 при этом не нужны: статику отдаёт
служба хранения.

ЧТО ЭТО ДАЁТ

  * Ни одной виртуальной машины: нет ядер, памяти и диска — значит,
    нечего обновлять и нечего патчить.
  * Плата — за хранение и запросы. Страницы сайта занимают
    килобайты, поэтому счёт за такое приложение близок к нулю.
  * Сайт не зависит от того, включена ли машина и перезагружалась
    ли она: отдачей файлов занимается сервис облака.

КОГДА ТАКОЙ ВАРИАНТ ГОДИТСЯ

  * Визитка, лендинг, документация, страница курса или отчёта.
  * Собранное одностраничное приложение (SPA): после сборки это
    обычные файлы.
  * Раздача статики и артефактов рядом с остальной инфраструктурой.

КОГДА НЕ ГОДИТСЯ

  * Нужна серверная логика: обработка форм, обращения к базе,
    авторизация. Бакет ничего не вычисляет — для динамики нужны
    функция, контейнер или машина.
  * Нужен HTTPS со своим сертификатом: у бакета адрес только
    по HTTP. Сертификат ставят на CDN или на прикладной
    балансировщик перед бакетом.
  * Нужны свои заголовки, перенаправления и ограничение доступа
    по IP: это тоже задачи CDN или балансировщика.

Разделение простое: бакет отвечает за СТАТИКУ, а всё остальное —
за сервисы перед ним. В практике 5 балансировщик уже стоял перед
машиной; здесь его можно поставить перед бакетом, если понадобится
HTTPS.

------------------------------------------------------------------
2. БАКЕТ И СТРАНИЦЫ САЙТА
------------------------------------------------------------------

Вся работа с хранилищем собрана в одном файле storage.tf: бакет
с настройками сайта, две страницы и загрузка каталога assets.
Комментарии в коде объясняют решения, которые ниже разобраны
по частям.

cat > storage.tf <<'EOF'
# Object Storage: бакет со статическим сайтом.
#
# Это приложение — только про бакет: ни виртуальной машины, ни сети,
# ни базы данных здесь нет. Зато подробно разобрано то, на чём обычно
# спотыкаются:
#
#   1) как отдать бакет наружу БЕЗ устаревшего ACL;
#   2) как Terraform понимает, что файл сайта изменился;
#   3) почему публичный сайт не совмещается с шифрованием своим
#      ключом KMS;
#   4) чем метки бакета отличаются от меток остальных ресурсов.
#
# Приватные данные, шифрование своим ключом KMS и политика доступа
# разобраны в практике 6. Здесь их нет намеренно: с шифрованием
# и с политикой публичный сайт не работает (см. ниже).

# ------------------------------------------------------------------
# БАКЕТ: ПУБЛИЧНЫЙ СТАТИЧЕСКИЙ САЙТ
# ------------------------------------------------------------------
#
# У этого бакета НЕТ шифрования своим ключом KMS, и это осознанное
# решение. Мы получили ошибку 403 на живом стенде, когда попробовали
# совместить шифрование KMS и публичный сайт:
#
#   curl -s http://<бакет>.website.yandexcloud.net/
#   403 Forbidden, Code: AccessDenied
#
# Причина: содержимое бакета зашифровано нашим ключом, а анонимный
# читатель не имеет права пользоваться этим ключом — значит, облако
# не может расшифровать объект и отказывает.
#
# ВЫВОД: публичные данные и данные, зашифрованные своим ключом, —
# это разные бакеты. Публичный сайт — здесь, приватные данные
# с шифрованием — в практике 6.

resource "yandex_storage_bucket" "site" {
  bucket = var.bucket_name

  # Публичный доступ к бакету.
  #
  # Это современный способ сделать бакет читаемым для всех — вместо
  # устаревшего поля acl = "public-read". Флагов три, и они означают
  # разное:
  #
  #   read        — можно читать объекты;
  #   list        — можно получать список объектов;
  #   config_read — можно читать настройки бакета.
  #
  # ВНИМАНИЕ: ДЛЯ СТАТИЧЕСКОГО САЙТА НУЖНЫ ОБА ФЛАГА — И read, И list.
  #
  # Документация Яндекс Облака говорит об этом прямо: хостинг
  # статического сайта не работает, если нет публичного доступа
  # «к объектам И ИХ СПИСКУ». Мы на этом споткнулись: включили только
  # read (рассудив, что список файлов посторонним видеть незачем),
  # и сайт отвечал
  #
  #   403 Forbidden, Code: AccessDenied
  #
  # при том, что объекты в бакете были и публичный доступ был
  # «включён». Несуществующий объект при этом давал честный 404 —
  # то есть служба хостинга работала, а анонимное чтение запрещалось.
  #
  # Там же в документации перечислены другие условия, при которых
  # хостинг не работает: шифрование бакета (поэтому у сайта нет
  # шифрования своим ключом) и политика доступа, ограничивающая
  # анонимный доступ к объектам и списку. Оба случая разобраны
  # в практике 6.
  #
  # ИСПРАВЛЕНО. В прежней версии курса публичность открывали полем
  # acl, а при проблемах с загрузкой файлов предлагалось заменить
  # acl = "public-read" на acl = "public-admin". Такого значения
  # не существует; кроме того, само поле acl объявлено устаревшим
  # (провайдер 0.146.0 и новее). Публичность открывают флагами
  # anonymous_access_flags, а для тонких правил есть политика доступа.
  anonymous_access_flags {
    read        = true
    list        = true
    config_read = false
  }

  # Версионирование: облако хранит предыдущие версии объектов.
  # Спасает от случайной перезаписи и от «мы залили не тот файл».
  # Обратите внимание: с версионированием объекты занимают больше места,
  # а удалить бакет можно только вместе с версиями (практика 2).
  versioning {
    enabled = true
  }

  # Настройки статического сайта: какая страница главная, какая —
  # при ошибке. Именно они превращают бакет в веб-сервер.
  website {
    index_document = var.site_index
    error_document = var.site_error
  }

  # force_destroy = true позволит удалить бакет вместе с объектами
  # и версиями. Для учебного стенда это удобно, для рабочего — опасно:
  # по умолчанию стоит false, и это правильно.
  force_destroy = true

  # Обратите внимание: у бакета НЕТ аргумента labels, в отличие
  # от машин, сетей и баз данных. Object Storage — отдельный сервис
  # со своим API, и метки в нём называются tags:
  #
  #   tags = { course = "terraform" }
  #
  # Попытка указать labels заканчивается ошибкой:
  #
  #   Error: Unsupported argument
  #   An argument named "labels" is not expected here.
  tags = {
    course   = "terraform"
    appendix = "bucket"
    purpose  = "public-site"
  }
}

# ------------------------------------------------------------------
# ОБЪЕКТЫ САЙТА
# ------------------------------------------------------------------
#
# ВАЖНАЯ ДЕТАЛЬ: как Terraform узнаёт, что файл изменился.
#
# Если указать source = "site/index.html", Terraform загрузит файл
# при создании объекта и больше не будет за ним следить: содержимое
# файла он не читает, а значит изменения не заметит. Правка страницы
# не приведёт ни к чему — это одна из самых частых жалоб новичков.
#
# Два способа решить это:
#
#   1. content_base64 = base64encode(file(...)) — содержимое попадает
#      в конфигурацию, и Terraform сравнивает его при каждом плане;
#
#   2. source = "..." плюс source_hash = filemd5("...") — содержимое
#      не попадает в конфигурацию, но хэш файла отслеживается.
#
# Мы используем первый способ для страниц (они небольшие) и второй —
# для остальных файлов сайта (таблицы стилей, картинок, скриптов).

resource "yandex_storage_object" "index" {
  bucket = yandex_storage_bucket.site.id
  key    = var.site_index

  content_base64 = base64encode(file("${path.module}/site/index.html"))
  content_type   = "text/html; charset=utf-8"
}

resource "yandex_storage_object" "error_page" {
  bucket = yandex_storage_bucket.site.id
  key    = var.site_error

  content_base64 = base64encode(file("${path.module}/site/error.html"))
  content_type   = "text/html; charset=utf-8"
}

# Второй способ: файл на диске и его хэш.
#
# Обратите внимание на for_each по результату fileset: так загружают
# целый каталог, не перечисляя файлы руками.
resource "yandex_storage_object" "assets" {
  for_each = fileset("${path.module}/site/assets", "*")

  bucket = yandex_storage_bucket.site.id
  key    = "assets/${each.key}"

  source      = "${path.module}/site/assets/${each.key}"
  source_hash = filemd5("${path.module}/site/assets/${each.key}")

  # Тип содержимого по расширению: без него браузер может не понять,
  # что это за файл, и предложит его скачать вместо отображения.
  content_type = lookup({
    "css"  = "text/css"
    "txt"  = "text/plain; charset=utf-8"
    "json" = "application/json"
    "js"   = "application/javascript"
  }, split(".", each.key)[length(split(".", each.key)) - 1], "application/octet-stream")
}

# Проверить, что объект доступен анонимно, можно без Terraform:
#
#   curl -s http://<бакет>.website.yandexcloud.net/assets/style.css
#
# А список объектов в бакете показывает команда:
#
#   yc storage s3api list-objects --bucket <бакет>
#
# Для приложения этого достаточно: приватность в одном бакете
# не настраивается. Публичность включается бакетом целиком —
# поэтому приватные данные держат в отдельном бакете без флагов
# и со своим ключом KMS (практика 6).
EOF

РАЗБОР ПО ЧАСТЯМ

  bucket = var.bucket_name

    Имя бакета. Оно должно быть уникальным во всём Object Storage
    и попадает в адрес сайта: <имя>.website.yandexcloud.net.

  anonymous_access_flags { read, list, config_read }

    Публичный доступ к объектам бакета. Именно он делает сайт
    открытым: без флагов служба хостинга ответит 403. Подробно —
    в разделе 3.

  versioning { enabled = true }

    Облако хранит предыдущие версии объектов: правка страницы
    не затирает прежнюю версию. Плата за это — место, которое
    занимают версии, и то, что бакет нельзя удалить, пока в нём
    есть версии (раздел 6).

  website { index_document, error_document }

    Включает хостинг статического сайта. index_document отдаётся
    на корневой запрос, error_document — при обращении
    к несуществующему объекту, вместе с кодом 404.

  force_destroy = true

    Разрешает удалить бакет вместе с объектами и версиями.
    Для учебного стенда удобно, для рабочего бакета опасно:
    по умолчанию false.

  tags = { course, appendix, purpose }

    Метки бакета. Именно tags, а не labels: у Object Storage своя
    модель меток, и об этом ниже в этом же разделе.

ЧТО ТАКОЕ index_document И error_document

  Оба параметра — просто имена объектов в бакете. Никакого
  отдельного каталога для них нет: index_document = "index.html"
  означает «на запрос к корню сайта отдать объект с ключом
  index.html». Поэтому страницы обязаны лежать в бакете под теми же
  ключами, что указаны в блоке website, — иначе сайт ответит 404
  при том, что файлы на диске есть.

  error_document работает так же: облако отдаёт этот объект, когда
  запрошенного ключа в бакете нет, и добавляет к ответу код 404.
  Если error_document не указан, на такой запрос придёт стандартная
  страница ошибки Object Storage.

ПРО АДРЕС САЙТА

  Сайт открывается по адресу <имя-бакета>.website.yandexcloud.net.
  Это обычный публичный адрес, и он работает по HTTP: по HTTPS
  на этом имени ответа не будет, потому что сертификата для домена
  website.yandexcloud.net у вашего бакета нет.

  Не путайте два адреса одного и того же бакета:

    <имя>.website.yandexcloud.net   хостинг статики: главная
                                    страница, страница ошибки, HTTP;
    <имя>.storage.yandexcloud.net   S3-совместимый API: объекты
                                    по ключам, без понятия «главная
                                    страница».

  Значение вывода website_endpoint — как раз первое, без схемы.
  Поэтому в командах проверки адрес пишется как http://<вывод>/.

  Ещё одна деталь про метки: у бакета, в отличие от машин, сетей
  и баз данных, нет аргумента labels. Попытка указать его
  заканчивается ошибкой:

    Error: Unsupported argument
    An argument named "labels" is not expected here.

  Метки Object Storage называются tags — так и написано в storage.tf.

ПРОВЕРИТЬ, ЧТО ХОСТИНГ ВКЛЮЧЁН

  Об этом говорит не код, а поведение: запрос к корню сайта отдаёт
  index.html, а запрос к несуществующему адресу — страницу ошибки
  с кодом 404. Если на оба запроса приходит 403, дело не в сайте,
  а в публичном доступе: смотрите раздел 3.

------------------------------------------------------------------
3. ПУБЛИЧНЫЙ ДОСТУП: ФЛАГИ, А НЕ ACL
------------------------------------------------------------------

Публичность бакета включают блоком anonymous_access_flags.
Устаревшее поле acl = "public-read" в курсе не используется,
и это не придирка к стилю: поле объявлено устаревшим (провайдер
0.146.0 и новее), а значения public-admin, которым иногда пытаются
«починить» доступ к файлам, не существует вовсе.

ФЛАГОВ ТРИ, И ОНИ ЗНАЧАТ РАЗНОЕ

  read        — можно читать объекты;
  list        — можно получать список объектов;
  config_read — можно читать настройки бакета (для сайта не нужен).

ПОЧЕМУ ДЛЯ ХОСТИНГА НУЖНЫ ОБА ФЛАГА — И read, И list

  Документация Яндекс Облака говорит об этом прямо: хостинг
  статического сайта не работает, если нет публичного доступа
  «к объектам И ИХ СПИСКУ». Мы на этом споткнулись: включили
  только read, рассудив, что список файлов посторонним видеть
  незачем. Объекты в бакете были, публичный доступ был «включён»,
  а сайт отвечал:

    403 Forbidden
    Code: AccessDenied

  При этом запрос к несуществующему файлу честно отвечал 404.
  То есть служба хостинга работала, а анонимное чтение
  запрещалось: без list она не может отдать объект. Лечится это
  одним флагом:

    anonymous_access_flags {
      read        = true
      list        = true
      config_read = false
    }

  Полезная диагностика на будущее: если несуществующий адрес
  отдаёт 404, а существующий — 403, значит хостинг работает,
  а дело именно в правах на объекты и их список.

ЧЕГО НЕЛЬЗЯ ДЕЛАТЬ ВМЕСТЕ С ПУБЛИЧНЫМ САЙТОМ

  * Шифровать бакет своим ключом KMS. Анонимный читатель не имеет
    прав на ваш ключ, поэтому облако не может расшифровать объект
    и отвечает тем же 403 Forbidden, Code: AccessDenied.
  * Вешать на бакет политику доступа, ограничивающую анонимное
    чтение объектов и списка. Документация перечисляет это среди
    условий, при которых хостинг не работает.

  Оба случая разобраны подробно в практике 6: там приватный бакет
  с шифрованием своим ключом и отдельный разбор политики, которой
  легко запереть себя снаружи. Полный разбор лежит в файле
  files/06_data_secrets/storage.tf; в этом приложении ни шифрования,
  ни политики нет намеренно.

ДВА СПОСОБА ЗАГРУЗКИ, И В ЭТОМ ЖЕ ЛОВУШКА

  Главная жалоба новичков звучит так: «я поправил index.html,
  применил apply, а на сайте старая страница». Причина — в способе
  загрузки.

  ЕСЛИ УКАЗАТЬ ФАЙЛ ТОЛЬКО ЧЕРЕЗ source:

    resource "yandex_storage_object" "index" {
      bucket = yandex_storage_bucket.site.id
      key    = "index.html"
      source = "${path.module}/site/index.html"
    }

  Terraform загрузит файл при создании объекта и больше за ним
  не следит: содержимое файла он не читает, поэтому изменения
  не заметит. Так выглядит самая частая ловушка этой темы.

  ДВА РАБОЧИХ СПОСОБА

    1. content_base64 = base64encode(file(...)) — содержимое
       попадает в конфигурацию, и Terraform сравнивает его
       при каждом плане. Так загружены обе страницы сайта.

    2. source = "..." плюс source_hash = filemd5("...") — файл
       читается с диска, а отслеживается его хэш. Так загружен
       каталог assets.

  В плане это выглядит так (меняем в странице номер версии с 1
  на 2):

    terraform plan

    # yandex_storage_object.index must be replaced
    + content_base64 = "PCFET0NUWVBFIGh0bWw+CjxodG1sIGxhbmc9InJ1Ij4..."
    Plan: 1 to add, 0 to change, 0 to destroy.

  Обратите внимание на формулировку must be replaced: объект
  не «обновляется», а заменяется целиком. Для статики это
  нормально, но помните, что с версионированием старая версия
  объекта остаётся в бакете и занимает место.

ЗАГРУЗКА КАТАЛОГА ЦЕЛИКОМ

    resource "yandex_storage_object" "assets" {
      for_each = fileset("${path.module}/site/assets", "*")
      bucket   = yandex_storage_bucket.site.id
      key      = "assets/${each.key}"
    }

  fileset перечисляет файлы в каталоге, for_each загружает каждый
  из них, а lookup подбирает content_type по расширению. Без
  content_type браузер может не понять, что за файл ему отдают,
  и предложит скачать его вместо отображения: таблица стилей
  подключается только с text/css.

  Новый файл в каталоге assets не требует правки кода: он появится
  в fileset, и следующий plan покажет его добавление. А вот
  удаление файла с диска Terraform заметит: объекта в конфигурации
  больше не будет, и провайдер удалит его из бакета.

  Такой же приём пригодится, когда файлов станет много: шаблон
  в fileset можно сузить, например до "*.css", а картинки грузить
  отдельным ресурсом со своим префиксом в ключе объекта.

  Поправьте текст в site/index.html, примените terraform apply
  и обновите страницу в браузере. Новая версия должна появиться
  сразу после apply. Если этого не произошло, смотрите раздел 7.

------------------------------------------------------------------
6. УБОРКА
------------------------------------------------------------------

Удаляем всё созданное:

  terraform destroy

  ...
  Destroy complete! Resources: 4 destroyed.

  yc storage bucket list

Это ожидаемый вывод: команда yc ничего не печатает, когда бакетов
в каталоге не осталось. Если вывод не пуст, бакет ещё существует —
посмотрите его имя в первой колонке и удалите вручную либо
разберитесь, почему Terraform его не удалил.

ПОЧЕМУ БАКЕТ НЕ УДАЛЯЕТСЯ БЕЗ force_destroy

  В бакете включено версионирование. Пока в нём лежат версии
  объектов и маркеры удаления, бакет считается непустым, а непустой
  бакет удалить нельзя:

    Error: error deleting Storage Bucket: BucketNotEmpty:
    The bucket you tried to delete is not empty

  Флаг force_destroy = true говорит провайдеру: сначала удали все
  объекты, все версии и маркеры удаления, а потом удаляй сам бакет.
  Именно поэтому в storage.tf он стоит. Уберите флаг — и destroy
  остановится с ошибкой выше.

  В рабочей среде force_destroy = true опасен: он снимает защиту
  от «удалил бакет вместе с данными одной командой». Там флаг
  оставляют выключенным, а версии чистят политикой жизненного цикла
  (задание 3 в разделе 8).

------------------------------------------------------------------
7. РАЗБОР ПОЛОМОК
------------------------------------------------------------------

Все ошибки ниже получены на живом стенде — это не пересказ
документации.

  СИМПТОМ: сайт отвечает 403 Forbidden, Code: AccessDenied, хотя
  объекты в бакете есть и публичный доступ «включён»
  ПРИЧИНА: включён только флаг read. Для хостинга нужен ещё list:
  без публичного доступа к списку объектов служба хостинга не может
  отдать объект.
  ЧТО ДЕЛАТЬ: добавить list = true в anonymous_access_flags
  и применить изменения. Проверить причину помогает запрос
  к несуществующему файлу: если он отвечает 404, хостинг работает,
  а дело именно в правах.

  СИМПТОМ: тот же 403, но включены оба флага
  ПРИЧИНА: бакет зашифрован своим ключом KMS. С включённым
  шифрованием хостинг статического сайта не поддерживается:
  анонимный читатель не имеет прав на ваш ключ.
  ЧТО ДЕЛАТЬ: убрать блок server_side_encryption_configuration
  из конфигурации бакета с сайтом и держать зашифрованные данные
  в отдельном бакете (практика 6).

  СИМПТОМ: Error: InvalidBucketName
  ПРИЧИНА: имя бакета не соответствует правилам: заглавные буквы,
  подчёркивание, длина больше 63 символов, имя начинается с дефиса
  или точки.
  ЧТО ДЕЛАТЬ: оставить только строчные латинские буквы, цифры,
  точку и дефис. Блок validation в variables.tf поймает такую
  ошибку ещё до обращения к облаку.

  СИМПТОМ: бакет не удаляется — «bucket is not empty»
  ПРИЧИНА: включено версионирование, поэтому в бакете остались
  версии объектов и маркеры удаления.
  ЧТО ДЕЛАТЬ: поставить force_destroy = true и удалить бакет через
  terraform destroy, либо снять версии вручную (практика 2).

  СИМПТОМ: Error: error creating Storage Bucket: BucketAlreadyExists
  (иногда то же самое приходит как Conflict: Conflict)
  ПРИЧИНА: имя бакета уникально во всём Object Storage, и его занял
  кто-то другой — в том числе в другом облаке.
  ЧТО ДЕЛАТЬ: изменить bucket_name, добавив логин, название команды
  или дату. Освободить занятое имя нельзя: имена бакетов
  не резервируются и не выдаются по заявке.

  СИМПТОМ: сайт открывается по адресу http://, но не по https://
  ПРИЧИНА: у бакета нет TLS-сертификата для домена
  website.yandexcloud.net, поэтому HTTPS на этом имени не отвечает.
  ЧТО ДЕЛАТЬ: поставить перед бакетом CDN или прикладной
  балансировщик, выпустить сертификат в Certificate Manager
  и направить на них свой домен (задания 4 и 5 в разделе 8).
  Для учебного стенда достаточно HTTP.

  СИМПТОМ: главная страница отвечает 404, хотя файлы на диске есть
  ПРИЧИНА: объект с ключом index.html не загрузился или назван
  иначе, чем указано в index_document.
  ЧТО ДЕЛАТЬ: сверить ключи объектов (yc storage s3api list-objects)
  со значениями переменных site_index и site_error.

8. ЗАДАНИЯ
------------------------------------------------------------------

  1. Своя страница ошибки. Замените текст в site/error.html
     на свой и убедитесь, что после terraform apply несуществующий
     адрес отдаёт новую страницу. Раз страницы загружаются через
     content_base64, правка должна доехать без дополнительных
     действий.

  2. Второй способ отслеживания. Переделайте загрузку index.html
     на source плюс source_hash = filemd5(...) и повторите
     упражнение 1. Сравните содержимое плана: в первом случае
     в плане видно содержимое файла, во втором — только хэш.
     Объясните, какой способ удобнее для страницы на 100 КБ.

  3. Жизненный цикл версий. Добавьте бакету политику жизненного
     цикла, которая удаляет старые версии объектов старше 30 дней.
     Поля правила смотрите по схеме провайдера:
     terraform providers schema -json. Примените изменения
     и объясните, почему старые версии не исчезают сразу: правило
     действует в фоне, а не в момент apply.

  4. Свой домен. Заведите публичную DNS-зону (практика 5) и запись
     типа CNAME на адрес сайта из вывода website_endpoint.
     Проверьте ответ командами dig или nslookup. HTTPS при этом
     не появится — объясните почему.

  5. CDN перед бакетом. Поставьте перед бакетом ресурс CDN
     с источником-бакетом, выпустите сертификат в Certificate
     Manager и проверьте, что сайт открывается по HTTPS. Обратите
     внимание: кэш CDN живёт своей жизнью, поэтому правка страницы
     видна не сразу.

  6. Приватная страница. Добавьте в бакет объект
     private/report.html и убедитесь, что он тоже доступен
     анонимно: публичность включается бакетом целиком, а не
     отдельным объектом. Сделайте второй бакет без флагов
     anonymous_access_flags и проверьте, что он отвечает 403.
     Какие роли нужны, чтобы прочитать объект из приватного бакета
     сервисным аккаунтом?
